## 2. Root Cause That Was Confirmed

The old adapter path mixed two incompatible PyReason input modes:

1. graph attributes via `pr.load_graph(graph)`
2. explicit facts via `pr.add_fact(...)`

For the same label, this is bad in PyReason:

| Mode | Result |
| --- | --- |
| graph attr only | no rule propagation |
| `add_fact(...)` only | rule propagation works |
| graph attr + `add_fact(...)` on same label | conflict; propagation blocked |

The stable boundary is:

- **graph** carries only structure
- **initial label facts** must go through `add_fact(...)`

This is why the adapter now builds a structure-only graph and lowers `PyReasonSession` facts into explicit fact registrations.

## 3. Current Remaining Issue

The real demo still does **not** show `compliant` / `high_confidence` in the interpretation, even though the rule engine is now running.

What is known:
- this is **not** the old adapter materialization bug
- the engine is now iterating and producing at least one derived edge fact
- the remaining issue looks like a **demo / rule-data / label-vocabulary** problem

Current hypothesis:
- PyReason may require a label to exist in the vocabulary before it can derive into it in this specific rule pattern, which might mean seeding `compliant` (for example with `[0,0]`) or otherwise making the label known up front

Important:
- treat that as a **hypothesis**, not a frozen conclusion
- do not encode “IDB labels require `[0,0]` initialization” into framework logic without a minimal isolated reproduction
