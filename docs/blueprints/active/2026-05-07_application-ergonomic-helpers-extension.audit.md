- Phase 0 implementation (2026-05-08): package migration shipped without behavior changes for existing Batch 2 helpers. The known single-file ProofFrame gate was converted immediately to a package-aware boundary test to keep focused regression green after `capability_helpers.py` became a package.
- Phase 0 audit caveat (2026-05-08): plain `python -c` may resolve imports through the editable install from the parent worktree; verification for A worktree import paths must use `PYTHONPATH=src` from `/Users/zhenzhili/hnsm-backend-A` so imports resolve against the A filesystem.
- Phase 1 implementation (2026-05-08): Check helper is a DTO builder only. It performs helper-owned input-origin and binding-form validation, but leaves engine literal checks, `$` variable prefix checks, and multi-head plan rejection to the `CheckRequest` protocol validator.
- Phase 1 strict-audit polish (2026-05-08): recorded the 54-test focused regression count and added a local cycle guard to `_reject_sdk_origin(...)`; self-referential binding values now raise `CapabilityHelperError` instead of recursing.
- Phase 2 implementation (2026-05-08): Diagnose helper intentionally reuses the same shared `_binding.py` utility as Check instead of importing Check-private functions. This is the first real cross-helper reuse point, so the shared utility boundary is explicit and capability-family modules remain thin DTO builders.
- Phase 1-2 strict-audit fix (2026-05-08): SDK-origin rejection now traverses application dataclass DTO fields before builder DTO construction. This keeps `CompiledDerivationPlan` application-typed at the boundary while still catching SDK objects embedded in loose fields such as `body_ir: list[Any]`.
- Phase 3 implementation (2026-05-08): ProofFrame helper bridges the blueprint's `overlay=None` convenience to the protocol's required `EvaluationOverlay` by constructing `EvaluationOverlay()` before DTO construction. It remains a pure DTO builder and does not import or call `recheck_proof_frame(...)`.
- Phase 4 implementation (2026-05-08): Rule overlay helpers intentionally differ from Phase 3 overlay handling. `overlay=None` does **not** mean an empty overlay at request time; each helper synthesizes the one required `Rule*Action` and returns an overlay containing exactly that action. Non-empty caller overlays are rejected rather than merged so helpers remain deterministic one-action DTO builders.
- Phase 3-4 strict-audit fix (2026-05-08): Rule overlay helpers must scan raw caller inputs for SDK-origin objects before constructing `Rule*Action` protocol DTOs; otherwise SDK objects in top-level or family-specific positions can surface as `CapabilityHelperError` / `ProtocolShapeError` instead of `OriginPackageError`. The `note=None` helper parameter is retained and documented as pass-through to the existing action DTO `note` fields, not as a new request DTO field.
- Phase 5 implementation (2026-05-08): Round event payload helper is a thin projector dispatch, not a recorder wrapper. It supports only the 5 currently projector-backed capability result kinds; lifecycle events stay owned by `RoundRecorder`, and rule-overlay event kinds remain deferred until audit-layer projectors/kinds exist.
- Phase 5 strict-audit polish (2026-05-08): Behavior was already aligned; polish added explicit regression coverage for nested SDK-origin objects inside request dataclasses and synchronized docs chronology after the Phase 5 surface landed.
- Phase 6 implementation (2026-05-08): Cross-cutting invariants are scoped by helper generation. Static no-SDK / no sibling-runtime / no recorder checks apply to the whole helper package; runtime origin-package and determinism invariants apply to Phase 1-5 builders. Batch 2 Store/projector reads remain legal precedent and are not treated as drift.
