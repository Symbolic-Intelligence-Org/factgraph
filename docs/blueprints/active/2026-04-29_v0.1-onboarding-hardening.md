# v0.1 Onboarding Hardening

- Date: 2026-04-29
- Status: implemented
- Branch: `v0.1-onboarding-hardening`(off `oss-prep-v0.1` @ `bdd34a5`)
- Companion audit: `2026-04-29_v0.1-onboarding-hardening.audit.md`

## 1. Goal

消除 v0.1 OSS publish 前 cold-onboarding 阶段的 critical silent footguns,以及 user-path docs 对 v0.1 wheel 之外 namespace 的引用泄露。

这是发布前 hardening:
- 不重构 SDK 主架构、不重写 application、不改公开符号命名
- 不引入新 feature、不下沉 DSL primitive、不改 K-contract
- 范围严格控制在"无报错但语义错"的写入路径,以及主用户文档对 wheel 之外 namespace 的依赖

成功定义:cold-install 用户照 README + `kernel.sdk` 主用户文档操作,**不会撞到无错误反馈的语义错位**(写入不显式 / cardinality 错配 / Identity 半残),**不会从主路径 docs 链接到 v0.1 wheel 不存在的 namespace**。

## 2. Background

2026-04-29 完成的 4-agent simulated cold-walk 与 docs 审计交叉确认了三类 critical 问题:

- **SDK 写入路径不一致**:`sdk.set/add` 不自动写 identity / `<T>:exists`,`sdk.batch` 写;`set/add` 不校验 cardinality,`batch` 校验。新用户照 README 用 `set` 写完后再跑 query / derivation 静默返回空,无任何反馈。
- **Identity 规则有 silent footgun**:`Identity()` 不带 `primary_key=True` 仍可 schema compile + 建 store + ingest;身份语义悄悄错。仓库已有 secondary identity coordinate 设计(`locale`、`lang`),所以规则应是"至少一个 primary_key=True",而不是"禁止所有 no-primary"。
- **主用户路径 docs 引用 v0.1 wheel 之外 namespace**:`sdk/docs/00_user_guide(.en).md` 引 `domains.ecss.sdk_helpers`;`docs/SECURITY.md` 主叙事是未发布的 HTTP service 鉴权;`audit/docs/01_overview.md` 多处把 `service.*` / `domains.*` 当成 audit consumer 必经路径。

## 3. Decisions(locked 2026-04-29)

### D1 — `sdk.set/add` 行为

保留 `sdk.set/add` 作为 ergonomic public API。**内部改成 application write-plan adapter**,不再直接调底层 `set_field/add_field`。

行为契约:
- 写入路径走 `kernel.application.entity_write` 的 write-plan / apply-plan API
- 自动 materialize identity predicates + `<T>:exists`
- 返回值仍为本次 field mutation 对应的 assertion id;identity / exists 写入产生的 assertion id 不返回
- 传入的 `e_ref` 必须 resolvable 到该 entity 的完整 identity(包含所有 declared `Identity(...)` 字段,含 primary 与 secondary identity);无法解析时抛 actionable `SDKStoreError`,**不 fallback 到旧 direct-write 路径**

差异化决策(明文记录):

| 路径 | identity 缺失时行为 | 理由 |
|---|---|---|
| `sdk.set` / `sdk.add` | hard error | 用户手里已经持有对象引用,语义是"我知道在写谁";cache miss 通常意味着 ref 来源错了,fallback 会掩盖 bug |
| `sdk.ingest` | 保留现有 fallback | 外部 DTO 灌入路径,输入未必先经 `sdk.ref(...)`;fallback 是有现实价值的 ergonomic 行为 |
| `sdk.batch` | 自有 cache 路径 | 当前行为不在本 blueprint 改动范围 |

blueprint 只描述行为契约("ref must be resolvable to full identity"),**不钉死内部缓存字段名**。

### D2 — Cardinality 校验落点

落 `kernel.application` runtime,SDK 层 wrap 错误。

行为契约:
- application write-plan / mutation planning 阶段校验 `set` ↔ `single`、`add` ↔ `multi` 类型对应
- 违反时 application 抛 `EntityWriteError(code="FIELD_CARDINALITY_MISMATCH")`(或与现有 EntityWriteError 体系一致的等价表达)
- `SDKStore.set/add` 把 application 错误转成 `CardinalityError`(已存在于 `kernel.sdk.errors`)或带 code/path 的 `SDKStoreError`
- batch / ingest / direct SDK facade 全部收敛到同一 runtime contract,不再各自实现校验

明确不在本 D2 范围:**`set` 同一 single 字段两次不拦** —— 这是 append-only ledger 的合法更新语义(产生新 assertion,chosen view 更新),不是 cardinality violation。

### D3 — Identity primary_key 规则

修正版规则(secondary identity 合法):
- 每个 `Entity` 必须至少声明一个 `Identity(primary_key=True)`;否则 schema compile 时抛 `SDKSchemaError`
- 非 primary `Identity()` 仍允许(secondary identity coordinates,例 `locale`、`lang`)
- 多个 primary_key 不额外禁止(为后续 composite primary key 留口;本 blueprint 不实现 composite 行为)
- 仅消除"zero-primary entity"的 silent footgun

迁移要求(详见 §4 commit 1a):仓库现有 11 处 Python `Identity()` 无 primary_key 调用 + 3 处 notebook 命中,必须分类迁移:
- secondary identity(同 entity 已有别的字段是 primary)→ 保留原样
- zero-primary entity → 加 `primary_key=True`
- 若发现某 test 就是在验证 no-primary 行为 → 改为验证新 hard error

triage 表先于 1a 实施(写入 audit 文件,不写进主 blueprint)。

### D4 — Query DSL 错误 UX

**不在本 scope。**

Deferred 到 v0.1.x backlog:
- `unsupported DSL term: Field` 等错误信息不可操作
- where atom 缺 location / path 提示
- 多 entity_ref 字段 `field == var` 提前 eager 解为 bool 的边界

理由:伤 onboarding,但**不写错数据,不阻塞 v0.1 publish**;改 DSL 内部体量超出 hardening 边界。

## 8. Risks / footguns

- **Identity 迁移分类错误**:secondary identity 误改为 primary,或 zero-primary 漏改。缓解:1a 之前出 triage 表(写入 audit),逐项分类;1a 实施后回归全 suite。
- **e_ref 来源边界 case**:用户从外部传入 manually constructed e_ref(非 `sdk.ref(...)`)在 D1 后撞 `SDKStoreError`。这是有意行为(消除 silent path)。缓解:user_guide 在 commit 2 明示 ref-first 是 contract;错误信息要 actionable(说明"用 sdk.ref(EntityType, **identity_kwargs) 先生成 e_ref")。
- **Application cardinality 校验影响 ingest 既存测试**:cardinality 第一次成为 batch / ingest / SDK 共同 contract,既存 ingest 路径假设若不一致会暴露。缓解:1b 实施时同跑 ingest 全 suite,出现失败时按"既有 ingest 行为不变"原则修正校验,而不是反向修测试。
- **`00_user_guide` 替代示例设计偏离原意**:替换 ECSS 段落时若新示例不能体现"optional-domain 边界 / schema helper"等原本想说的概念,文档教学价值丢失。缓解:commit 2 implementing 阶段先草拟示例 + user review,再写入文档。
- **Branch off oss-prep-v0.1 时序**:hardening 完成 merge 时若期间 oss-prep-v0.1 有新 commit,可能要 rebase。当前 oss-prep-v0.1 处于稳态(`bdd34a5`),merge 风险低。

### Deviations

Two implementation details were tightened during 1c:

- `_legacy_ingest_set_or_add` was kept as a direct `set_field/add_field` fallback so ingest fallback does not recurse through the newly hardened `sdk.set/add` adapter.

Both changes preserve the locked D1 decision: `sdk.set/add` use the application write-plan path with no fallback, while ingest keeps its DTO-oriented fallback.
