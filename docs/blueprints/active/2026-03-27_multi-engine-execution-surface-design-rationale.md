## Problem Statement

PyReason first landed as an adapter-local vertical slice (schema, session, runner, accept, ledger) that **bypassed core**. It used a parallel set of containers (PyReasonRuleDef, PyReasonSession, adapter-local AcceptResult), a parallel compilation path, and a parallel accept flow. The original problem statement in this rationale was that shared `Rule.engine_ext` had not yet been implemented and an adapter-local wrapper had been built instead.

The result is two incompatible pipelines where users must learn different APIs depending on which engine they use. This contradicts the framework's core narrative: "users write rules and get results through one interface; engine-specific capabilities are handled by adapters behind that interface."

## What Makes This Cool

A framework where you can write `Rule(where=[...], engine_ext=PyReasonRuleExt(timestep_delay=1))`, call `store.evaluate(mode="pyreason")`, and get back the same `CandidateSet` you'd get from Souffle. The engine is a detail; the interface is universal. Your audit report looks the same regardless of which engine produced the results.

## Constraints

1. **435 existing tests must remain green** — no regressions
2. **Souffle path must not change** — its pipeline is stable and tested
3. **Annotation Store already works** — this redesign must integrate with it, not replace it
4. **42 frozen contracts** — many are relevant (engine_ext, annotation, confidence semantics)
5. **Hook restriction** — `src/factpy_kernel/` edits must be provided as code

## Premises

1. **The user should see one pipeline, not two.** A rule author writes `Rule(...)` + `engine_ext`, calls `evaluate`, gets `CandidateSet`, calls `accept`. Same API for every engine.

2. **"Unified interface, not unified implementation" is the correct principle.** Adapters can do wildly different things internally. The constraint is: inputs and outputs conform to shared types.

3. **The current shadow pipeline is a design problem, not just an implementation gap.** It's not that we "haven't wired it up yet." We built structures (PyReasonRuleDef, adapter-local AcceptResult) that are inherently incompatible with the core pipeline.

4. **engine_ext belongs on shared Rule AND Derivation.** Rule is the definition/registry object; Derivation is the evaluation subject (`sdk.evaluate(Derivation(...))`). Both need engine_ext because:
   - Rule.engine_ext: carries engine-specific rule semantics (timestep_delay) for compilation
   - Derivation.engine_ext: carries engine-specific evaluation hints for the derivation subject
   - The evaluate dispatch reads from Derivation (since that's what enters `Store.evaluate()`), not from Rule directly

## Approaches Considered

### Approach A: Interface-Level Fusion (Recommended)

**Summary:** Add `engine_ext` to shared Rule/Derivation, register PyReason as a proper engine evaluator returning CandidateSet, deprecate adapter-local wrappers. All 7 layers converge on the core pipeline's interface types.

**Effort:** L (human: ~2 weeks / CC: ~6-8 hours with iteration)
**Risk:** Med-High — touches frozen dataclass (blast radius across 435 tests), lowering, evaluate dispatch, accept flow. Mitigated by: feature-flag `engine_ext=None` default, layer-by-layer test regression, Souffle path untouched

**Concrete changes by layer:**

| Layer | Change |
|-------|--------|
| 1. SDK | Add `engine_ext: EngineExtBase \| None` to Rule + Derivation frozen dataclass |
| 2. Compile | `engine_ext` exists **only on in-memory Rule/Derivation objects**. It does NOT enter `to_authoring_payload()` or compiled/persisted artifacts. When evaluate dispatch needs it, it reads from the in-memory Derivation object that the caller passed in. WhereIR stays unchanged. No serialization/deserialization protocol needed for v0. |
| 3. Dispatch | Add `"pyreason"` to `EvaluateMode`. Add `engine_ext: EngineExtBase \| None = None` kwarg to `evaluate_store()` and `EngineEvaluatorFn` signature. Passed through to engine evaluator |
| 4. Execute | New `pyreason_engine_eval(store, ..., engine_ext=None)` registered via `__init__.py`. Internally: materialize EDB from Ledger → PyReasonSession (inverse of accept), compile WhereIR → rule strings, run PyReason, extract → CandidateSet. Returns one CandidateSet per derived fact |
| 5. Results | PyReason engine_eval returns `list[CandidateSet]` with `support_kind=engine_no_witness_v1`. Additionally returns a `PyReasonEvalResult` wrapper containing both `candidates: list[CandidateSet]` and `pending_annotations: dict[str, list[dict]]` keyed by `candidate_id` |
| 6. Accept | Generic `accept_candidate_set()` used. After accept, caller calls `pyreason_persist_annotations(ledger, eval_result, accept_result)` which maps `candidate_id → written_assertions[i]["asrt_id"]` and writes `pyreason/semantic/*` AnnotationRows. No module-level cache; annotations are bound to the `PyReasonEvalResult` object returned from engine_eval |
| 7. Audit | Annotations queryable via existing `find_annotations()`. Trace persistence deferred to v1 |

**Pros:**
- Implements the frozen decision (engine_ext on shared Rule)
- Users see one API regardless of engine
- Existing accept/audit infrastructure reused
- Annotation Store integration natural

**Cons:**
- Changing frozen dataclass Rule requires careful migration
- WhereIR → PyReason compiler is new code (but scoped to PredAtom + literals v0)
- Post-accept annotation hook is a v0 compromise

### Approach B: Formalized Adapter Protocol

**Summary:** Minimal core changes (only EvaluateMode gate). Define a formal `EngineAdapter` protocol (interface) that both Souffle and PyReason implement. Each adapter has its own pipeline, but the protocol enforces: same input types (Rule with engine_ext), same output type (CandidateSet), same annotation contract.

**Effort:** M (human: ~1 week / CC: ~2 hours)
**Risk:** Low — no core changes, just protocol definition + PyReason conformance

**Pros:**
- Zero risk to existing Souffle path
- Each adapter retains full internal freedom
- Protocol is documentation-as-code

**Cons:**
- Users still learn two integration patterns (even if types match)
- `Store.evaluate(mode="pyreason")` still requires core changes (EvaluateMode gate)
- Protocol enforcement is runtime-only, not compile-time
- Adapter-local wrappers (PyReasonRuleDef) would still exist alongside Rule.engine_ext

### Approach C: Deferred — Stabilize Adapter-Local First

**Summary:** Accept that PyReason is a shadow pipeline. Clean up the worst inconsistencies (rename adapter AcceptResult, document the two-pipeline reality) but don't attempt fusion yet. Wait for a third engine to reveal the true abstraction.

**Effort:** S (human: ~2 days / CC: ~30 min)
**Risk:** Low

**Pros:**
- Minimal disruption
- Avoids premature abstraction
- Honest about current maturity

**Cons:**
- The shadow pipeline gets further entrenched
- Users learn two APIs
- Design debt compounds
- At the time of this rationale, the frozen engine_ext decision was still unimplemented

## Recommended Approach

**Choose A: Interface-Level Fusion.**

The engine_ext decision had already been deferred twice when this rationale was written. Each deferral created more divergence. That diagnosis still explains why the later `Rule.engine_ext` alignment was the correct cleanup path.

The work is well-scoped: `EngineExtBase` base class (~5 lines), one field on Rule + Derivation, WhereIR compiler v0 (pred atoms + literals), `pyreason_engine_eval()` (wraps existing runner), and annotation persistence via `PyReasonEvalResult`. Core changes are ~15-25 lines across `types.py`, `_evaluate.py`, `runtime.py`.

## Frozen Design Contracts (approved 2026-03-27)

### F1: engine_ext crosses compile boundary as independent kwarg

`engine_ext` does NOT enter `to_authoring_payload()` or any compiled/persisted artifact. Instead, `sdk.evaluate()` extracts `derivation.engine_ext` separately and passes it as an independent kwarg to `evaluate_store()`:

```python
# sdk/store.py evaluate path
compiled = derivation.to_authoring_payload()  # unchanged, no engine_ext
engine_ext = derivation.engine_ext             # extracted separately
evaluate_store(..., engine_ext=engine_ext)     # new kwarg
```

`evaluate_store()` signature gains `engine_ext: EngineExtBase | None = None`, forwarded to `engine_evaluate(**engine_kwargs)`.

### F2: annotation side-channel via Store pending state

`EngineEvaluatorFn` return type stays `list[CandidateSet]`. Annotations travel via Store instance pending state:

```python
# Inside pyreason_engine_eval():
store._engine_pending_annotations[run_id] = annotation_templates

# After accept, caller calls:
pyreason_persist_annotations(store, run_id, accept_result)
# which: reads pending, maps candidate_id → asrt_id, writes AnnotationRows, clears pending
```

Lifecycle: `evaluate → accept → persist → clear`. Single-threaded; no concurrent run_id collision in v0.

### F3: PyReason v0 fact semantics = attribute existence model

v0 freezes on "attribute existence" model, consistent with current tested code:
- Node fact: `graph.nodes[node_ref][pred_short_name] = 1` (bound still applies)
- Derived extraction: outputs `"true"` / `"false"` (not arbitrary values)
- WhereIR compiler generates: `popular(X) <-2 strength(Y, X), popular(Y)` (no value variables)
- Value-carrying predicates deferred to v1

### F4: v0 first closed on Derivation.engine_ext, then aligned Rule.engine_ext to the same carrier

The first closed loop was:
- Derivation(where=[...], mode="pyreason", engine_ext=PyReasonRuleExt(...))
- sdk.evaluate(derivation) → engine_ext extracted → pyreason_engine_eval()

Current implementation now also supports `Rule.engine_ext` as the preferred definition-time carrier for adapter-local PyReason rule compilation, while `PyReasonRuleDef` remains compatibility-only.

### F5: EDB materialization default bounds for non-PyReason facts

When Ledger facts from non-PyReason sources enter PyReason:
- Default bound: `[1.0, 1.0]` (definitely true)
- No temporal: `active_from=0, active_to=None`
- Rationale: if a fact was accepted into the Ledger, it's treated as ground truth for PyReason EDB. Engine-native annotations (if present) can refine this in v1.

## Resolved Design Details

### EngineExtBase Contract

```python
class EngineExtBase:
    """Base class for engine-specific rule extensions.

    Subclasses must be frozen dataclasses. The framework never inspects
    fields; only the target engine's adapter reads them.
    """
    pass
```

No methods, no required fields. It's a marker type for isinstance checks. Engine adapters define their own fields:

```python
@dataclass(frozen=True)
class PyReasonRuleExt(EngineExtBase):
    timestep_delay: int = 0
```

### Migration: Adding engine_ext to frozen Rule and Derivation

Both are frozen dataclasses. Adding `engine_ext: EngineExtBase | None = None` is safe because:
- Default is `None` — all existing constructions remain valid
- `engine_ext` is **in-memory only** — it does NOT enter `to_authoring_payload()`, compiled artifacts, or persisted payloads. No serialization/deserialization protocol needed for v0.
- No schema version bump needed — it's additive and non-persisted
- `Derivation.mode` already determines which engine runs; `engine_ext` adds engine-specific parameterization on top of `mode`

**Rule vs Derivation distinction:**
- `Rule.engine_ext` → consumed by rule compilation (e.g., `timestep_delay` embedded in rule syntax)
- `Derivation.engine_ext` → consumed by evaluate dispatch (e.g., passed to engine evaluator as kwarg)
- In practice for v0, they may carry the same ext object. But they are conceptually separate: Rule defines "how to express this rule in the engine," Derivation defines "how to run this evaluation in the engine."

### Error Cases

| Scenario | Behavior |
|----------|----------|
| `engine_ext=PyReasonRuleExt(...)` + `evaluate(mode="souffle")` | **Error.** Raises `ValueError("engine_ext type PyReasonRuleExt is not compatible with engine 'souffle'")`. Per frozen decision: presence of engine_ext pins the rule to a specific engine; cross-engine invocation is a type mismatch, not a degradation. |
| No `engine_ext` + `evaluate(mode="pyreason")` | Valid — timestep_delay defaults to 0. No error. |
| `engine_ext=SouffleRuleExt(...)` + `evaluate(mode="pyreason")` | PyReason adapter checks `isinstance(engine_ext, PyReasonRuleExt)`. If wrong type, raises `ValueError("engine_ext type mismatch")`. |

### WhereIR → PyReason Compiler Feasibility

Example mapping (proof the subset is expressible):

```
WhereIR input:
  [("pred", "user:popular", ("$x", "$v")),
   ("pred", "friends:strength", ("$y", "$x", "$s")),
   ("pred", "user:popular", ("$y", "$pv"))]

PyReason output (with timestep_delay=2):
  "popular(X, V) <-2 strength(Y, X, S), popular(Y, PV)"
```

Mapping rules:
- `("pred", pred_id, terms)` → predicate name is `pred_id.split(":")[1]`, terms are uppercased variable names (strip `$` prefix)
- String/number literals → quoted in PyReason syntax
- `cmp`/`not`/`ruleref`/`branch-list` → raise `PyReasonCompileError`

### EDB Materialization (Store → PyReasonSession)

```python
def _materialize_edb_from_store(store, schema_ir) -> PyReasonSession:
    """Read all current facts from Ledger, populate a PyReasonSession."""
    session = PyReasonSession(schema_ir)
    for pred in schema_ir["predicates"]:
        pred_id = pred["pred_id"]
        facts = store.ledger.get_facts_for_pred(pred_id)  # existing Ledger API
        for fact in facts:
            if pred.get("relationship_type"):
                session._write_edge_fact_internal(pred_id, fact.e_ref, fact.rest_terms[0][1], ...)
            else:
                session._write_node_fact_internal(pred_id, fact.e_ref, fact.rest_terms[0][1], ...)
    return session
```

This is the inverse of `accept_pyreason_session()`. Exact implementation depends on Ledger's fact retrieval API shape.
