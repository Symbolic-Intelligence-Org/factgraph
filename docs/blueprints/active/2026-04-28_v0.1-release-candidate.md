## 1. Problem

OS-prep readiness is implemented, but that does not mean the code should be published immediately.

The project now has a clean release boundary:

- v0.1 OSS surface is `kernel` only.
- `pyproject.toml` publishes `kernel*` and excludes `kernel.tests*`.
- README is kernel-first.
- runtime authority is in `kernel.application`; `kernel.sdk` is the Python product surface.
- `kernel.audit` optional ECSS domain behavior is explicit.
- 1097 tests pass and `python -m ruff check src/kernel` is blocking-clean.

The remaining question is not "what is the release shape?" but "does the current code and wheel artifact deserve a v0.1 release candidate?"

This blueprint defines a no-publish verification pass. It must surface blockers, residual risks, and whether a real publish-day workflow can be scheduled.

## 2. Goals

- Verify the built wheel matches the kernel-only contract.
- Verify a clean environment can install the wheel and import/use the public kernel surfaces.
- Smoke-test the README quickstart exactly as written.
- Smoke-test audit optional-domain behavior from an installed wheel context.
- Check PyPI metadata / dependency metadata for accidental private or AGPL-bearing surfaces.
- Produce an RC verdict:
  - `pass`: release-day workflow may be scheduled.
  - `conditional pass`: release-day workflow may be scheduled after listed small fixes.
  - `block`: code or packaging is not ready.
- Record known non-blocking residual risks explicitly.

## 3. Non-goals

- Do not publish to PyPI.
- Do not create a GitHub release or tag.
- Do not reserve the PyPI name.
- Do not clean all mypy errors.
- Do not clean service/tools Ruff baseline unless it blocks wheel or docs verification.
- Do not expand OSS scope to `agent`, `service`, or `domains`.
- Do not archive OS-prep / runtime-authority / audit-delivery blueprints during RC verification.

## 5. Proposed Shape

This RC pass is a verification workflow with a short written verdict. It should be implemented as small, auditable commits only if fixes are discovered.

### 5.1 Hard Gates

The RC cannot pass unless all hard gates pass:

1. **Wheel build and content**
   - Build a wheel locally.
   - Wheel includes `kernel/`.
   - Wheel excludes `kernel/tests/`, `agent/`, `service/`, and `domains/`.
   - Wheel metadata does not expose private extras or PyMuPDF / PyMuPDF4LLM.
2. **Clean install smoke**
   - Install the wheel into a fresh virtual environment.
   - Import `kernel`.
   - Import key public surfaces:
     - `kernel.sdk`
     - `kernel.application`
     - `kernel.audit`
3. **README quickstart smoke**
   - Run the quickstart from README / README.en in the fresh environment.
   - It must not rely on monorepo-only paths.
4. **Audit optional-domain smoke**
   - From the installed wheel, verify `AuditOptionalDomainError` is available.
   - Verify missing `domains.ecss` is reported as optional-domain behavior, not a raw import failure.
5. **License / dependency metadata**
   - Built metadata shows Apache-2.0 project license.
   - Built metadata does not include private monorepo extras.
   - Built metadata does not include AGPL document parser dependencies.
6. **Test and lint baseline**
   - Current 5-segment test baseline remains green before scheduling release.
   - `python -m ruff check src/kernel` remains green.

### 5.2 Verdict Thresholds

- **pass**:all hard gates pass without code or docs changes.
- **conditional pass**:all hard gates pass after no more than two trivial fixes,where each fix is low-risk,local,and expected to take no more than 30 minutes.
- **block**:any hard gate needs substantive design,code,packaging,or documentation work;or the same hard gate fails again after a trivial fix.

Hard gate failure handling:

- Trivial fix path:make a small commit,rerun the failed gate,and record the fix in the audit log.
- Substantive fix path:do not continue toward release;record blocker evidence in §10 and leave verdict as `block`.
- No external issue tracker is assumed;follow-up tasks are recorded in this blueprint/audit unless the user asks for issue creation.

### 5.3 Soft Gates / Risk Register

These do not automatically block RC, but the verdict must record them:

- mypy remains non-blocking.
- service/tools Ruff remains non-blocking.
- `SDKStore` / `sdk.batch` / `sdk.facade` remain large facade files.
- K primitive-contract traps remain deferred:
  - Query id/version asymmetry.
  - where validation timing.
  - Derivation head/target/head_vars shape.
- PyPI name is not reserved until first upload / trusted publishing.
- agent/service/domains are private monorepo companion surfaces, not v0.1 OSS package content.

## 8. Implementation Plan

1. **Pre-flight local state**
   - Confirm branch, clean worktree, current HEAD, and current test/lint status.
2. **Build artifact**
   - Install/use `build` if available.

3. **Inspect wheel**

   - Confirm include/exclude contract.

   - Install wheel.

5. **Optional-domain smoke**

7. **Verdict**
   - Fill §10 Outcome / Deviations with `pass`, `conditional pass`, or `block`.
   - Append audit log decision with evidence and next action.
   - If a hard gate failed and was fixed inline, record the commit and rerun evidence.
