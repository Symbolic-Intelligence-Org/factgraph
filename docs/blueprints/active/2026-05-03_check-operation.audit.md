## Decision Notes

- 2026-05-03: Blueprint starts in `draft` because concrete DTO / error / engine payload / test contract is intentionally not frozen by the reference topic doc.
- 2026-05-03: Application-first boundary is mandatory. Any SDK surface is optional and delegate-only.
- 2026-05-03: Step 0 is a gate, not optional planning; no multi-file implementation before Step 0 decisions are recorded here.
- 2026-05-03: Step 0 must map topic doc §7.1-§7.6 drift traps to explicit prevention/detection decisions before status can move to `scoped`.
- 2026-05-03: RuleRef/evidence caching is out of scope for Check MVP. If future caching is introduced, it must live behind registry/runtime authority, not inside Check request/result objects.
- 2026-05-03 (Step 0.A): **Engine scope = Option IV (representability-gated multi-engine).** Native: real implementation. Souffle: real implementation where witness-bearing support rows exist (`souffle_witness_v1` reuses `SupportArtifact`). ProbLog / PyReason: support decision semantics via evaluate-then-match **only when requested binding is representable from candidate payload or stored provenance/support metadata**; non-representable (engine, binding-shape) combinations return `status="unsupported"`, never `failed`. Runtime failures (evaluator not registered, binary unavailable, adapter exception) propagate through runtime error channel, **not** into Check status enum.
- 2026-05-03 (Step 0.A): **Engine boundary anchor function** = `extract_match_binding(candidate, evidence_or_provenance, requested_binding) -> binding_items | unsupported`. Single architectural seam where engine-specific representability is decided. Per-engine implementations: native uses final bindings directly; souffle uses `SupportArtifact.binding_items`; problog/pyreason use candidate payload first, fall back to provenance only if Step 0.C can define a safe extractor — otherwise `unsupported`.
- 2026-05-03 (Step 0.A): **Source-backed pattern verification** — `DerivationEvaluateRequest` + `CompiledDerivationPlan` are stable frozen protocol dataclasses; `evaluate_derivation_plans(request, *, store, registry=None) -> list[CandidateSet]` is the runtime executor pattern Check must mirror. Check is a **sibling capability** to evaluate (not an extension of `DerivationEvaluateRequest`). Non-native Check decision semantics will reuse `evaluate_derivation_plans` internally as the engine adapter dispatch entry.
- 2026-05-03 (Step 0.B): **Request DTO** — `CheckRequest` carries **single** `CompiledDerivationPlan` (B1; single-shot semantics; multi-plan is evaluate orchestration). **Binding wire** = `BindingItems` typedef from `core/store/_support`, with Check-specific DTO post_init validator: `$`-prefix variable name + duplicate impossible. **Engine** = required `Literal["native", "souffle", "problog", "pyreason"]`, no default (B3). **No engine_options at request level** (B4); `CompiledDerivationPlan.engine_options` continues to be honored when Check delegates to `evaluate_derivation_plans` for non-native modes. **No identity / query_id / run_id** fields in MVP (B5); caller wraps own correlation IDs.
- 2026-05-03 (Step 0.B): **Result DTO nullable matrix** (B6 corrected) — `passed`: matched_count≥1 + matched_binding present + evidence present; `failed`: matched_count=0 + matched_binding=None + evidence=None; **`unsupported`**: matched_count=**None** + matched_binding=None + evidence=None + errors required; **`invalid_request`**: matched_count=**None** + matched_binding=None + evidence=None + errors required. `matched_count=None` signals "didn't / couldn't evaluate", distinct from `0` which means "evaluated, no match". `requested_binding` echoes normalized `BindingItems` when DTO construction succeeds.
- 2026-05-03 (Step 0.B): **Errors / warnings** — reuse `ErrorDTO` / `WarningDTO` from `application.protocol.common` (B7); SCREAMING_SNAKE_CASE codes per `_CODE_RE`.
- 2026-05-03 (Step 0.B): **EvidenceEnvelope shape** (B8 + B9 + B10 corrected) — fields: `engine`, `support_kind`, `support_digest`, `branch_index: int | None` (None for engines with no per-branch concept, B8 fix for ProbLog/PyReason), **`engine_payload: SupportArtifact | ProvenanceEnvelope`** (B8 rename: was `native_payload` in topic doc; reason: "native_payload" misleads as "for native engine only" while field holds payload for all engines), **`branch_atom_projection: None = None`** (B10: literal None type, **no skeleton `BranchAtomProjection` class defined in MVP** — that would prematurely commit cross-capability projection shape; future widening to `BranchAtomProjection | None` when second consumer appears).
- 2026-05-03 (Step 0.B): **Boundary clarification** (B2 corrected split):
  - **Malformed CheckRequest DTO shape** (wrong container type, $-prefix violation, missing required field, malformed BindingItems structure) → **`ProtocolShapeError`** at DTO construction, per existing `application.protocol.common` convention. **Not** converted to `status="invalid_request"`.
  - **Semantically invalid but well-shaped request** (unknown variable in rule body, RuleRef without registry) → **`status="invalid_request"`** with `errors` populated.
- 2026-05-03 (Step 0.B): **Topic doc supersede applied** — `native_payload` field renamed to `engine_payload` in topic doc §1-§5 + §7 with explicit supersede note at top; §6 historical entries retain original `native_payload` naming (per topic doc "§1-§5 wins over §6" rule + audit trail discipline).
- 2026-05-03 (Step 0.C): **Headline freeze (per user framing)** — *"Check uses final-result matching, not partial evaluator injection. Native obtains final bindings via `evaluate_native_where`; non-native obtains candidates via `evaluate_derivation_plans` after a request-level representability precheck. Primary selection is explicitly sorted. EvidenceEnvelope is built only for `passed` primary result. **Unsupported** means the question is not representable for that engine/output shape; **failed** means it was representable and no match exists."*
- 2026-05-03 (Step 0.C): **Native algorithm (C1+C2 unified)** — Native always goes through `evaluate_native_where(view_facts, where, *, registry, witness_facts, remember_support_artifact)` regardless of whether requested binding is complete or partial. Complete binding is the special case where subset-match equals exact match. RuleRef resolution naturally happens through `evaluate_native_where`. Direct `_branch_satisfies` primitive call is **future no-RuleRef fast path**, **not** MVP contract. Empty binding (full enumeration request) is allowed and equivalent to "any result binding exists"; unknown variable in requested binding is **semantic** `invalid_request`.
- 2026-05-03 (Step 0.C): **`extract_match_binding` per-engine spec (C3 corrected)** —
  - native: **bypasses the seam**; uses final bindings directly from `evaluate_native_where` (no per-candidate extraction needed)
  - souffle: uses `SupportArtifact.binding_items` (from `_ParsedWitnessRow`); `requested ⊆ binding_items` → representable
  - problog / pyreason: maps from `plan.heads[0].head_var_names + CandidateSet.payload`; requested **only-head-vars** → representable; body-only vars → `unsupported`; entity-targeted candidate → `unsupported` unless reliable mapping later defined
  - **No provenance fallback as default in MVP**; provenance fallback only when source-backed safe extractor is proven (deferred to engine-extension-surface topic)
- 2026-05-03 (Step 0.C): **Deterministic primary explicit sort (C4 corrected)** —
  - native + souffle: primary key = `(branch_index, binding_items, candidate_key_or_empty)` (lex sort)
  - problog + pyreason: primary key = `(candidate_key, binding_items)`
  - engines where `branch_index=None`: don't participate in branch source-order; sort by `(binding_items, candidate_key)` only
  - Souffle `branch_index` derived from `SupportArtifact` atom keys (e.g., `b{n}.a{m}:` prefix parse); if derivation fails but candidate otherwise representable → `branch_index=None`, fall back to binding/candidate sort
  - **Application explicitly sorts; does not depend on adapter/materialization order**
- 2026-05-03 (Step 0.C): **RuleRef failure error codes (C5 with softening)** —
  - missing registry but rule has ruleref → `code="REGISTRY_REQUIRED"`
  - rule_id not found in registry → `code="RULE_REF_UNRESOLVABLE"` (with `details.rule_id` / `details.version` if available)
  - cycle in ruleref graph → `code="RULE_REF_CYCLE"`
  - version mismatch (only when source can distinguish stably) → `code="RULE_REF_VERSION_MISMATCH"`; otherwise fall back to `RULE_REF_UNRESOLVABLE` with `details.reason`
  - **NO** parsing of brittle adapter/registry exception text required
- 2026-05-03 (Step 0.C): **Non-native algorithm (C6 critically corrected)** — Two-stage:
  1. **Request-level representability precheck** from plan + requested binding: if requested vars not representable for that (engine, plan/output shape) → `status="unsupported"` **before evaluating**. Avoids vacuous "empty candidates → unsupported" bug.
  2. If precheck passes → `evaluate_derivation_plans(plan_only_request, *, store, registry)`:
     - zero candidates → `status="failed"`, matched_count=0 (representable, evaluated, no result)
     - nonzero candidates → `extract_match_binding(...)` per candidate; no match → `failed`; match(es) → primary selection per C4
  3. Malformed candidate despite passing precheck → engine boundary error; propagate via runtime error channel per C7 (not collapsed into status)
  - **Critical distinction**: "no result" = `failed` (representable, evaluated, nothing matched); "cannot ask this question" = `unsupported` (not representable, did not evaluate)
- 2026-05-03 (Step 0.C): **Runtime failure mapping (C7)** — Adapter exceptions during evaluate / evaluator-not-registered / engine-binary-unavailable propagate through runtime error channel. **Never** wrapped into `status="unsupported"` or `"invalid_request"`. DTO post_init failure → `ProtocolShapeError` (per Step 0.B B2).
- 2026-05-03 (Step 0.C): **Drift prevention §7.1-§7.6 mapping + anti-regression test wording (C8 corrected)** —
  - §7.1 partial → primitive: C2 algorithm explicitly forbids; runtime call site adds `assert binding is full` precondition; mock test asserts `_branch_satisfies` never called with non-full binding
  - §7.2 opaque / flatten payload: per-engine round-trip test asserts **both** typed payload preservation (Python type stays `SupportArtifact` / `ProvenanceEnvelope`) **and** serialization round-trip (engine-specific fields preserved across serialize/deserialize)
  - §7.3 None ≠ degraded: DTO type `branch_atom_projection: None = None`; runtime always assigns None; test: passed + branch_atom_projection=None + engine_payload non-None → not interpreted as degraded
  - §7.4 registry / store / resolutions in DTO: acceptance wording is "DTO construction rejects unexpected fields"; **does not** require specific `ProtocolShapeError` (Python dataclass natively raises `TypeError` on unknown kwargs unless `from_dict` validator is implemented); test asserts construction fails
  - §7.5 §6 vs §1-§5 priority: doc-level discipline only (topic doc supersede note already in place); **not** an impl test
  - §7.6 anti-patterns (5 classes): each has banned-call / DTO field rejection / status enum non-extension / etc. test case
- 2026-05-04 (Step 0.D): **Scoped lift complete** — Blueprint §5 Proposed Shape now states the frozen request/result/evidence envelope contract from Step 0.B, including single-plan request, `engine_payload`, nullable `matched_count`, and `branch_atom_projection: None = None`. Blueprint §8 Implementation Plan now starts at protocol DTO implementation and carries the Step 0.C algorithm decisions into native, RuleRef/determinism, and non-native boundary steps.
- 2026-05-04 (Step 0.D): **Status transition** — `draft → scoped`. Step 0 gate is complete. Any future change to request/result DTO semantics, engine scope, primary sort key, RuleRef error mapping, or representability semantics requires blueprint + audit update before code changes.
- 2026-05-04 (Step 1 immediate): **Multi-head policy** — `CheckRequest` requires `len(plan.heads) == 1` and rejects multi-head plans with `ProtocolShapeError` during DTO construction. Rationale: Check is a single-shot, single-question verifier; multi-head plans are evaluate orchestration input. This is a CheckRequest shape invariant, not a runtime `invalid_request` result.
