## 1. Problem

Namespace split(2026-04-27 commit `0f2ee52`)已扫清 kernel 的架构债,但 OS 公开发布还有一批**决策性 + 工程性**前置工作未做。这些工作**单看每一项都不复杂**,但**互相牵制**(包名决定影响 PyPI publishing;LICENSE / dependency policy 决定 kernel wheel 是否可干净发布;OS scope 决定 README 与 package inclusion),适合在一个 blueprint 里一次性收口。

本 blueprint 的目标是:从"namespace 干净的 monorepo"走到"可以面向公众的 v0.1 OSS release"。

### 5.1.1 #2 PyPI Policy Inputs

`documents` extra 原本是 #2 的硬输入,因为当时 scoped 假设是 single distribution / all namespaces。该前提已被 kernel-only OSS surface 修正取代。

当前 `documents = ["pymupdf", "pymupdf4llm", "python-docx"]`,其中 PyMuPDF / PyMuPDF4LLM metadata 为 **dual AGPL-3.0 or Artifex Commercial License**。这些依赖由 private `agent.documents` PDF parser 使用,不属于 kernel-only v0.1 OSS package。#2 scoping 的新约束是:

- PyPI wheel/package metadata 不得 include `documents` extra 或 AGPL document parsing dependencies.
- `agent` / `documents` install path 可留在 monorepo private docs,但不得出现在 v0.1 OSS install instructions / PyPI long description.
- 若未来把 agent/document parsing 开源,以下 disposition choices 重新启用:

| 选项 | 处置 | 代价 |
|---|---|---|
| a | 保留 `documents` extra,在 README / CONTRIBUTING / PyPI long description 显式标 license boundary | 最低成本;PyPI metadata / dependency graph 仍呈 mixed-license signal |
| b | `documents` extra 不随 PyPI distribution 发布,仅保留 GitHub install 路径 | PyPI license surface 干净;牺牲安装便利和 demo reproducibility |
| c | 替换为 permissive parser(如 `pypdf` MIT / `pdfplumber` MIT) | 需要生产代码替换与回归;可能损失 PyMuPDF 能力 |
| d | v0.1 完全去掉 `documents` extra | license surface 最干净;失去 PDF extraction 演示路径 |

**#2 scoped decision**:

- PyPI policy:cadence-based;only stable release tags are published to PyPI.
- Publishable package inclusion:`kernel*` only,excluding `kernel.tests*`.
- Publishable extras:only `[dev]`;private monorepo dependencies for service/documents/extraction/observability live in `requirements/dev.txt`.
- `documents` extra disposition is private/future-agent concern,not a kernel PyPI blocker.
