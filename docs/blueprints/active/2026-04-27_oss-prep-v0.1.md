## 1. Problem

Namespace split(2026-04-27 commit `0f2ee52`)已扫清 kernel 的架构债,但 OS 公开发布还有一批**决策性 + 工程性**前置工作未做。这些工作**单看每一项都不复杂**,但**互相牵制**(包名决定影响 PyPI publishing;LICENSE 决定影响 PyReason 是否能进 OS extras;OS scope 决定影响 OpenAPI yaml 归属),适合在一个 blueprint 里一次性收口。

本 blueprint 的目标是:从"namespace 干净的 monorepo"走到"可以面向公众的 v0.1 OSS release"。

### 5.1.1 #2 PyPI Policy Inputs

`documents` extra 是 #2 的硬输入,不是 README wording 问题。当前 `documents = ["pymupdf", "pymupdf4llm", "python-docx"]`,其中 PyMuPDF / PyMuPDF4LLM metadata 为 **dual AGPL-3.0 or Artifex Commercial License**。在 Apache-2.0 主包上 PyPI 时,必须显式选择 disposition:

| 选项 | 处置 | 代价 |
|---|---|---|
| a | 保留 `documents` extra,在 README / CONTRIBUTING / PyPI long description 显式标 license boundary | 最低成本;PyPI metadata / dependency graph 仍呈 mixed-license signal |
| b | `documents` extra 不随 PyPI distribution 发布,仅保留 GitHub install 路径 | PyPI license surface 干净;牺牲安装便利和 demo reproducibility |
| c | 替换为 permissive parser(如 `pypdf` MIT / `pdfplumber` MIT) | 需要生产代码替换与回归;可能损失 PyMuPDF 能力 |
| d | v0.1 完全去掉 `documents` extra | license surface 最干净;失去 PDF extraction 演示路径 |

#2 scoping 时必须同时决定 publication policy 与 `documents` extra disposition;不能只决定"是否上 PyPI"。
