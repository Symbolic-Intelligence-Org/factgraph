## 1. Problem

The post-Track-3 lifecycle/assets sequence is complete on `origin/master`
through `16cc8647`. The public SDK now has a coherent lifecycle surface:

- public `Inference` vocabulary;
- inference service/registry vocabulary;
- graph-bound authoring asset persistence;
- FactGraph workspace `create(path=...)` / `save(...)` / `load(...)`.

The next release action should cut a new release candidate that captures this
surface. `v0.1.0-rc.2` already exists on origin and points at the older
`release/0.1.x` commit `c4bc79b4`, so the next candidate is `v0.1.0-rc.3`.

## 2. Goals

- Verify the current `origin/master` release projection for `v0.1.0-rc.3`.
- Run `scripts/release.sh v0.1.0-rc.3 --source-ref <current-head> --dry-run --yes`.
- Record any release blockers before live publishing.
- Preserve all sacred refs unless the user explicitly authorizes live release.

## 3. Non-goals

- No live release branch update.
- No live tag creation on origin.
- No GitHub Release creation.
- No PyPI publish.
- No destructive deletion of existing tags, milestone refs, or release refs.
- No cleanup of unrelated dirty notebooks/docs/scratch files.

## 4. Current Context

- `origin/master = 16cc8647` after the lifecycle/assets handoff commit.
- `origin/release/0.1.x = c4bc79b4`.
- `v0.1.0-rc.1` exists and points to release commit `1aa157cc`.
- `v0.1.0-rc.2` exists and points to release commit `c4bc79b4`.
- `v0.1.0-rc.3` does not exist on origin.
- `pyproject.toml` currently declares `version = "0.1.0rc3"`.
- The working tree has unrelated dirty files. The release dry-run should run
  from a clean worktree or clean source ref rather than mutating those files.

## 5. Proposed Shape

Use the existing release script without changing the release workflow:

```bash
./scripts/release.sh v0.1.0-rc.3 --source-ref HEAD --dry-run --yes
```

Because the current worktree is dirty with unrelated files, run the dry-run
from a clean auxiliary worktree or otherwise ensure the script sees a clean
worktree. Do not stash, revert, or modify unrelated user files.

If dry-run passes, ask for explicit live-publish authorization before running
the non-dry-run release command.

## 6. Boundaries And Invariants

- Existing `v0.1.0-rc.1` and `v0.1.0-rc.2` tags are immutable unless the user
  explicitly asks for destructive reissue.
- `release/0.1.x` is sacred until live release is authorized.
- Milestone refs are branch refs under `refs/heads/milestone/...`, not tags.
- Use `git push origin HEAD:master` form when publishing source commits from a
  detached/topic HEAD.
- The release projection must not include `memory/`, `docs/blueprints/`,
  `docs/references/`, `src/service/`, `src/agent/`, examples, notebooks, or
  other denylisted development material.
- Release candidate verification must observe the six known release traps from
  `feedback_release_workflow_traps.md`.
