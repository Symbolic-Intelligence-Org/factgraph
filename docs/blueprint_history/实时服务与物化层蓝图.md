# 实时服务与物化层蓝图

## 1. 目标

本蓝图用于明确当前系统在性能与实时处理上的核心痛点，尤其是：

- 哪些问题已经在实现中确定存在
- 哪些问题目前还是扩展性风险，而不是已证实的产品 blocker
- 如果要支持实时数据处理与前端高频交互，架构上必须补哪些层

本文件是问题边界与目标架构文档，不是具体表结构或代码实现文档。

相关文档：

- `docs/application_projection_blueprint.md`
- `docs/application_protocol_spec.md`
- `docs/blueprint_history/视图层.md`

## 2. 非目标

本蓝图不解决以下问题：

- 不修改 `Entity / Identity / Field` 核心建模方式
- 不替换 ledger 作为 source of truth
- 不把所有性能问题一概归结为 Datalog / Soufflé 引擎问题
- 不直接定义最终数据库表结构、缓存键格式或部署拓扑

## 3. 当前已确认的痛点

### 3.1 重复全量投影

当前系统的主要读路径，往往先通过 `project_view_facts(...)` 从 ledger 重建整份 current view，然后再做后续 hydration / filtering / query 渲染。

这会出现在：

- `application/entity_view.py`
- `sdk/query_runtime.py`
- `service/runtime_v1.py` 的部分查询路径

这意味着：

- 读取单个实体，也可能先支付一次“整库当前视图投影”的成本
- 多个读路径之间会重复计算相同的 current view
- 数据规模和并发上来后，读延迟会被这一层放大

这是当前最明确的性能风险。

### 3.2 assertion / history 物化存在 N+1 倾向

当前 assertion/history 读取路径存在明显的逐 claim 读取 args/meta 的模式：

- `find_claims(...)`
- `find_claim_args(...)`
- `find_meta(...)`

这会影响：

- 实体详情页
- 字段断言历史
- provenance / explain / conflicts 相关视图

当单个实体的历史深度变大时，这条路径会变重。

### 3.3 service 仍以 runtime primitive 为主

当前 `service` 暴露的主接口仍然是：

- `pred_id`
- `e_ref`
- `rest_terms`

这更接近 runtime primitive，而不是前端真正需要的 entity-centric serving API。

问题不在于它“不能工作”，而在于：

- 前端实体交互需要更多拼装
- 容易重复触发底层 projection
- 不利于后续引入图投影、绑定、关系归并等中层能力

### 3.4 迁移期双规划成本

当前 SDK batch 在兼容期会：

- 先做 legacy field op 编译
- 再尝试转成 application write plan
- 不满足条件时整批回退

这确实有额外成本，但它属于迁移期税，不是当前产品级第一瓶颈。

## 4. 痛点边界

### 4.1 还不能下的结论

当前还不能直接下结论说：

- “性能已经致命”
- “现在一定撑不住生产”
- “必须立刻换引擎”

原因：

- 目前没有系统化 benchmark
- 没有真实规模下的 P50 / P95 / P99 数据
- 也没有明确的目标吞吐、并发和数据量边界

### 4.2 已经可以下的结论

当前可以明确下结论的是：

- 重复全量投影是当前最明显的扩展性风险
- 它不是局部小优化问题，而是 read path 的结构性成本
- 如果产品目标包含实时处理和高频前端交互，它不能作为长期方案

### 4.3 产品风险判断

可以用下面的口径统一描述：

| 问题 | 当前是否已证实为 blocker | 是否是主要扩展性风险 | 与实时目标是否冲突 |
|---|---|---|---|
| 重复全量投影 | 否 | 是 | 是 |
| assertion/history N+1 | 否 | 是 | 是 |
| service 接口过低层 | 否 | 是 | 是 |
| SDK batch 双规划 | 否 | 否 | 否 |

## 5. 对实时目标的影响

如果目标里包含以下任一项：

- 高频前端读取
- 写后立即可见
- 实时列表 / 图谱 / 面板刷新
- 接近流式的数据处理

那么当前“ledger-only + request-time current-view projection”的模式会直接带来问题。

原因是当前模式更接近：

- 写入只写 ledger
- 读取时再从 ledger 重建 current view

而实时系统更需要：

- 写入后顺手维护 serving state
- 读取时直接命中 serving layer

因此，问题不在于 `Entity` 模型本身不适合实时，而在于：

**ledger-only + read-time 全量投影** 不适合实时路径。

## 6. 架构判断

### 6.1 当前需要补的一层

如果要支持实时与高频交互，系统需要在 ledger 之上增加一层：

- current view materialization
- 或更一般地说：serving / materialized layer

推荐分层：

- ledger: source of truth
- current view materialization: 当前对外可见状态
- application/service: 基于 current view 提供 entity / query / graph API

### 6.2 ledger 与 materialization 的职责分工

ledger 继续负责：

- append-only truth
- 断言历史
- provenance
- explain / conflicts / 审计可回放

materialization 层负责：

- 当前 active/chosen 结果
- 面向前端的 current entity state
- 高频读取所需的 serving index

这两层不是互斥关系，而是标准的 truth layer / serving layer 分离。

## 7. Soufflé / Datalog 的边界

### 7.1 可以做什么

Soufflé 可以表达 current view 的核心语义：

- `active`
- `single` 字段的 chosen/current
- `multi` 字段的 active 集合

仓库里已经有这类 view generator 雏形。

### 7.2 不建议直接怎么做

不建议把 Soufflé 直接接成：

- 每次 `sdk.get/find`
- 每次 service read request
- 每次前端实体详情页

的实时 projection 执行器。

原因是当前 Soufflé 接入方式更接近：

- export package
- 运行外部引擎
- 读取输出

这适合批量计算，不适合前端低延迟读路径。

### 7.3 当前建议

Soufflé 更适合做：

- 批量重算 current view
- 离线/周期性 materialization
- 校验 Python/SQL materialization 与 policy 语义一致

而不是当前第一版实时 serving path。

## 8. 建议的解决顺序

### Phase 1: 先降低重复投影成本

短期优先级最高的是：

- 为 `project_view_facts(...)` 增加 revision-based cache
- 避免相同 ledger 状态下重复重建 current view

这一步改动小，收益最大。

### Phase 2: 建 current view materialization

中期应引入 materialized current view，例如：

- `current_facts`
- `entity current snapshot`
- `entity ref edges / relationship serving index`

重点不是具体表名，而是：

- read path 不再从 ledger 全量投影起步
- serving data 可以按 revision 增量维护

### Phase 3: service 接入新的 serving path

前端最终应通过新的 service API 读取：

- entity read
- entity write
- query view
- graph projection

而不是继续围绕 `pred_id + e_ref + rest_terms` 自行拼装。

### Phase 4: 再决定是否引入 Soufflé materialization

当 current view contract 稳定后，再评估：

- 是否需要 Soufflé 做批量重算
- 是否需要 Soufflé 做一致性校验
- 是否需要 Soufflé 做离线 serving build

不建议在 contract 未稳定时先把引擎塞进实时路径。

## 9. 近期不该做的事

为避免方向偏掉，当前阶段不建议：

- 直接把前端建立在旧 `service/runtime_v1` primitive 接口之上
- 把“性能问题”简单等价为“必须换 Datalog 引擎”
- 在没有 current view contract 的情况下先实现复杂实时同步框架
- 在未 benchmark 之前拍脑袋定义 QPS 结论

## 10. 当前推荐结论

当前应统一采用以下判断口径：

1. 主要痛点不是 `Entity` 模型，而是 read-time 重建 current view 的执行策略。
2. 当前最重要的性能债是重复全量投影，以及 assertion/history 物化的 N+1。
3. 这两个问题现在未必已成为产品 blocker，但如果要做实时处理与高频前端交互，它们会迅速变成核心风险。
4. 因此系统需要引入 current view materialization / serving layer。
5. Soufflé 可以参与批量 materialization，但不应作为当前前端实时读路径的第一版方案。
