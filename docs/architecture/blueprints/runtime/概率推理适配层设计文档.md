# ProbLog 概率推理适配层设计文档（v0.4）

> 状态：讨论中 · 尚未实现  
> 相对 v0.3 的主要变化：修正三个阻塞点——confidence 更新策略、单分支 Body 语法、重复 accept 策略

> **向后兼容性说明**：本次所有代码改动均无需考虑向后兼容。直接实现最干净的版本，删除 deprecated alias、旧接口、兼容 shim，不保留过渡路径。

---

## 1. 背景与目标

本文档涵盖两个相互驱动的设计课题：

**课题 A：ProbLog 概率推理适配层**——在现有 IR 基础上引入 ProbLog 推理后端支持。概率来源覆盖两个正交层次：

- **EDB 层（断言级）**：`meta.confidence` 字段，对应 ProbLog 的 `P :: fact.`
- **规则层（推导级）**：`where` 的 OR 分支（body）通过 `Body` 包装对象携带 per-body 置信度，编译后剥离为 `body_confidences` sidecar

**课题 B：可配置视图层**——由 ProbLog 的多源置信度并存需求驱动出来的架构升级。现有 view 层是固定策略投影，无法在运行时配置 `active`、`valid`、`confidence` 等维度。ProbLog 引入后，同一事实会有来自不同推理批次的多条置信度并存，view 层必须能够按需聚合，否则 confidence 信息无法被上层正确消费。

两个课题本次一起落地，课题 B 是课题 A 的基础依赖。

### 2.1 `confidence` float 存储

**现状**：`write_protocol._infer_meta_kind()` 只接受 `bool/str/int`，不接受 `float`；`int` 的 kind 名为 `"num"`。

**决策**：扩展支持 `float`，新增 `kind="float"`；同时将现有 `kind="num"` 重命名为 `kind="int"`。

**完整影响面**：

| 文件 | 改动内容 |
|---|---|
| `core/evidence/write_protocol.py` | `_infer_meta_kind` 中 `int → "int"`（重命名），新增 `float → "float"`；`_KEY_KIND_MAP` 中 `confidence → "float"`；`confidence` key 值域检查 `(0,1]` |
| `core/mapping/canon.py` | `_optional_confidence` 改为读取 `kind="float"` |
| `core/store/ledger.py` | `_enc` / `_dec` 支持 float 序列化（SQLite REAL，无需 schema migration）；`META_KINDS` 常量从 `{"str","num","bool","time","json"}` 更新为 `{"str","int","float","bool","time","json"}` |
| `adapters/souffle/package.py:272` | `_build_fact_rows` 新增 `kind="float"` 查询，输出到独立 `meta_float.facts`；`_atom_to_str` 调用 `_float_to_meta_str` 序列化；`kind="num"` 改为 `kind="int"`，输出到 `meta_int.facts` |
| `audit/assertions.py:140` | `_parse_meta_num` 重命名为 `_parse_meta_int`；新增 `_parse_meta_float`（`float(raw)`）；`_manifest_facts` 新增 `meta_float` required key，`meta_num` 改为 `meta_int` |

**export 协议版本升级**：`kind` 重命名和文件分离是 breaking change，需要显式版本切换。manifest 新增 `"export_version": "v2"` 字段，reader/tooling 通过该字段区分 v1（`meta_num`）和 v2（`meta_int` + `meta_float`）。v1 reader 遇到 v2 包应报错而非静默读错。

**kind 体系重命名 + 文件分离硬约束**：

- `kind="num"` → `kind="int"`，`meta_num.facts` → `meta_int.facts`
- 新增 `kind="float"`，对应新文件 `meta_float.facts`
- `_manifest_facts` required key 同步：`meta_num` → `meta_int`，新增 `meta_float`
- `runner.py` package layout 校验同步更新
- Souffle 的 `max_confidence` tie-break 规则改为同时读 `meta_int` 和 `meta_float`

**`float` 序列化规范函数**（定义在 `adapters/souffle/package.py` 或 `core/evidence/write_protocol.py`）：

```python
def _float_to_meta_str(value: float) -> str:
    return repr(value)

def _parse_meta_float(raw: str) -> float:
    return float(raw)
```

使用 `repr()`：Python 3.1+ 保证产生最短可逆字符串，约束是 `float(repr(x)) == x`，不限制格式。科学计数法（如 `1e-10`）是合法输出，`float()` 可正确还原。不使用 `:.17g` + 禁科学计数法断言——后者在极小概率值下会误拒合法输入。

### 2.4 `CandidateSet.confidence` 全链路透传

**透传缺口**：`CandidateSet.confidence` 是新增字段，现有序列化/反序列化链路不感知，会静默丢失：

| 位置 | 问题 | 修复 |
|---|---|---|
| `service/runtime_v1.py:686` `_candidate_to_dict` | 序列化时未输出 `confidence` | 增加 `"confidence": candidate.confidence` |
| `service/runtime_v1.py:705` `_candidate_from_dict` | 反序列化时未读取 `confidence` | 增加 `confidence=value.get("confidence")` |
| `sdk/store.py:724` `_with_candidate_run_id` | 多头合并重建时未复制 `confidence` | 增加 `confidence=candidate.confidence` |

**写回策略（重新定义）**：

`meta` 是数据语义的一部分（来源、上下文、运行批次），不是附属信息。同一事实按不同 meta 并存是预期能力，不是脏数据。`Derivation → accept` 的默认语义是**追加新证据**，不是修改旧证据。

因此 ProbLog 每次推理结果直接作为新断言写入，携带自己完整的 meta：

```python
# ProbLog accept 路径——无需查找现有 asrt_id，直接 set_field
write_meta = {
    "source": "derivation.accept",
    "derived_rule_id": derived_rule_id,
    "run_id": candidate_set.run_id,
    "confidence": candidate_set.confidence,  # 本次推理的边际概率
    ...
}
set_field(ledger, pred_id, e_ref, rest_terms, write_meta)
```

`confidence` 在此表示"该来源/该运行批次下的置信度"，不是全局唯一真值。多次推理的结果自然并存，由 view 层的置信度融合策略负责聚合（见第 2.7 节）。

`confidence` 不参与 `candidate_key` digest（概率不是候选身份的一部分）。

### 2.5 单分支 `Body` 语法修正（阻塞点修正）

**v0.3 的问题**：文档允许 `where=Body([...], confidence=0.8)`（单个 `Body` 对象），但 `Rule/Derivation.where` 在 SDK 构造层必须是 list（[rule.py:49,122](src/factpy_kernel/sdk/dsl/rule.py)）。

**决策**：单分支 `Body` 必须包裹在 list 中，与多分支形式统一：

```python
# ✅ 正确：单分支也用 list 包裹
Rule(
    where=[Body([LivesIn(li), li.person == p], confidence=0.8)],
)

# ❌ 不支持：裸 Body 作为 where 值
Rule(
    where=Body([LivesIn(li), li.person == p], confidence=0.8),
)
```

SDK 构造层只需在现有 list 校验基础上，增加对 `Body` 元素的识别，不需要修改 `where` 类型签名。

### 2.6 `MetaRow.kind` 对用户不可见（写入协议改进）

**现状**：用户（包括适配器代码）在构造 `MetaRow` 或调用 `write_protocol` 时需要显式指定 `kind`，但 `kind` 对已知 key 来说是完全派生的——`confidence` 永远是 `float`，`ingested_at` 永远是 `time`，`source` 永远是 `str`。显式传 `kind` 既冗余又容易出错（如误传 `kind="int"` 给 `confidence`）。

**决策**：在 `write_protocol` 层固化 key → kind 的映射，`kind` 对调用方不可见：

```python
# write_protocol.py 新增
_KEY_KIND_MAP: dict[str, str] = {
    "confidence":   "float",
    "ingested_at":  "time",
    "source":       "str",
    "source_loc":   "str",
    "trace_id":     "str",
    "approved_by":  "str",
    "note":         "str",
    "derived_rule_id":      "str",
    "derived_rule_version": "str",
    "run_id":               "str",
    # ... 其余 CONVENTION_META_KEYS / SENSITIVE_SEMANTIC_META_KEYS
}

def _infer_meta_kind(key: str, value: Any) -> str:
    if key in _KEY_KIND_MAP:
        _validate_kind_value(key, _KEY_KIND_MAP[key], value)  # 类型校验
        return _KEY_KIND_MAP[key]
    # 未知 key：按 value 类型推断（bool/str/int/float）
    ...
```

**`MetaRow` 结构本身不变**：`kind` 字段保留，因为序列化路由（`find_meta(kind=...)` 分桶、TSV 导出分文件）仍依赖它。变化在于 `kind` 变成**派生值**，由 `_infer_meta_kind` 统一决定，调用方无需也无法覆盖。

**约束**：
- `CONVENTION_META_KEYS` 和 `SENSITIVE_SEMANTIC_META_KEYS` 中的所有 key 必须在 `_KEY_KIND_MAP` 中有映射，编译期（模块加载时）做 `assert` 检查
- 未知 key 按 value 类型推断，行为与现在一致（向后兼容）
- 若传入 value 类型与 `_KEY_KIND_MAP` 期望不符，`WriteProtocolError` 报错，提示 key 期望的类型

**影响面**：仅 `write_protocol._infer_meta_kind` 和相关校验逻辑，不影响 Ledger、序列化、查询路径。

### 2.8 duplicate 判定细化

**现状矛盾**：文档定义"追加新证据"为默认语义，但现有 `accept` 的 duplicate 短路只看 `(pred_id, e_ref, rest_terms)`，完全忽略 meta——这会阻止 ProbLog 多批次推理结果并存。

**新判定逻辑**：先看 claim 是否相同，再看**业务语义 meta** 是否相同。

```
duplicate 条件：
  (pred_id, e_ref, rest_terms) 相同
  AND
  排除 primary key 后的 meta 完全相同
```

**Primary key meta**（排除在比较之外）：

```python
# 记录身份字段：时间戳 + run/candidate 标识
# 这些字段每次写入必然不同，排除在 duplicate 比较之外
_META_PRIMARY_KEYS = {
    "run_id",
    "ingested_at",
    "accepted_at",
    "trace_id",
    "candidate_id",
    "candidate_key",
    "cand_key_digest",
    "key_tuple_digest",
    "materialize_id",
}
```

**不在排除集里的字段**（参与 duplicate 比较）：`source`、`support_digest`、`support_kind`、`derived_rule_id`、`derived_rule_version`、`schema_digest`、`policy_digest`、`approved_by`、`note`、`confidence`。

这些是语义溯源字段，代表"这条断言来自哪个来源、哪条规则、哪个版本的 schema"——两条断言如果这些字段相同，才是真正的重复证据。

**系统管理键处理**：`ingest_key`、`revoked_asrt_id` 等系统管理键不属于业务语义，不参与 duplicate 比较（即不纳入 meta 比较输入）。

**效果**：

| 场景 | 结果 |
|---|---|
| EDB 同一来源重复写入（`source`、`confidence` 相同） | duplicate，幂等跳过 |
| ProbLog 不同批次（`confidence` 不同） | 非 duplicate，并存 |
| 确定性推理同一规则重复 accept（`derived_rule_id`、`support_digest` 相同） | duplicate，幂等跳过 |
| 同一事实不同来源写入（`source` 不同） | 非 duplicate，并存 |

**影响面**：

| 文件 | 改动内容 |
|---|---|
| `core/derivation/accept.py` | `_find_existing_claim_assertions_v2` 增加 meta 比较逻辑，排除 `_META_PRIMARY_KEYS` |
| `core/evidence/write_protocol.py` | 新增 `_META_PRIMARY_KEYS` 常量 |

## 3. EDB 层：`meta.confidence` 作为概率源

`meta.confidence` 在 ProbLog 路径中定义为：

> 该断言对应概率原子为真的先验概率，存储为 `float` ∈ `(0, 1]`，`None` 表示确定性事实（概率 1.0）。

**多断言的概率合并（Noisy-OR）**：同一 `(pred_id, E, value)` 可能有多条 active 断言，以 `asrt_id` 为概率原子标识符，让 ProbLog Noisy-OR 语义自然处理。

```prolog
0.9::edb_fact("A2", "person:speaks", "idref_v1:Person:...", "german").
0.7::edb_fact("A3", "person:speaks", "idref_v1:Person:...", "german").
% Noisy-OR: 1-(1-0.9)*(1-0.7) = 0.97

person_speaks(E, Lang) :- edb_fact(_, "person:speaks", E, Lang).
```

**注意**：Noisy-OR 假设各证据来源独立，概率正确性由用户保证——同一语义断言不应重复写入。系统层面已有幂等键机制辅助去重。

## 4. 规则层：`Body` 包装对象

### 4.1 用户 DSL

```python
from factpy_kernel.sdk import Body, Rule, vars

# 不需要概率 → 裸 list，与现有写法完全相同
Rule(
    where=[
        [LivesIn(li), li.person == p, li.language == c],
        [Pred("person:nationality", p, c)],
    ],
)

# 需要概率 → Body 包装（单分支或多分支，均用 list 包裹）
Rule(
    where=[Body([LivesIn(li), li.person == p], confidence=0.8)],
)

Rule(
    where=[
        Body([LivesIn(li), li.person == p, li.language == c], confidence=0.9),
        Body([Pred("person:nationality", p, c)], confidence=0.6),
    ],
)
```

### 4.2 `Body` 数据结构

```python
@dataclass(frozen=True)
class Body:
    atoms: list                       # where 原子列表（AND 语义）
    confidence: float | None = None   # 与 meta.confidence 对齐；None = 确定性
```

### 4.3 编译器 normalize 规则

| 输入形式 | normalize 后的 where | body_confidences |
|---|---|---|
| 裸 list（单体） | 不变 | `None` |
| 裸 list（多体 OR） | 不变 | `None` |
| `[Body(...)]`（单分支） | 解包 `Body.atoms` | `[confidence]`（长度 1） |
| `[Body(...), Body(...)]`（多分支 OR） | 解包各 `Body.atoms` | `[c0, c1, ...]` |

**禁止混用**（编译期报错）：

```python
# ❌ 裸 list 与 Body 在同一 where 中混用
where=[
    [atom1, atom2],
    Body([atom3], confidence=0.9),
]
```

**`Body.confidence` 值域**：`(0, 1]`，`0` 编译期报错。

**不支持顶层 `confidence`**：只能在 `Body` 中定义。

### 4.4 IR payload 层（JSON）

```json
{
  "where": [
    [["pred", "livesin:person", ["$p", "$c"]]],
    [["pred", "person:nationality", ["$p", "$c"]]]
  ],
  "body_confidences": [0.9, 0.6]
}
```

单体 / 无概率时 `body_confidences` 字段缺省。

## 7. 课题 B：可配置视图管理系统

> 本节是独立设计课题，与课题 A（ProbLog 适配器）共享同一文档，便于查看和修改。后续可单独拆分。

### 7.1 背景与动机

**由 ProbLog 驱动的需求**：ProbLog 引入后，同一事实会有来自不同推理批次的多条置信度并存。上层需要能够按策略聚合这些置信度，而不是拿到一堆原始断言自己处理。

**更根本的问题**：现有读路径（`sdk.run()`、`sdk.find()`）的投影和置信度聚合策略硬编码，无法按视图配置。用户在前端无法配置"用哪个视角看数据"。

**目标**：用户可以定义、管理具名视图，读操作基于视图执行（`confidence_strategy` 影响结果呈现）；推理路径不受 view 影响，始终基于完整 active 断言集：

```python
# 定义视图
sdk.views.create("conservative", ViewSpec(
    active=True,
    confidence_strategy="max",
))
sdk.views.create("hr_only", ViewSpec(
    active=True,
    confidence_strategy="prefer_source",
    prefer_source="HR系统",
))

# 读操作基于视图（confidence_strategy 影响结果呈现）
sdk.run(vip_rule, view="conservative", row_format="dict")
sdk.find(User, view="hr_only")

# 推理不接受 view 参数，始终基于完整 active 断言集
sdk.evaluate(drv, mode="problog")
```

### 7.2 `ViewSpec` 定义

```python
@dataclass(frozen=True)
```

### 7.4 置信度融合策略

融合策略只影响 `confidence` 的**呈现值**，不影响 `chosen`（哪条断言代表这个事实）。两者正交：

- `chosen`：解决"哪条断言代表这个事实"（现有 tie-break 逻辑不变）
- 置信度融合：解决"这个事实的综合置信度是多少"

当前唯一需要融合的字段是 `confidence`，其他 meta 字段不参与融合。

| 策略 | 语义 |
|---|---|
| `max` | 取最高置信度（默认） |
| `mean` | 算术平均 |
| `median` | 中位数 |
| `prefer_source` | 优先取指定来源的置信度，无则降级为 `max` |

### 7.5 view 的作用边界

**决策：view 不进入推理路径。**

`sdk.evaluate()` 不接受 `view` 参数，推理引擎（native/souffle/problog）始终基于完整 active 断言集执行，`confidence_strategy` 对推理过程无任何影响。原因：
- native/souffle 是确定性推理，`evaluate_where` 只接受 `dict[pred_id, list[tuple]]`，无置信度 IR，传入无意义
- problog 需要所有并存断言各自的 `confidence` 供 Noisy-OR 处理，折叠后反而损失信息

**`view` 只作用于读取/展示路径**：

| 操作 | 接受 `view` | 说明 |
|---|---|---|
| `sdk.run(rule, view=...)` | ✅ | 结果后处理时应用 `confidence_strategy` |
| `sdk.find(..., view=...)` | ✅ | 投影时应用 `confidence_strategy` |
| `sdk.evaluate(..., view=...)` | ❌ | 不接受，传入报错 |
| `sdk.accept(...)` | ❌ | 不涉及 |

`confidence_strategy` 的消费方：audit、前端展示层、`sdk.find()`、`sdk.run()` 结果后处理。

**`sdk.run(..., view=...)` 输出契约（本次定论）**：

- 默认返回类型保持不变：`row_format="tuple"` 返回 `list[tuple]`，`row_format="dict"` 返回 `list[dict]`。
- 不在行内注入 `confidence` 字段，避免与用户 `select_vars` 命名冲突。
- 新增可选参数 `return_display_meta: bool = False`：
  - `False`（默认）：仅返回 `rows`（与当前行为一致）。
  - `True`：返回 `(rows, display_meta)`，其中 `display_meta` 与 `rows` 等长，每项至少包含 `confidence`、`confidence_strategy`、`source_breakdown`。
- `sdk.find(..., view=...)` 直接在展示对象上暴露聚合后的 `confidence`，不改变实体值字段语义。

## 11. 已定论

- **`Body.confidence` 值域**：`(0, 1]`，`0` 编译期报错。
- **不支持顶层 `confidence`**：只能在 `Body` 中定义。
- **单分支 `Body` 语法**：必须用 list 包裹 `where=[Body([...], confidence=0.8)]`，与多分支形式统一，SDK 构造层 `where` 类型签名不变。
- **`Derivation` 支持 `Body`**：与 Rule 一致。
- **`Query.Body.confidence` 编译期报错**：纯投影路径，无推理语义。
- **裸 list 与 `Body` 禁止混用**：编译期报错。
- **命名**：`confidence`，与 `meta.confidence` 对齐。
- **`confidence` 存储协议**：`kind="num"` → `kind="int"`，新增 `kind="float"`，SQLite 无需 schema migration。
- **`EvaluateMode` 重命名**：`"python"` → `"native"`，`"engine"` → `"souffle"`，旧名直接删除，注册表改为 `dict[str, fn]`。
- **`body_confidences` 传递**：内部签名链扩展，用户不感知，`native`/`souffle` 忽略。
- **`meta` 语义升格**：`meta` 是数据语义的一部分，不是附属信息。同一事实按不同 meta 并存是预期能力。`Derivation → accept` 默认语义是追加新证据，不修改旧证据。
- **duplicate 判定细化**：`_META_PRIMARY_KEYS` 只包含时间戳和 run/candidate 标识（`run_id`/`ingested_at`/`accepted_at`/`trace_id`/`candidate_id` 等）。`support_digest`、`derived_rule_id`、`schema_digest` 等语义溯源字段**不**排除，参与 duplicate 比较。业务语义 meta 完全相同才判为 duplicate，否则视为新证据并存。
- **`confidence` 写回**：ProbLog 推理结果直接作为新断言写入，携带自己完整的 meta（含 `run_id`、`derived_rule_id`、`confidence`），不查找现有 `asrt_id`，不追加 `MetaRow`。
- **`CandidateSet.confidence` 全链路透传**：`runtime_v1.py` 序列化/反序列化、`_with_candidate_run_id` 重建时均需显式保留该字段，否则服务层跨进程传递和多头合并时静默丢失。
- **可配置视图层**（本次范围内实现）：引入 `ViewSpec`，本次落 `active + confidence_strategy`；`valid_at` 下一阶段实现。`confidence_strategy` 仅作用于展示/读取层，不进入推理引擎。置信度聚合作为独立函数 `aggregate_confidence`，不侵入 `project_view_facts`，与 `chosen` 正交。
- **kind 体系重命名**：`"num"` → `"int"`，新增 `"float"`，与 `"str"`/`"bool"`/`"time"`/`"json"` 并列。导出文件分离：`meta_int.facts`（原 `meta_num.facts`）+ 新增 `meta_float.facts`。序列化通过 `repr()`（`_float_to_meta_str`），反序列化通过 `float()`（`_parse_meta_float`），约束为可逆性 `float(repr(x)) == x`。
- **`MetaRow.kind` 对用户不可见**：`kind` 由 `_infer_meta_kind` 通过 `_KEY_KIND_MAP` 统一派生，调用方无需也无法显式指定。所有 `CONVENTION_META_KEYS` / `SENSITIVE_SEMANTIC_META_KEYS` 必须在映射表中有条目，模块加载时 `assert` 检查。
- **引擎调用**：子进程模式，与 Souffle 适配器一致。
- **不引入 `support_kind="probabilistic"`**：调用哪个适配器已隐含推理器类型。
- **Noisy-OR 独立性**：ProbLog 建模约束，由用户保证数据质量，系统不强制干预。
