# 教程 6：事务策略与排障（v1/v2）

本教程总结 `apply-execute` 的事务策略语义、失败路径，以及如何用 CLI/Audit 页面快速定位问题。

## 1. 当前支持的事务策略

### `best_effort_no_rollback_v1`（默认）

- 支持 prevalidate（写前检查）
- 不支持 rollback / compensation
- 运行期写失败时，可能出现 `partial_apply=true`

### `prevalidate_no_partial_strict_v2`（当前最小可执行版）

- 需要显式传入 `--transaction-policy prevalidate_no_partial_strict_v2`
- 当前已可执行，但仍是**最小实现**
- 目前不承诺完整 rollback/compensation，因此“严格 no-partial”仍有边界（文档已明确）

## 2. 关键输出字段（排障优先看这些）

在 `apply_execute` 输出（或 `authoring_apply_execute_run` event）中关注：

- `idempotency.apply_request_id`
- `idempotency.plan_digest`
- `transaction.policy`
- `transaction.prevalidate_before_write`
- `transaction.prevalidate_status`
- `transaction.writes_started`
- `transaction.failure_phase`
- `transaction.partial_apply`

## 3. 常见执行路径（`execution_path`）

静态审计页面中的 authoring apply detail 会显示 `execution_path` / `execution_path_label`。

常见值包括：

- `success`
- `replay`
- `idempotency_conflict`
- `prevalidate_blocked`
- `runtime_partial`

> `runtime_partial` 表示执行阶段发生写失败；请结合 action events 与 `failure_summary` 查看具体原因。

### 3.1 页面友好标签：`execution_path_label`

在 `authoring_apply_runs/<req>.html` 页面里，一般会看到更友好的执行路径标签，例如：

- `Success`
- `Replay`
- `Idempotency conflict`
- `Prevalidate blocked`
- `Runtime partial apply`

## 4. 常见排障步骤

### 场景 A：同一个请求重复执行，结果不符合预期

先看：

```bash
python -m factpy_kernel.authoring.cli registry-show \
  --registry-dir .tutorial_work/registry \
  --kind apply-run \
  --id tutorial-req-001
```

检查：

- 是否 `replay`
- `plan_digest` 是否与你当前输入一致
- `transaction.policy` 是否发生变化（同 `request_id + plan_digest` 但策略不同会冲突）

### 场景 B：CLI 返回 `status=error`

优先检查：

- `diagnostics[]`
- `diagnostics_summary`
- `transaction.failure_phase`

再去静态审计页中看：

- `authoring_apply_runs/<req>.html`
- `failure_summary.blocked_action_diagnostic_codes`

## 5. 失败注入演练（最小示例）

如果你想演练 `runtime_partial` 路径，建议用 mock 模拟 registry 写失败（而不是修改真实代码）。示意：

```python
from unittest import mock

from factpy_kernel.authoring import AuthoringRegistryFSError, FileAuthoringRegistry
from factpy_kernel.authoring.cli import main

def _boom(self, _payload):
    raise AuthoringRegistryFSError(
        "simulated runtime write failure",
        code="registry_schema_write_failed",
        path="$.schema",
    )

with mock.patch.object(FileAuthoringRegistry, "upsert_schema_ir", _boom):
    main([
        "apply-execute",
        "--authoring-schema", "/path/to/authoring_schema.json",
        "--registry-dir", "/path/to/registry",
        "--apply-request-id", "req-runtime-demo",
    ])
```

演练后建议查看：

- `registry-show --kind apply-run --id req-runtime-demo`
- `authoring_apply_runs/req-runtime-demo.html`

## 6. 当前限制（必须知晓）

- `v2` 目前是最小可执行版，不是完整严格事务实现
- 未实现 rollback / compensation
- file registry 不是生产级并发/原子写 backend

## 7. 实践建议

- 开发与验证阶段：
  - 优先用 `workflow-dry-run` + `--safe`（针对 DSL）
  - 再执行 `apply-execute`
- 排障阶段：
  - 先 `registry-show --kind apply-run`
  - 再看 `authoring_apply_events.html`
  - 再看 `authoring_apply_runs/<req>.html` 详情页
