## Key Architectural Insight (discovered this session)

```
Not: "neurosymbolic reasoning engine" (推理引擎)

This is architecturally correct — but it means traceability/explainability capabilities should be **consumed from engines**, not **reconstructed in an annotation layer**.

### The delivery pipeline problem

This session built an extensive delivery pipeline:

```
evidence tree → summary → narrative → NL → ranking → bottleneck → additive
    → audit export → audit query → static HTML → visual upgrade
    → confidence routing → fact confidence carrier
```

The pipeline is well-engineered and reusable. But the **content flowing through it is thin**:

- Evidence tree shows rule structure + specific fact instances — not much more than reading the rule definition
- Certainty v1 returns null for any non-trivial Datalog (recursive, multi-path, nested)
- Narrative/NL is a presentation layer over shallow underlying data

**Analogy: we built an expensive highway system but only have bicycles driving on it.**

### What the evidence tree CAN and CANNOT do

**CAN do (for all Souffle complexity):**
- Show that a conclusion was derived ✅
- Show which specific facts were used ✅
- Show the rule structure (which rules referenced which) ✅
- Provide audit trail ("this conclusion used these facts at this time") ✅

**CANNOT do:**
- Explain WHY a condition failed (negative reasoning) ❌
- Show recursive derivation chains (only last step visible) ❌
- Show alternative proof paths ❌
- Answer counterfactual questions ("what if this fact changed?") ❌
- Provide minimal proof ("which facts are essential?") ❌

**Key limitation for ESA**: in compliance scenarios, "why is this NOT compliant?" is often more important than "why IS it compliant?" Current evidence tree can only answer the positive case.

### Certainty v1 limitations

- Only works on single-rule, flat-condition, non-recursive cases
- Returns null for: multiple rule_ref_edges, nested referenced_support, recursive Datalog, OR branches
- Incompatible with Souffle's core value (recursive reasoning)
- The entire certainty chain (summary → narrative → NL → ranking → bottleneck → additive → routing → confidence carrier) is well-built infrastructure but serves a very narrow computational result
- **Frozen as v1** — no further investment planned

### Root cause: annotation layer vs engine-native capabilities

```
Current: Engine (Souffle) → bindings only → framework reconstructs traceability from outside
Correct: Engine (Souffle -p) → bindings + provenance → framework consumes & presents

Current: Framework invents certainty scoring in annotation layer
Correct: Engine provides native probability/provenance → framework consumes & presents
```

Capabilities like provenance, sensitivity analysis, and minimal proof are **engine-native** — they require access to the engine's internal reasoning state. Reconstructing them post-hoc in an annotation layer either lacks information or equals re-running the engine.

## Engine Provenance Research (COMPLETED 2026-03-21)

### Souffle Provenance — FEASIBLE, LOW COST

**How it works**: `-t explain` runtime flag (interpreter mode). Produces full proof trees via stdin/stdout.

**What it provides**:
- ✅ Full recursive derivation chains (`explain rel(args)` → complete proof tree)
- ✅ Minimal-height proofs (automatic — tracks shortest derivation)
- ⚠️ Negative reasoning (`explainnegation` — interactive, requires specifying rules/bindings)
- ✅ JSON output (`format json` + `output filename`)
- Performance: ~1.3-1.5x overhead, lazy construction (zero cost until queried)

**Critical compatibility**: factpy already calls Souffle in interpreter mode (`runner.py` line 80). Adding `-t explain` requires NO architecture change — just add the flag and pipe explain commands via stdin, parse JSON output.

**Integration sketch**:
```python
# runner.py — add provenance mode
proc = subprocess.run(
    [souffle_bin, "-F", facts_dir, "-D", out_dir, "-t", "explain", program.dl],
    input="format json\noutput provenance.json\nexplain target(args)\n",
    capture_output=True, text=True
)
# Parse provenance.json → feed into evidence tree pipeline
```

**Limitations**:
- Interpreter-only (already the factpy default — not a new limitation)
- Minimal-height proof only (can't enumerate all paths — acceptable for audit)
- Negation explanation is interactive (need to specify which rule/bindings to check)
- Aggregate provenance (`count`, `sum`) support unclear
- No Python API — stdin/stdout pipe only

### ProbLog Explanation — FEASIBLE, MEDIUM COST

**What it provides**:
- ✅ Mutually exclusive proof enumeration (`problog explain model.pl`)
- ✅ Ground formula graph (`LogicFormula.to_dot()`, clause enumeration)
- ✅ Per-fact probability attribution via aProbLog provenance semiring (symbolic polynomials)
- ⚠️ Sensitivity: compile-once evaluate-many pattern (no built-in API)
- ❌ No built-in why-not explanation
- ✅ MPE (Most Probable Explanation) mode

**Integration**: requires switching from subprocess to Python API (`from problog.program import PrologString`) for richer access. Current factpy calls problog via subprocess.

**Key capability**: aProbLog `use_semiring` with polynomial semiring can produce expressions like `p1*p2 + p1*p3*(1-p2)` showing exactly how each fact's probability contributes to the query probability. This is true per-fact attribution, not heuristic scoring.

### Priority Order

```
Priority 1: Souffle -t explain → recursive proof chains + minimal proof
  Cost: LOW (add flag, parse JSON, feed into existing pipeline)
  Impact: evidence tree goes from "audit trail" to "reasoning explanation"
  Timing: can do in parallel with ECSS rule encoding

Priority 2: ProbLog explain mode → mutually exclusive proofs
  Cost: MEDIUM (switch from subprocess to Python API)
  Impact: probability-lane proof structure

Priority 3: aProbLog provenance semiring → per-fact probability attribution
  Cost: HIGH (understand semiring mechanism, integrate symbolic output)
  Impact: true probabilistic explainability
```

### Unified ProofNode Architecture

**Why this design is necessary**:

The framework supports multiple reasoning engines (Souffle, ProbLog, PyReason), each with fundamentally different computational models (deterministic, probabilistic, interval-based). Without a unified intermediate representation, the delivery pipeline (narrative, NL, audit, static) would need engine-specific rendering logic for every output format × every engine — an N×M explosion that makes adding new engines or new delivery surfaces prohibitively expensive.

The current evidence tree attempted to be engine-agnostic but achieved this by stripping away engine-native information (provenance, probability, intervals), leaving only the thin structural skeleton. The unified ProofNode design solves this by preserving engine-native annotations in an extensible dict while keeping the structural contract shared across all engines. This allows the delivery pipeline to remain engine-agnostic for structure but engine-aware for annotations — degrading gracefully when an annotation is absent rather than failing entirely.

This also addresses the core architectural insight from this session: traceability/explainability capabilities should be **consumed from engines**, not **reconstructed in an annotation layer**. ProofNode is the consumption interface — each engine adapter is responsible for translating engine-native provenance into this shared shape, and the framework never tries to reconstruct what the engine should have provided.

**Problem**: Souffle, ProbLog, and PyReason each produce provenance in completely different formats and semantics:

| Engine | Semantics | Proof structure | Node annotations |
|--------|-----------|----------------|-----------------|
| Souffle | Deterministic (true/false) | Tree (single minimal proof) | rule_id, min_height |
| ProbLog | Probabilistic (0.0-1.0) | DAG (mutually exclusive proofs) | probability, proof_index |
| PyReason | Interval ([lower, upper]) | Annotated graph | confidence bounds, iteration |

**Solution**: Unified intermediate representation consumed by the delivery pipeline, with engine-specific annotations as an extensible dict.

```python
@dataclass(frozen=True)
class ProofNode:
    """Engine-agnostic proof tree node. All engines produce this shape."""
    node_id: str
    node_type: str                  # "fact" | "derived" | "negation"
    relation: str                   # predicate name, e.g. "compliant", "reachable"
    args: tuple[str, ...]           # ground terms, e.g. ("satellite_1", "ecss_m_st_10")
    rule_id: str | None             # which rule derived this (None for base facts)
    children: tuple[ProofNode, ...]  # sub-proofs (empty for leaf facts)

    # Engine-specific annotations — extensible, not part of the core contract
    annotations: dict[str, Any] = field(default_factory=dict)
    # Souffle:  {"min_height": 3, "rule_number": 2}
    # ProbLog:  {"probability": 0.73, "proof_index": 1, "provenance_poly": "p1*p2"}
    # PyReason: {"lower": 0.6, "upper": 0.9, "iteration": 5}
```

**Adapter pattern** (mirrors existing engine execution adapter):

```
Engine-native provenance (each engine's own format)
    ↓ Engine-specific provenance adapter (one per engine)
Unified ProofNode tree/DAG
    + engine-specific annotations dict
    ↓
Framework delivery pipeline (summary → narrative → NL → audit → static)
```

**Each adapter's responsibility**:

| Adapter | Input | Output | Annotation keys |
|---------|-------|--------|----------------|
| Souffle provenance adapter | JSON proof tree from `-t explain` | `ProofNode` tree | `min_height`, `rule_number` |
| ProbLog provenance adapter | `LogicFormula` / explain output | `ProofNode` DAG | `probability`, `proof_index`, `provenance_poly` |
| PyReason provenance adapter | interval propagation log | `ProofNode` tree | `lower`, `upper`, `iteration` |

**Delivery pipeline adaptation** — narrative/NL renders differently based on available annotations:

```python
# Narrative renderer checks annotations to determine what to say
if "probability" in node.annotations:
    line = f"Fact {node.relation}{node.args} holds with probability "
           f"{node.annotations['probability']:.2%}"
elif "lower" in node.annotations:
    a = node.annotations
    line = f"Fact {node.relation}{node.args} confidence interval "
           f"[{a['lower']:.2f}, {a['upper']:.2f}]"
else:  # deterministic (Souffle)
    line = f"Fact {node.relation}{node.args} derived (deterministic)"
```

**Relationship to existing evidence tree**:

The current `candidate_evidence_tree` (built from `SupportArtifact`) captures rule structure + specific facts. `ProofNode` is a **richer replacement** that adds:
- Recursive derivation chains (not just last step)
- Minimal proof annotation (which facts are essential)
- Engine-native scoring (probability, interval, height)

Migration path: `ProofNode` lives alongside the existing evidence tree initially. The delivery pipeline can consume either. Once Souffle provenance adapter is proven, `ProofNode` gradually replaces the current evidence tree as the primary carrier.

**Design principles**:
- `ProofNode` core fields are frozen — all engines must produce `node_type`, `relation`, `args`, `children`
- `annotations` is the extensibility point — new engines add new keys, delivery pipeline degrades gracefully for unknown keys
- Framework never interprets engine-specific annotations without checking their presence first
- Engine adapters are the ONLY place that knows engine-specific provenance format

### Multi-Engine Data Format Architecture

**Key decision**: One user-facing format, engine-specific compilation hidden in adapters.

**Why not one universal engine format**: Adding new engines (e.g., PyReason) breaks universal formats because engine computational models are fundamentally different (relational vs probabilistic vs graph-interval). The current fact format implicitly assumes Datalog-style `predicate(entity, value)`, which doesn't naturally map to PyReason's annotated graph model. Forcing a universal format either loses engine-specific expressiveness or requires redesign with every new engine.

**Why not multiple user-facing formats**: Users should not need to know which engine runs underneath. Multiple formats create frontend confusion, management overhead, and force users to understand engine internals.

**Solution — compiler/adapter pattern (factpy already does this partially)**:

```
User layer (frontend / SDK)         Framework (compile/adapt)           Engine layer
─────────────────────              ───────────────────────            ────────────

User writes ONCE:                                                    Souffle receives:
  entity: satellite_1               → Souffle adapter →              satellite_1.facts (TSV)
  fact: material = "Ti"
  fact: mass = 150                   → ProbLog adapter →             material(satellite_1, ti).
                                                                     mass(satellite_1, 150).
                                     → PyReason adapter →            Node("satellite_1",
                                                                       material="Ti", mass=150)
```

**Frontend shows one unified view**:

```
Entity: satellite_1
├── material: "Ti-6Al-4V"
├── mass: 150 kg
├── compliant: true  [derived by Souffle]
└── failure_risk: 0.12  [derived by ProbLog]
```

The frontend does not expose that Souffle uses TSV, ProbLog uses Prolog terms, or PyReason uses graph nodes. Engine choice is a configuration decision, not a data format decision.

**Adding a new engine = writing a new adapter, not changing user interface**:

```
New engine support requires:
  ✅ Fact compilation adapter: unified fact → engine-native input
  ✅ Provenance adapter: engine-native output → ProofNode
  ❌ No schema changes
  ❌ No SDK changes
  ❌ No frontend changes
  ❌ No audit pipeline changes
```

**Cross-engine result interoperability**:

In practice, most deployments use ONE engine per project. Multi-engine workflows are possible but not the primary use case. If needed, cross-engine consumption uses explicit semantic bridges:

```
Deterministic → Probabilistic:  lossless (fact → probability 1.0)
Probabilistic → Deterministic:  lossy (requires threshold, user must configure)
Deterministic → Interval:       lossless (fact → [1.0, 1.0])
Interval → Deterministic:       lossy (requires threshold)
```

Each bridge is an explicit user decision, recorded in the audit trail. The framework does not auto-convert between semantic models.

### Rule Layer Architecture — The Hardest Problem

**The question**: Facts can be unified (all engines accept ground assertions). But rules are fundamentally different across engines. Does the SDK need one universal rule syntax, or separate syntaxes per engine?

**Current state**: The SDK `Rule(where=[Pred(...), ...])` is Datalog-flavored. It works for Souffle. ProbLog compatibility is partial (via `Body(confidence=...)` for probabilistic rules). PyReason compatibility does not exist.

**What each engine's rules look like**:

```python
# SOUFFLE (Datalog) — current SDK supports this
Rule(
    id="q.compliant",
    where=[Pred("material:strength", component, strength),
           Pred("standard:min_strength", standard, min_val),
           strength >= min_val],
    select=[component, standard],
)
# Compiles to: compliant(C, S) :- material_strength(C, Str), standard_min(S, Min), Str >= Min.

# PROBLOG — partially supported (Body.confidence)
Rule(
    id="q.risky",
    where=[Body([Pred("transaction:amount", acct, amt), amt > 10000], confidence=0.8),
           Body([Pred("account:flagged", acct, flag)], confidence=0.3)],
    select=[acct],
)
# Needs to compile to: 0.8::risky(A) :- transaction_amount(A, Amt), Amt > 10000.
#                       0.3::risky(A) :- account_flagged(A, F).

# PYREASON — NOT supported, fundamentally different
# Temporal steps:       reachable(X, Y, t+1) :- reachable(X, Z, t), edge(Z, Y).
# Interval annotations: edge(a, b) : [0.6, 0.9]
# Graph structure:      neighbors(X, Y) :- edge(X, Y) | edge(Y, X).
# Threshold rules:      infected(X) :- [proportion > 0.5] neighbor(X, Y), infected(Y).
```

**Why a universal rule syntax doesn't work**:

| Feature | Souffle | ProbLog | PyReason |
|---------|---------|---------|----------|
| Recursion style | Bottom-up fixed-point | Top-down SLD | Graph propagation |
| Negation | Stratified | Negation-as-failure | Interval complement |
| Probabilistic facts | ❌ No | ✅ `0.3::fact.` | ✅ `fact: [0.3, 0.3]` |
| Annotated disjunctions | ❌ No | ✅ `1/3::a; 1/3::b; 1/3::c.` | ❌ No |
| Temporal steps | ❌ No (encode manually) | ❌ No | ✅ Native `t, t+1` |
| Graph operations | ❌ No | ❌ No | ✅ Neighbors, degree, proportion |
| Aggregation | ✅ `count`, `min`, `max`, `sum` | ⚠️ Limited | ⚠️ Threshold-based |
| Function symbols | ❌ No | ✅ Yes (Prolog heritage) | ❌ No |
| Termination | ✅ Guaranteed | ❌ Not guaranteed | ✅ Bounded by timesteps |

Forcing a universal syntax either: (a) limits to the intersection of all engines (very small — essentially flat conjunctive rules only), or (b) grows into a superset that no single engine fully supports, creating confusing "this feature only works with engine X" situations.

**Recommended architecture — layered rule system**:

```
Layer 1: Core Rule IR (shared across all engines)
  — Conjunctive rules: A ∧ B ∧ C → Head
  — Predicate matching: Pred(name, var, var)
  — Comparison: var > value, var == var
  — Basic aggregation: count, min, max
  — RuleRef (call another rule)
  — This covers ~60-70% of real-world rules

Layer 2: Engine-specific extensions (opt-in per engine)
  — Souffle: stratified negation, subsumption, ADTs, lattice operations
  — ProbLog: probabilistic facts, annotated disjunctions, evidence conditioning
  — PyReason: temporal steps, interval annotations, graph operators, threshold rules

Layer 3: Raw engine syntax (escape hatch)
  — User writes native Souffle .dl / ProbLog .pl / PyReason syntax directly
  — Framework treats it as opaque, only handles fact I/O and provenance consumption
```

**How this works in practice**:

```python
# Layer 1 — works on ALL engines (SDK compiles to each)
Rule(
    id="q.compliant",
    where=[Pred("material:strength", comp, str), str >= 100],
    select=[comp],
)

# Layer 2 — ProbLog-specific (SDK validates engine compatibility)
Rule(
    id="q.risky",
    where=[Body([Pred("flagged", acct)], confidence=0.3)],  # ProbLog only
    select=[acct],
    engine="problog",  # explicit engine binding
)

# Layer 3 — raw syntax escape hatch
RawRule(
    engine="pyreason",
    source="""
    infected(X, t+1) :- [proportion > 0.5] neighbor(X, Y), infected(Y, t).
    """,
)
```

**Impact on adapter design**:

```
Adding new engine requires:
  ✅ Fact compilation adapter: unified fact → engine-native input
  ✅ Provenance adapter: engine-native output → ProofNode
  ✅ Rule compilation adapter: Layer 1 Core IR → engine-native rules
  ⚠️ Optional: Layer 2 extensions for engine-specific features
  ⚠️ Optional: Layer 3 raw syntax pass-through
  ❌ No schema changes
  ❌ No frontend changes (frontend shows Layer 1 rules universally;
     Layer 2/3 rules shown as "engine-specific" with raw preview)
  ❌ No audit pipeline changes
```

**Key design decision**: Layer 1 (Core Rule IR) is the `where_ast.py` AST that already exists. It currently supports: `PredAtom`, `RuleRefAtom`, `CmpAtom`, `InAtom`, `BuiltinAtom`, `NotAtom`, `AndExpr`, `OrExpr`. This is already a reasonable Core IR. The question is whether to extend it (risky — feature creep) or keep it stable and push engine-specific needs to Layer 2/3 (cleaner).

**Recommendation**: Keep Layer 1 stable. Use `Body(confidence=...)` as the precedent for Layer 2 extensions — it's already engine-specific (ProbLog) but lives within the SDK syntax. New engine-specific features follow the same pattern: optional fields that are validated only when the target engine is specified.

**Frontend implications**: The graphical rule builder in the frontend should target Layer 1 (core rules). Layer 2/3 rules are shown in a code editor with syntax highlighting for the target engine. This means the frontend doesn't need to understand every engine's syntax — it only needs to render the Core IR graphically and provide a text editor fallback for engine-specific rules.

## Certainty v1 — Frozen, Honest Assessment

### What it is
A lightweight heuristic scoring model for simple (flat, single-rule, non-recursive) Datalog derivations. Computes `impact = weight × confidence` per condition, aggregates via bottleneck (min) or additive (normalized sum).

### What it's not
- Not probabilistic reasoning (no probability theory semantics)
- Not compatible with recursive Datalog (returns null)
- Not a substitute for engine-native provenance

### Semantic model
```
confidence (instance-level, per-fact): "how sure are we about this fact?"
weight (rule-level, per-condition):    "how important is this condition to the rule?"
certainty (derived, per-candidate):    "how certain is this derivation?"

impact = weight × confidence
aggregate = min(impacts)       [bottleneck, default]
          = sum(norm_w × conf) [additive, explain-time option]
```

### Coverage
- Simple flat rules: works ✅
- Chain/recursive: null ❌ (could be implemented — needs eligibility guard relaxation + recursion)
- Multiple paths/OR: null ❌ (fundamental limitation — would need WMC)
- Shared subgoals: incorrect ❌ (assumes independence — fundamental limitation)

### Frozen contracts (DO NOT reopen without blueprint)
- CertaintySummary shape (including `aggregation` field)
- Evidence tree carrier fields (assertion_fact.confidence, predicate_witness_group.condition_confidence)
- ConfidenceKindResolver protocol
- Export-time materialization (certainty_summaries.jsonl)
- Ranking in annotation layer
- Test baseline: 234 tests

### Known gaps documented in architecture
- Chain/recursive propagation: deferred
- Probability lane: deferred
- WMC integration: deferred

## Team Reflection / Lessons

- "系统先行" (system first) is sound engineering, but both EXIST and ESA say: "show us it works in a real domain." The system is ready enough. Domain content is the gap.
- This session's most important discovery: the certainty/traceability capabilities built in the annotation layer are limited by being outside the engine. This is not a failure — it's architectural clarity. The framework's role is to consume and present, not to reconstruct engine-internal reasoning.
- ESA hasn't seen the current Souffle-based architecture. The delta from what they saw (LLM+Neo4j) to what exists now is large and positive — but only if demonstrated.
- The delivery pipeline (narrative/NL/ranking/audit/static) is well-built infrastructure that will become valuable when richer data sources (engine provenance, real ECSS rules) flow through it.
- An ESA AI department head personally provided a collaboration roadmap. This level of guidance is uncommon at pre-product stage and should be acted on quickly.
- EXIST "Nachbesserung" with specific requirements is more actionable than a vague rejection. Every requirement maps to something an ESA collaboration would provide.
