# FactPy Kernel 语法蓝图（v1）

本文件定义面向 `factpy_kernel` 的统一语法蓝图，覆盖三层：

- 用户侧 SDK 对象语法（推荐）
- Authoring DSL（字符串/文件输入，工具链语法）
- Core `where` IR（执行/编译语义基准）

目标：先稳定一个可执行的最小子集（MVP），在不破坏 `core` 语义一致性的前提下逐步扩展。

---

## 1. 分层与语义基准

### 1.1 三层职责

- **SDK 对象 DSL（推荐）**
  - 面向业务开发者，尽量贴近普通 Python 编程方式
  - 例：`Rule(...)` / `Derivation(...)` / `RuleRef(...)` / `with vars(...)`
- **Authoring DSL（工具链语法）**
  - 面向 CLI / 文件输入 / registry 工作流
  - 语法以 AST 解析 + helper/sugar 为主
- **Core Where IR（语义基准）**
  - `core` Python 求值器与 Soufflé 编译器共同依赖的执行语义
  - 采用 tuple/list 结构，避免运行期复杂表达式树

### 1.2 语义基准原则（重要）

- `core` 中 `("eq", a, b)` 表示 **值相等比较**，不是 Prolog 的统一（unification）
- `NOT` 语义按 **stratified negation** 理解，不以 Prolog NAF 为语义基准
- `OR` 使用 `where=[[...], [...]]`（多分支体）表达，不作为 builtin

### 1.3 最小 Where AST（治理层，PR-1/PR-2）

为支持后续规则治理、多后端能力矩阵与一致性回归，项目新增 **最小 where 语义 AST**（仅覆盖当前 where 子集）：

- 位置：`src/factpy_kernel/core/rules/where_ast.py`
- 校验器：`src/factpy_kernel/core/rules/where_ast_validate.py`

设计边界（当前阶段）：

- **不替代** 现有 `core where IR`（tuple/list）
- **不改变** `core` 对外行为与执行路径
- 先作为 **语义治理层**（round-trip + validator），当前已以入口 gate 方式接入 `where_eval/where_compile` 的前置校验（执行/编译仍使用原 where IR）

调试开关（兼容回退路径）：

- 环境变量 `FACTPY_WHERE_AST_VALIDATE`
  - 默认开启（未设置视为开启）
  - `0 / false / False / off / OFF` 关闭 AST 前置校验 gate
  - gate off 用于兼容兜底/回归；日常开发与 CI 默认保持 gate on

推荐回归命令（FactPy kernel）：

```bash
python -m unittest discover -s src/factpy_kernel/tests -p 'test_*.py'
FACTPY_WHERE_AST_VALIDATE=0 python -m unittest discover -s src/factpy_kernel/tests -p 'test_*.py'
```

Strict/profile 校验（Authoring compile，当前为可选产品能力）：

- 默认不启用 strict（保持现状行为）
- 启用方式：
  - `compile_authoring_rule_v1(..., strict=True)`
  - `compile_authoring_rule_v1(..., profile=PROFILE_SOUFFLE_STRICT)`
- `strict` / `profile` 仅影响 **AST gate 校验层**（不改变编译 payload 生成逻辑）
- 当前 `PROFILE_SOUFFLE_STRICT` 组合项：
  - `ruleref_policy=require_resolved`
  - `not_body_policy=forbid_or`
- HTTP 服务启动与接口路径见 `docs/service.md`

当前 AST 覆盖：

- `PredAtom`, `RuleRefAtom`, `CmpAtom`, `InAtom`, `BuiltinAtom(add/sub/neg/addc/mulc)`, `NotAtom`
- `AndExpr` / `OrExpr`
- `Var` / `Const`

当前阶段明确 **不做 normalize**（避免 round-trip 结构变化）：

- 不做 `neq -> not(eq)` 规范化
- 不做 OR 分支排序 / AND 重排
- 不做变量重命名（alpha-normalization）

## 2. 用户侧推荐语法（SDK 对象 DSL）

### 2.1 Schema（已支持）

```python
from factpy_kernel.sdk import Entity, Identity, Field

class Person(Entity):
    source_id: str = Identity()
    country: str = Field(cardinality="functional", pred_id="person:country")
```

### 2.2 Rule（推荐写法）

```python
from factpy_kernel.sdk import Rule, RuleRef, vars

with vars("p", "c", "li") as (p, c, li):
    rule = Rule(
        id="q_country_rows",
        version="1.0.0",
        select=[p, c],
        where=[
            LivesIn(li),
            li.person == p,
            li.country == c,
            RuleRef("q_other", version="1.0.0")(p, c),
            c != "xx",
        ],
    )
```

### 2.3 Derivation（推荐写法）

```python
from factpy_kernel.sdk import Derivation, vars

with vars("p", "c") as (p, c):
    drv = Derivation(
        id="drv.country_copy",
        version="1.0.0",
        head=Person.country(person=p, country=c),
        where=[("pred", "person:country", ["$p", "$c"])],
        materialize_as="fact",
    )
```

说明：`head=Person.field(...)` 的关键字参数名需要匹配该谓词的参数名；对普通无 dims 字段通常是 `person=<实体变量>, <字段名>=<值变量>`。只有带 dims 的字段（或显式 `value_name="value"`）才常见 `value=...` 写法。

### 2.4 Store（推荐写法）

```python
rows = sdk.run(rule)
cands = sdk.evaluate(drv)
res = sdk.accept(cands, meta_overrides={"approved_by": "admin"})
```

补充说明（当前实现）：

- `sdk.accept(...)` 也支持 keyword sugar：`approved_by=...`, `note=...`, `dry_run=True`
- `sdk.evaluate(...)` / `sdk.run(...)` 仍兼容低层 payload/spec 输入，但不作为教程主路径

## 3. Core Where IR（执行/编译基准）

`where` 采用以下形态：

- **AND**：`[atom, atom, ...]`
- **OR-of-AND**：`[[atom, ...], [atom, ...]]`

其中 `atom` 为 tuple。

### 3.1 基础 atom（已支持）

- `("pred", pred_id, [terms...])`
- `("ruleref", rule_id, version, [terms...])`
- `("eq", lhs, rhs)`
- `("in", var, [values...])`
- `("gt", lhs, rhs)`
- `("ge", lhs, rhs)`
- `("lt", lhs, rhs)`
- `("le", lhs, rhs)`
- `("not", [atom, ...])` 或 `("not", [[...], [...]])`

### 3.2 线性算术 builtin（v1 新增，已支持）

为保持 `core` 与 Soufflé 编译路径一致，采用“扁平 builtin atom”形式（不使用表达式树）：

- `("add", z, x, y)` -> `z = x + y`
- `("sub", z, x, y)` -> `z = x - y`
- `("neg", z, x)` -> `z = -x`
- `("addc", z, x, c)` -> `z = x + c`
- `("mulc", z, x, c)` -> `z = x * c`（`c` 必须是常量）

说明：

- `z` 必须是变量（例如 `"$age"`）
- `x/y` 可为变量或字面量（`addc/mulc` 的 `c` 必须是字面量）
- 当前语义仅支持 **整数线性算术**（bool 不允许参与）

### 3.3 term 约定

- 变量：以 `$` 开头的字符串，如 `"$p"`、`"$age"`
- 字面量：`str / int / bool / float / None`（实际是否允许由 atom 类型决定）

## 4. 算术表达式如何映射到 Where IR

SDK 对象 DSL 中可写比较自然的算术表达式；lowering 后会展开为扁平 builtin atom。

示例（SDK 写法）：

```python
age == (2026 - by)
age >= 18
```

lower 后（Where IR）：

```python
[
  ("sub", "$_arith1", 2026, "$by"),
  ("eq", "$age", "$_arith1"),
  ("ge", "$age", 18),
]
```

说明：

- SDK 会生成临时变量（如 `$_arith1`）
- 这是实现细节，名称不应被业务代码依赖

## 5. 静态规则（编译器/校验器必须执行）

### 5.1 变量绑定安全（必须）

对算术与比较类 atom：

- 输入变量必须在前面的正 atom 或算术 builtin 中已经绑定
- 输出变量（如 `z`）若未绑定，则在该 atom 后绑定
- 输出变量若已绑定，则作为一致性检查（不满足则分支失败）

### 5.2 类型约束（v1）

- 算术 builtin 仅支持整数操作数
- `gt/ge/lt/le` 仅允许可比较数值/时间域（由 `core`/编译器校验）
- `mulc` 的常量项必须是数值字面量

### 5.3 NOT 约束

- `NOT` 默认按 stratified negation 语义处理
- `NOT` 分支必须引用至少一个外层已绑定变量（防止不安全否定）
- 工程上建议用 `free_vars(not_body)`（外部相关变量集合）判定相关性，而不是 `vars(not_body)` 全量变量集合

### 5.4 AST validator 的最小数据流规则（PR-2）

`where_ast_validate.py` 的第一批规则目标是 **复刻现状而不增强语义**：

- 按 `AndExpr` 左到右做 branch-local 数据流检查
- 将校验拆为两层：
  - 结构/形态检查（node 类型、arity、allow-list）
  - 绑定检查（`requires(atom)` / `binds(atom, bound)`）
- `NotAtom` 使用：
  - `bound_outside`（进入 not 前外层已绑定变量）
  - `free_vars(not_body)`（not 体对外部环境的引用变量集合）
  - 约束：`free_vars(not_body) ⊆ bound_outside` 且 `free_vars(not_body) != ∅`
- `OrExpr` 在 PR-2 **不要求**“出口变量集合一致”；仅复刻现状需要的覆盖/安全性约束

## 6. 后端能力 profile（语义能力，不是具体语法）

本项目当前落地优先级：`core(Python)` + `Soufflé`。

### 6.1 Core 默认 builtin 集（推荐共同子集）

- `EQ, NEQ`
- `LT, LE, GT, GE`
- `ADD, SUB, NEG, ADDC, MULC`

当前 `NEQ` 通过 `("not", [("eq", ...)])` 形式表达。

### 6.2 扩展 builtin（未纳入 v1 默认核心）

- `MUL`（非线性）
- `DIV`
- `MOD`
- `ABS`
- `ITE`

这些能力会影响：

- 可判定性（尤其 CHC/SMT）
- Python/Soufflé/ProbLog 的语义一致性
- 编译器复杂度与测试成本

## 7. Authoring DSL（字符串）与 SDK 对象 DSL 的关系

### 7.1 现状定位

- **SDK 对象 DSL**：推荐给业务开发者（更 Pythonic）
- **Authoring DSL 字符串**：推荐给 CLI / 文件输入 / 工具链

二者目标是 lower 到同一类 authoring payload / compiled spec。

### 7.2 当前支持差异（v1）

已对齐的关键项：

- `RuleRef(...)(...)`（字符串 DSL parser 已支持）
- infix 比较：`== != > >= < <=`

尚未对齐项（字符串 DSL parser）：

- `ast.BinOp` 算术表达式（如 `age == (2026 - by)`）
- attr-to-attr 比较 sugar（如 `a.x == b.x`）的自动 lowering

建议：

- 业务代码优先使用 SDK 对象 DSL 获得算术表达式支持（lower 为 builtin atom）
- CLI/文件 authoring DSL 在字符串语法层先保持保守子集

## 8. 示例：成人筛选规则（完整）

SDK 对象 DSL：

```python
with vars("p", "by", "age") as (p, by, age):
    rule = Rule(
        id="q_adults",
        version="1.0.0",
        select=[p, age],
        where=[
            ("pred", "person:birth_year", ["$p", "$by"]),
            age == (2026 - by),
            age >= 18,
        ],
    )
rows = sdk.run(rule)
```

Where IR（典型 lowering）：

```python
[
  ("pred", "person:birth_year", ["$p", "$by"]),
  ("sub", "$_arith1", 2026, "$by"),
  ("eq", "$age", "$_arith1"),
  ("ge", "$age", 18),
]
```

## 9. 后续扩展路线（建议）

1. 在 `core where_eval` / `Soufflé where_compile` 保持 parity 的前提下扩展更多线性表达式
2. 再评估 `DIV/MOD/ABS` 等扩展 builtin（按 backend profile 显式开启）
3. 最后再扩字符串 DSL parser 的 `ast.BinOp` 支持

设计原则：**先扩 IR 与执行语义，再开放更“好看”的语法糖**，避免“语法能写但运行不了”。
