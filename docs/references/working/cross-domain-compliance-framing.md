### 第一层：ECSS/ESSB 条款告诉我们什么是"合规追溯"

研究结果非常清楚地揭示了 ESA 合规演示的结构。每一条 ESSB-ST-U-007 的 **"shall"** 条款都需要：

1. **VCD（Verification Control Document）** — 每条要求有唯一 ID、分配的子系统、验证方法、验证状态、以及指向证据文档的引用
2. **SDMR（Space Debris Mitigation Report）** — 逐条款列出合规状态，附 Monte Carlo 置信区间
3. **RID 闭环记录** — 每个不符合项都要有追溯到"已关闭"的完整证据链
4. **Waiver（豁免申请）** — 无法达标时，需要有完整的风险接受理由和补偿措施

关键的时间窗口与阈值例如：

- Pc（碰撞概率）阈值：**1×10⁻⁴ per conjunction**，触发后需降低两个数量级
- 近地轨道处置时限：**5年**
- 处置成功概率：**≥90%**（大型星座 ≥95%）
- 重返大气层人员伤亡风险：**≤1×10⁻⁴**

这些都是**可以用规则精确表达的义务与阈值**，而且每一条都需要**可追溯到具体证据的推理链**。

### 第二层：金融合规用例——与 ECSS 框架的深度同构

实例原文: 一个新开立的公司账户在36小时内收到来自不同汇款人的多笔转账，每笔金额都略低于机构的报告阈值。不久之后，这些资金被汇总并转至高风险司法管辖区的单一受益人。此外，还有一些微弱但可组合的信号表明，该账户与一位已引起怀疑的客户存在共同的经济影响：相同的支付设备、相同的境外受益人以及不一致的受益所有人信息。
我们为何能在此提供帮助？因为关键不在于识别单个大额支付，而在于从一系列异构事件中推导出与监管相关的状态信息。这正是义务、时间窗口推理和概率的交汇点。该系统能够从分布式流事件中推导出可解释的义务和风险状态，而不仅仅是统计原始警报数量。

两个领域的结构同构性的对照：

| 金融合规（AML/KYC）维度 | ECSS 空间碎片合规维度 | 系统必须提供的能力 |
|---|---|---|
| 36小时内多笔低于报告阈值的转账 | 5年内处置窗口、1×10⁻⁴ 碰撞概率阈值 | **时间窗口推理 + 阈值监控** |
| 多个汇款人 → 汇总 → 高风险司法管辖区 | 多个子系统 → 组合失效 → 超出 Pc 阈值 | **分布式事件 → 推导状态** |
| "略低于报告阈值"的刻意规避 | 松散要求之间的合规漏洞探测 | **否定推理 / 规避检测** |
| 共同经济影响的弱信号（同设备、同受益人、不一致的 BO 信息）| 多源证据组合（CDM 数据、轨道参数、可靠性分析）| **弱信号组合推理 + 置信度传播** |
| 为何此刻触发 SAR（可疑活动报告）义务 | 为何此刻 Pc 触发 CAM 执行义务 | **义务状态推导 + 可解释推理链** |
| 监管审计需要完整的决策追溯 | VCD/SDMR 需要逐条款证据引用 | **Audit-log → Proof-tree 输出** |

这个同构性有一定说服力。**此金融用例不是偏离 ESA 方向的，而是在一个更成熟、更具说服力的领域证明了系统的普遍价值。**

### 第三层：蓝图架构思想的具体可行性评估

现在可以逐点对蓝图中的四个候选方向做具体评估：

#### 方向 1：`CandidateSet-first`
**对应 ECSS 现实：** VCD 中每条要求的验证状态就是一个候选集——"这条要求是否合规"是个带置信度的候选结论。

**对应金融用例：** "账户 X 在时间窗口 T 内是否触发了 SAR 义务"是一个 CandidateSet，其 `confidence` 来自多个弱信号的组合。

**可行性：高。** 但 `confidence` 字段目前是窄字段，金融用例中需要的是多维度的弱信号加权，这正是 annotation/provenance 需要扩展的地方。

#### 方向 2：`audit-log-first`
**对应 ECSS 现实：** 这直接对应 VCD + SDMR 的逐事件追溯链。ESA 验证过程中每一步都需要有"哪次 run、哪条规则、哪个证据产生了这个结论"的记录。

**对应金融用例：** 监管机构审查 SAR 时，最基本的要求就是"系统为什么在这个时间点标记了这个账户"——这是 audit-log 的直接价值。

**可行性：最高，且是近期演示最容易落地的形态。** 当前仓库的 audit 基础设施直接可用。

#### 方向 3：`proof-tree / support-graph-oriented`
**对应 ECSS 现实：** ESSB-HB-U-002 的三层合规层级（System → Equipment → Material）本质上就是一棵 proof-tree。每一层的置信度向上传播（Monte Carlo 5% 显著性水平）。

**对应金融用例：** "为什么认为存在洗钱风险"的推理树：`SAR义务成立 ← (时间窗口违规 ∧ 高风险司法管辖区 ∧ 弱信号组合的置信度 > 阈值)`

**可行性：中期目标，是与竞品最大的差异化来源。** 当前没有通用工具能输出这种结构化推理链，这恰好是 ESA 说"我们喜欢可解释性"的核心所在。

#### 方向 4：`hybrid`（候选/注释/审计/图的分层）
**对应 ECSS 现实：** 完整的 ECSS 合规包就是 hybrid：候选状态（VCD 行）+ 语义注释（waiver 理由）+ 运行审计（RID 记录）+ 可视化图（项目评审报告中的 Verification Matrix）。

**对应金融用例：** 同样是 hybrid：风险状态（CandidateSet）+ 信号注释（哪条规则贡献了多少置信度）+ 决策追溯（audit log）+ 关系可视化（账户关系图）。

**可行性：长期理想形态，当前应以 hybrid 为方向，按 audit → proof-tree → graph 分阶段交付。**

### 第四层：金融用例 vs. ESA 场景作为演示入口的对比

| 维度 | 金融合规（AML/KYC） | ESA/ECSS 合规 |
|---|---|---|
| 用例具体性 | ✅ 极具体，立刻可演示 | ⚠️ 仍需选定具体条款和数据 |
| 受众理解门槛 | ✅ 任何商业听众都能理解 | ⚠️ 需要航天背景 |
| 监管框架复杂度 | ✅ FATF/4AMLD 框架清晰 | ✅ ECSS/ESSB 框架非常结构化 |
| 数据可获得性 | ✅ 合成数据易于生成 | ⚠️ 轨道数据/CDM 数据需要外部来源 |
| 与蓝图核心能力的匹配度 | ✅ 完美匹配（时间窗口 + 弱信号组合 + 义务推导 + 追溯） | ✅ 完美匹配（阈值 + 多源证据 + 处置义务 + VCD追溯） |
| ESA Discovery 申请适用性 | ❌ 不直接适用（ESA 关注空间应用） | ✅ 直接适用 |
| 市场规模与扩展性 | ✅ 金融合规市场巨大，且 "regulation-heavy" 领域通用 | ⚠️ 航天客户群体较小 |

### 结论

**1. 蓝图的架构思想是切实可行的，而且在两个方向上都有坚实支撑：**
- **ESA 方向**：ECSS/ESSB 的 VCD + SDMR + RID 闭环结构 = audit-log → proof-tree 的直接映射，系统恰好能填补"逐条款合规状态推导 + 证据追溯链自动化"这个当前手工操作繁重的缺口
- **金融合规方向**：描述的 AML 用例精准命中了系统最核心的差异化能力——从分布式异构事件中推导可解释的义务状态

**2. ESA 邮件指出的"缺 concrete use case"的问题，金融用例其实已经回答了**，而且回答得比 ECSS 场景更清晰。建议的策略是：
- 用**金融 AML 用例**作为 Discovery 申请和对外演示的**主 walkthrough**（任何听众都能理解）
- 用 **ECSS 合规场景**作为 ESA 专项材料中的**领域映射**（证明系统能迁移到航天监管）

**3. 蓝图中最需要推进的是 `audit-log-first → proof-tree` 这条路径**，因为两个领域的用例都直接需要它，而且当前仓库最接近可演示状态的也是这条路径。
