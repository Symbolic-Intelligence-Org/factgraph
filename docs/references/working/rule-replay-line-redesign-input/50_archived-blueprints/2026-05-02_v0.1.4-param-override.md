## 1. Problem

v0.1.1 established rule replay as an evidence-read-only workflow: operate on
temporary rule/derivation variants, re-evaluate, then compare candidates and
shallow evidence metadata. v0.1.2 added owner/path-scoped condition modules and
support-key-to-module-id joins. v0.1.3 added `action="disable"` using a native
runtime overlay that preserves payloads, module maps, and support-key locators.

The next likely operation is parameter override: temporarily change the value
used by one condition module without rewriting or deleting evidence. This is
the user-facing "try threshold 30 instead of 20" case, but the current system
does not yet have a first-class parameter handle. The design must avoid
pretending that arbitrary condition AST mutation is already supported.

The open design question is what "parameter override" means in today's
tuple-form where language. It might mean replacing a literal inside an atom,
overriding a declared parameter handle, injecting a temporary binding, or
applying an evaluation-time overlay. Each shape has different effects on
variable binding, support artifacts, module identity, candidate identity, and
future Parameter Handle UX.

This blueprint starts as a draft. It must run a source-backed Step 0 feasibility
spike before entering `scoped`.

## 2. Goals

- Define source-backed semantics for replay-time parameter override.
- Preserve the v0.1.1-v0.1.3 boundary: rule/derivation variants are operable;
  evidence remains read-only and run-derived.
- Preserve `b{branch}.a{atom}` locator stability and v0.1.2 module identity
  invariants.
- Decide whether v0.1.4 should implement a literal override now, reserve
  declarative Parameter Handle for later, or first add parameter declaration
  substrate.
- Keep `SDKStore.evaluate(...)` public surface narrow unless Step 0 proves a
  broader evaluation overlay contract is necessary.
- Keep RuleRef-bound replay, multi-engine replay, candidate universes, audit
  JSONL persistence, persistent rule variants, and mutable evidence trees out
  of scope unless Step 0 explicitly re-scopes them.

## 3. Non-goals

- No mutable evidence tree API.
- No compiled-plan in-place rewrite.
- No persistent rule variant storage or promotion to a new rule version.
- No general condition AST editor.
- No add-condition operation.
- No lazy why-not / red-green completeness board.
- No multi-engine parameter override unless separately proven.
- No RuleRef-bound replay support unless Step 0 changes scope.
- No audit JSONL persistence of replay events in this blueprint.
- No public `SDKStore.evaluate(..., param_overrides=...)` unless Step 0 locks
  that as the minimal correct shape.

## 5. Proposed Shape

Draft framing only:

```text
authoring derivation/rule body
  -> module IR over complete body
  -> apply replay-time parameter override shape
  -> evaluate original and variant
  -> candidate diff + shallow evidence/module mapping
```

The likely target is an extension of `replay_with_patch(...)`, but the exact
action name and carrier are blocked on Step 0. Candidate shapes include:

- `action="param"` with a structured `param_override=...`;
- `action="replace"` over a literal term only;
- declarative parameter handles first, then override handles later;
- native runtime overlay over resolved literal values.

This blueprint should not enter `scoped` until Step 0 decides the semantic
unit being overridden and the layer that owns it.

## 6. Boundaries And Invariants

- Compile / validate / evaluate remains authoritative.
- Evidence remains read-only and run-derived.
- Parameter override must produce a temporary replay variant, not mutate the
  source rule/derivation in place.
- Existing `replay_with_patch(action="replace"|"disable")` behavior must remain
  backward compatible.
- Existing locator support (`b{branch}.a{atom}`) must remain valid.
- Module ids remain owner/path-scoped. A replay-time parameter override must not
  mutate stored `ConditionModule.atom` after `module_id` computation.
- Candidate diff must continue to use `candidate_key`.
- RuleRef-bound replay remains rejected unless Step 0 explicitly proves a safe
  registry-context carrier.
- Public API stays narrow by default: do not add `SDKStore.evaluate(...)`
  overlay kwargs unless there is a source-backed need.

## 8. Implementation Plan

### Step 0 — Source-Backed Feasibility And Scope Lock

Answer these before implementation:

1. Parameter override semantics:
   - Is v0.1.4 overriding a literal value inside one atom, a future declared
     parameter handle, an expression value, or a temporary variable binding?
   - Which current atom kinds can safely support override without a general AST
     editor (`eq`, comparisons, `in`, arithmetic constants)?
   - Should the first scope deliberately exclude non-literal sides?

2. Variable binding / confidence impact:
   - If override changes a binder into a filter, or a filter into a binder,
     where does failure surface today?
   - Does overriding comparison thresholds affect `confidence` /
     `confidence_kind`, or only candidate membership?
   - Should v0.1.4 rely on existing compile / where-validation errors, or add a
     replay-domain preflight?

3. Locator / support mapping:
   - Does override change support keys? Or should the same locator emit the same
     `b{branch}.a{atom}:...` key with changed step details / support digest?
   - Should `variant_module_map` retain the same module ids if the variant
     atom content changes, or should replay expose an additional override map?
   - How does this interact with owner/path-scoped module ids that include atom
     content?

4. Public API shape:
   - Extend `replay_with_patch(...)` with `action="param"`?
   - Add a new method such as `replay_with_param_override(...)`?
   - Treat literal override as a constrained `replace` operation?
   - Which shape avoids broadening `SDKStore.evaluate(...)` prematurely?

5. Payload / DTO carrier:
   - Should overrides be represented as `dict[str, Any]`, a structured DTO, or
     action-specific kwargs?
   - Should keys be locators, module ids, explicit parameter ids, or future
     `shared_id` handles?
   - Does the carrier imply persistent rule variant semantics by accident?

6. RuleRef and registry context:
   - Does parameter override remain unsupported for RuleRef-bound derivations
     under the current dict replay path?
   - Is v0.1.1-v0.1.3's `REPLAY_UNSUPPORTED_DEPENDENCIES` still the right
     boundary?

7. Tests and docs:
   - Which targeted tests are required for literal threshold override, invalid
     locator/term, list-form atoms, variable-binding failure, no-op override,
     candidate diff, evidence digest change, and module-map behavior?
   - Which SDK/authoring docs need updates if the public API expands?

## 10. Outcome / Deviations

Closed as `abandoned` on 2026-05-02 after Step 0 Phase 1 source-backed
feasibility.

### Final landed result

No runtime implementation landed. The useful output was the Step 0 decision:
`param_override` is not one coherent capability in the current architecture.

Phase 1 separated four distinct value families:

- **Atom literal / term changes**: e.g. `("eq", "$risk", "high")` ->
  `("eq", "$risk", "medium")` or changing constants inside
  `("pred", pred_id, [terms...])`. These affect candidate membership and
  support digest. Implementing this by changing the atom is a constrained
  `replace_atom` path, not a new parameter model.
- **`condition_weights[locator]` changes**: rule asset metadata consumed by
  certainty / explain materialization, not by where execution. These affect
  certainty summaries, not candidate membership.
- **ProbLog probability carriers**: branch probabilities / fact probabilities
  owned by the ProbLog adapter and engine extension path.
- **PyReason bounds / thresholds**: body predicate bounds, head bound, and
  run-time reasoner configuration owned by the PyReason adapter.

Because these families have different owners, read sites, effects, and
testing contracts, a single `param_override` API would be a false abstraction.

### Scope decision

Chosen strategy: **stop v0.1.4 and move to v0.1.x release close-out**.

Rejected alternatives:

- Do not ship a small constrained-replace helper as v0.1.4. It is only sugar
  over existing `replay_with_patch(action="replace")` and does not justify a
  version slice.
- Do not scope Parameter Handle yet. It is a real future substrate because it
  solves "value changes, identity remains stable", but it needs its own Step 0
  design around handle identity and override maps.
- Do not pivot immediately to another deferred feature. That would hide the
  release-strategy decision rather than resolve it.

### Deviations from draft framing

The draft asked whether v0.1.4 should implement a replay-time parameter
override. Step 0 answered negatively: current source facts show no single
implementation unit named "parameter override" that preserves the
v0.1.1-v0.1.3 boundaries without either collapsing into replace sugar or
expanding into multiple independent features.

### Archive plan

Archive this blueprint and audit immediately as `abandoned`. Keep the
`v0.1.4-param-override` branch as a design-probe branch for traceability; do
not delete it as part of this close-out.
