## 1. Problem

v0.1.1 rule replay intentionally used the smallest safe substrate: patch a top-level derivation authoring payload at an atom-position locator such as `b0.a3`, then recompile and re-evaluate. That preview proved the product loop, but it did not solve the deeper object model problem.

The current rule body shape is still mainly list/tuple authoring IR. This is enough for compile/evaluate, but it is a weak user-facing substrate for future operations such as:

- disabling a condition without deleting knowledge from evidence;
- replacing a condition while preserving identity and history;
- declaring a parameter handle for threshold-like changes;
- mapping evidence nodes back to the rule module that produced them;
- supporting shared conditions or library conditions without accidental global edits.

v0.1.2 should investigate and, if source-backed, introduce a rule module IR layer that keeps the v0.1.1 boundary intact: rules / derivations are operable, evidence remains read-only and run-derived, and authoritative truth still comes from compile / validate / evaluate.

## 2. Goals

- Define a source-backed L2 rule module IR shape for rule/derivation bodies.
- Preserve the v0.1.1 replay contract and keep existing authoring payloads compatible.
- Decide how module identity relates to existing `b{branch}.a{atom}` locators.
- Decide which first operation, if any, should graduate from atom replacement to module operation.
- Define how evidence views can point back to module identity without becoming mutable evidence.
- Keep future compatibility with Parameter Handle, `disable_condition`, shared condition identity, and candidate-universe work.

## 3. Non-goals

- No mutable evidence tree API.
- No partial proof mutation or local proof re-evaluation as source of truth.
- No in-place mutation of `CompiledDerivationPlan.body_ir`.
- No cross-engine module semantics unless separately proven.
- No lazy red/green board or complete failed-case universe in this blueprint.
- No persistent replay audit JSONL unless an engine-neutral export owner is explicitly introduced.
- No breaking change to existing tuple/list authoring payloads without a migration plan.
- No public API expansion before Step 0 resolves the object model and compatibility questions.

## 5. Proposed Shape

Scoped v0.1.2 shape:

```text
authoring rule / derivation body
  -> module-aware body IR
  -> existing where IR lowering
  -> compile / validate / evaluate
  -> read-only evidence view with module pointers where available
```

The module-aware layer is a compatibility layer, not a replacement for the current compiler in one jump. Existing tuple/list authoring payloads continue to compile. New module objects lower to tuple-form `where` IR before runtime evaluation. Evaluators, Souffle, PyReason, and current support artifact builders must not see module container objects.

Ownership decision: module IR lives in `kernel.authoring` as a lowerable DTO/substrate. SDK may expose ergonomic construction helpers later, but the first implementation should not make module IR a top-level SDK product surface. Core runtime should remain tuple-IR based.

Identity decision: generated module ids are owner/path-scoped and stable, not pure content hashes. A generated id should include owner identity/version plus branch/atom position and normalized lowered atom content. This avoids accidental shared identity when two rules contain identical atoms. Cross-rule or library-level identity requires explicit `shared_id` / library reference in a later scope.

First operation decision: v0.1.2 lands the module carrier and lowering path, then wires the existing atom replacement replay flow through that carrier where possible. It does not add new behavior such as `disable_condition` or `param_override`. The public v0.1.1 replay contract remains compatible.

Evidence should never be the mutation target. Evidence may expose module pointers or locators to help users understand which rule module participated in a run, but operations produce rule/derivation variants and then re-run the normal pipeline.

## 6. Boundaries And Invariants

- Compile / validate / evaluate remains the authoritative runtime path.
- Evidence is read-only and run-derived.
- Module identity must not rely on `candidate_id`.
- Module identity must coexist with `b{branch}.a{atom}` for backward compatibility.
- Any module-level operation must have clear binding validation semantics before evaluation.
- Shared identity must be explicit. Default edits should affect only the current rule/derivation module.
- `kernel.audit` remains a consumer of exported packages, not a live replay write owner.
- `v0.1.1-preview` remains frozen except for hotfixes; this blueprint works on the stacked v0.1.2 branch.

## 8. Implementation Plan

### Step 0 — Source-Backed Feasibility And Scope Lock

Completed on 2026-05-02.

1. Existing body shape inventory:
   - Decision: module IR must lower to tuple-form `where` IR before evaluator/backend entrypoints.
   - Source basis:
     - `src/kernel/core/rules/where_eval.py::_is_atom` accepts tuple-only atoms.
     - `src/kernel/adapters/souffle/where_compile.py::_is_atom` accepts tuple-only atoms.
     - `src/kernel/adapters/pyreason/where_compile.py::_validate_pred_atom` expects tuple atoms.
     - `src/kernel/authoring/rule_compile.py::_is_where_atom` accepts tuple-form and JSON list-form atoms.
     - `src/kernel/sdk/replay.py::_is_where_atom` mirrors the tuple/list authoring tolerance.
   - Risk found: `src/kernel/core/rules/rule_ir.py::_normalize_where_branches` silently falls back to `return [list(where)]` for mixed shapes. Module containers must not leak there.
   - Risk found: `src/kernel/sdk/store.py::_validate_body_confidences_arity` uses list-based branch detection, so module containers must be lowered before body-confidence arity checks or the arity checker must be upgraded.

2. Module IR ownership:
   - Decision: place the first module IR substrate in `kernel.authoring`.
   - Rationale: SDK is the product facade and should not become the canonical IR owner; core evaluators are tuple-IR/runtime code and should not see authoring module containers. `kernel.authoring` already owns lowering and validation-adjacent transformation from ergonomic/authoring shapes to runtime shapes.
   - Initial lowering hook candidates: `lower_blueprint_where_sugar_with_schema_v1(...)`, rule/derivation compile paths, or a new authoring module body lowerer called before existing compiler validation.

3. Module identity and locator strategy:
   - Decision: retain `b{branch}.a{atom}` as compatibility locator and add owner/path-scoped module ids as an optional identity layer.
   - Generated ids should be stable but not globally shared by content alone. Recommended input: owner kind/id/version, branch index, atom index, and normalized lowered atom content.
   - Explicit user identity must be namespaced separately from generated identity. Future shared/library identity must be opt-in through `shared_id` or a library reference, not inferred from identical atom text.
   - Rationale: v0.1.1 showed `candidate_id` was unstable because it carried `run_id`; module ids need cross-run stability. But pure content hashes would accidentally merge same-shaped conditions in unrelated rules.

4. First operation scope:
   - Decision: v0.1.2 first lands the module carrier/lowering path and keeps behavior equivalent to v0.1.1 atom replacement.
   - Out of scope for this blueprint: `disable_condition`, `param_override`, add-condition, persistent rule variant promotion, and candidate-universe UX.
   - Rationale: operation semantics that remove or add atoms need binding validation and UX rules that deserve separate blueprints. The lowest-risk v0.1.2 value is making the body object model real without expanding behavior.

5. Evidence mapping:
   - Decision: native support artifacts already expose positional evidence keys, but not module ids. v0.1.2 can map evidence to module ids by joining support keys back to the lowering map.
   - Source basis:
     - `SupportArtifact.pred_witnesses[].pred_atom_key` and `non_fact_steps[].step_key` carry suffixed keys such as `b0.a1:pred_id` or `b0.a2:eq`.
     - `make_pred_atom_key(...)` and `make_non_fact_step_key(...)` generate those keys.
     - `Store.explain_support(support_digest)` can retrieve a rendered support artifact from the in-memory/sidecar support store.
   - Minimum carrier: the module lowerer must emit a sidecar mapping `{locator -> module_id}` and `{module_id -> locator}` for the current authoring body. Evidence mapping can normalize support keys to their `b{branch}.a{atom}` prefix and join against that map.
   - Audit package persistence of module maps remains out of scope unless an engine-neutral export owner is introduced.

6. RuleRef and dependency rules:
   - Decision: inherit v0.1.1 rejection for registry-bound replay in v0.1.2.
   - Source basis:
     - SDK object paths can discover object-backed dependencies through `dependency_rules()`.
     - Dict payload paths have no method to recover registry context.
     - `SDKStore.replay_with_patch(...)` currently rejects non-empty `dependency_rules()` with `REPLAY_UNSUPPORTED_DEPENDENCIES`.
   - Rationale: adding `registry=` replay support or embedding registry bindings into module IR would expand scope beyond the no-new-behavior v0.1.2 carrier work.

7. Compatibility and docs:
   - Decision: docs must frame module IR as an authoring/lowering substrate, not as mutable evidence.
   - Required doc candidates if implementation lands:
     - SDK rule/derivation docs for module identity and locator compatibility.
     - SDK API surface docs if any public helper is exported.
     - User guide note only if user-facing syntax changes.
     - Rule replay docs should retain the v0.1.1 boundary that evidence is read-only.
   - Notebook/demo is optional; if added, it must show module identity + replay compatibility without claiming red/green completeness.

### Step 1 — Authoring Module IR Substrate

Add a small authoring-layer module substrate that can represent a rule/derivation body as branches of condition modules. It should lower to current tuple-form `where` IR and emit a locator/module-id map. It must accept existing tuple/list authoring payloads through normalization.

### Step 2 — Replay Integration Without New Behavior

Wire the existing replay patch flow through the module-aware lowering path where possible while preserving the public v0.1.1 API and semantics. Existing `b{branch}.a{atom}` locators must continue to work.

### Step 3 — Evidence Mapping Hook

Add a shallow helper or internal hook that maps retained-candidate support artifact keys back to module ids using the lowering map. Do not expand proof trees or persist audit JSONL.

### Step 4 — Tests

Add targeted tests for:

1. tuple-form and JSON list-form atoms normalizing into module IR;
2. flat AND and OR-of-branches shapes;
3. generated id stability and non-sharing across owners;
4. lowering to tuple-form before evaluator/backend entrypoints;
5. replay backward compatibility;
6. evidence support-key-to-module mapping for native support artifacts;
7. explicit rejection of RuleRef-bound replay unless re-scoped.

### Step 5 — Docs

Update affected SDK docs and this blueprint outcome. Keep references to the rule-replay working bundle as design rationale, not current implementation truth.

### Deviations From Scoped Blueprint

- `ModuleLoweringMap` was made immutable before being exposed through `ReplayResult`.
  - This was not explicitly called out in the initial Step 3 proposal, but follows the same identity-invariant rule as immutable `ConditionModule.atom`: once a module id or mapping is computed, SDK holders must not be able to mutate the structure behind it.
- Step 2 keeps the public replay result payloads in the user's authoring shape, and only lowers internal eval payloads.
  - This preserves v0.1.1 compatibility while still proving the module-aware lowering path before evaluator/backend entrypoints.

### Why Deviations Were Accepted

Both deviations tightened correctness without expanding behavior. They do not add `disable_condition`, `param_override`, candidate universe handling, mutable evidence, RuleRef-bound replay, audit replay persistence, or cross-engine semantics.
