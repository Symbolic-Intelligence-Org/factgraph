## 0. TL;DR

86 drafts across 2 samples were reviewed by hand. Zero outright hallucinations
(`no = 0`). Strict approval rate is **11.6%**. The dominant failure class is
**semantic binding misalignment**, not structural invalidity.

The two failure modes concentrate cleanly:

1. **Document.title fabrication** — 39 / 86 drafts (`WRONG_ENTITY`). LLM
   synthesizes `Document.title` from doc_id hashes, body prose, or section
   headings instead of picking a stable identifier that appears verbatim in
   the source text.
2. **module:description overreach** — 35 / 86 drafts (`WRONG_ARG`). LLM fills
   `module:description` with checklist / acceptance / coverage items instead
   of declarative descriptions.

Iter 5's fix target is a scoped prompt iteration on the LLM's **semantic
grounding** behavior, not another structural rule. Target combined strict
approval rate: **≥40%** (from 11.6%).

## 1. Scope and method

### 1.1 What was reviewed

Two review packets generated by `generate_review_packet.py` from a single
pipeline rerun (regen run 2) on 2026-04-10. Each packet contains one
YAML-like block per `FactDraftSpec` with:

- full draft fields (`entity_type`, `entity_identity`, `pred_id`, `field_values`)
- full `ExtractionProvenance` including `raw_text`
- empty `REVIEW` block with `approve` / `reason_code` / `notes` fields

Reviewer filled in every `REVIEW` block manually.

### 1.2 Reason code taxonomy used

As defined in the review packet headers:

| code | meaning |
|---|---|
| `CORRECT` | no issue; `approve: yes` |
| `HALLUCINATED` | fact not present in `raw_text` at all |
| `OVERGENERAL` | fact in `raw_text` but too broad / vague |
| `WRONG_ENTITY` | subject entity mis-identified |
| `WRONG_PREDICATE` | relation should use a different `pred_id` |
| `WRONG_ARG` | object / `field_values` value is factually wrong |
| `DUPLICATE` | same fact as another approved draft |
| `AMBIGUOUS` | `raw_text` is genuinely ambiguous |
| `OTHER` | fill in notes |

Taxonomy was not modified during the review pass.

### 1.3 Which run this reflects

This review is based on **regen run 2** (the packet generation rerun), NOT
the archived iteration 4 run. Per OBS-01, three independent runs of the same
pipeline on the same day produced different absolute counts:

| run | medium valid | long valid | combined valid |
|---|---:|---:|---:|
| run 1 (archived iter 4) | 14 | 57 | 71 |
| **run 2 (this packet)** | **9** | **77** | **86** |
| run 3 (stability check) | 7 | 60 | 67 |

The review results are therefore best interpreted as "one sample from the
iter 4 distribution", not as "the iter 4 bundle quality". Per OBS-01 §What
this changes, the qualitative conclusions (failure modes, dominant error
classes) are stable across runs even when absolute counts are not.

**Archived iter 4 run records are intentionally NOT backfilled with these
review results.** They refer to a different in-memory bundle that no longer
exists. See [review packet variance caveats](./review_pass_2026-04-11_medium_01_security.md#variance-caveat-added-2026-04-11-read-before-reviewing)
for the full reasoning.

## 2. Aggregate metrics

### 2.1 Two complementary rates

Two summary rates are reported because they measure different things:

| rate | formula | meaning |
|---|---|---|
| **strict approval rate** | `yes / total` | proportion of drafts the reviewer would accept into the ledger **as-is**, with no editing |
| **salvageable rate** | `(yes + partial) / total` | proportion of drafts whose `raw_text` supports *some* fact, even if the specific binding is wrong |

**Iter 5 optimizes the strict rate, not the salvageable rate.** The goal is
to make the LLM emit drafts that are correct out of the box, not drafts that
could be manually fixed. Salvageable rate is reported as a floor / guardrail:
if it drops below 100% in future iterations, that signals new hallucination,
which would be a regression.

### 2.2 Per-packet metrics

| metric | medium_01_security | long_01_kernel_p0 | combined |
|---|---:|---:|---:|
| drafts | 9 | 77 | 86 |
| yes | 2 | 8 | 10 |
| partial | 7 | 69 | 76 |
| no | 0 | 0 | 0 |
| **strict approval rate** | **22.2%** | **10.4%** | **11.6%** |
| **salvageable rate** | 100% | 100% | 100% |

Strict approval is higher on medium despite the tiny sample — because both
`yes` drafts on medium are on `Module + module:description`, and medium has
proportionally more Module candidates.

## 3. Qualitative findings

### 3.1 F-01: Document.title fabrication dominates

**Observation**: On medium, 7/7 Document drafts (100%) are `partial`, all
with Document.title values that do not appear verbatim in the source text:

- 5 drafts use the opaque 16-char `doc_id` hash (`8e729d68d5deab3a`) as the title
- 1 draft synthesizes a title from body prose ("current repository-level security hygiene rules...")
- 1 draft uses a code-literal env var name (`FACTPY_KERNEL_API_KEY`) as Document title — but the env var name should have routed to a Module extraction instead (this is also counted under F-03 below)

On long, 34/36 Document drafts are `partial` for analogous reasons.

**Interpretation**: The LLM has no stable source for `title:string` because
the schema's `Document` entity is under-specified for corpus documents that
do not begin with a "Title: X" line. When forced to produce a title, the LLM
falls back to the most-stable-available identifier (doc_id hash), fabricates
one from body content, or misroutes a code-literal into the wrong entity type.

**Positive evidence** (2 drafts): On long, 2 Document drafts are `yes`
(#063, #064). Both use a **stable identifier that appears verbatim in the
source segment** — `SECURITY.md` and `KP0-04`. This confirms the LLM is
capable of correct Document.title extraction when the source provides a
self-referential name; it just only does so ~6% of the time without
explicit guidance.

### 3.2 F-02: `module:description` overreach dominates on long

**Observation**: On long, 35/41 Module drafts are `partial` with
`reason_code=WRONG_ARG`. The Module identity is usually correct (clean
code-literal: function name, class name, test name), but the
`module:description` value is drawn from checklists, acceptance bullets,
coverage items, or plan headings instead of a declarative description of
what the module does.

**Interpretation**: The `module:description` predicate is permissive — it
accepts any string, and the LLM interprets it as "any textual context
associated with the module name". When the surrounding segment contains a
task list or acceptance criteria (common in blueprint-style documents like
long_01_kernel_p0), the LLM fills the description with task text.

**Positive evidence** (6 drafts): Module + `module:description` successfully
extracts when the surrounding text is a declarative noun-phrase description.
Medium's 2 CORRECT drafts (`FACTPY_KERNEL_API_KEYS`, `FACTPY_KERNEL_AUTH_DISABLED`)
and long's 6 CORRECT Module drafts (`HttpRuntimeAPI`, `test_service_auth`,
`test_service_app_v1_auth`, `test_agent_http_runtime_api_auth`,
`test_ledger_concurrency`, `test_ledger_close`) all share this shape:
declarative text that describes what the module **is** or **does**, not
what someone plans to do to it.

### 3.3 F-03: Entity/predicate routing failures collapse into single-code reports

**Observation**: Some drafts are wrong on multiple axes simultaneously
(e.g., medium draft #008: `FACTPY_KERNEL_API_KEY` wrapped as
`Document(title=FACTPY_KERNEL_API_KEY) + document:mentions`, when it should
be `Module(module_name=FACTPY_KERNEL_API_KEY) + module:description`). The
reason code taxonomy forces a single category per draft, and draft #008 was
tagged `WRONG_PREDICATE` rather than `WRONG_ENTITY + WRONG_PREDICATE`.

**Interpretation**: The 2 `WRONG_PREDICATE` counts in §2.3 understate the
entity/predicate routing failure class. A more precise recount would merge
`WRONG_ENTITY + WRONG_PREDICATE` into a single "routing failure" bucket.
Under that re-classification, routing failures account for ~54% of all
failures (39 + 2 = 41 out of 76), and `WRONG_ARG` accounts for 46%.

**Implication for iter 5**: The reason code taxonomy is functional for this
review pass but should be revisited if the semantic grounding fix surfaces
new dual-axis failures. Not a blocker for iter 5.

### 3.4 F-04: Failure clustering is clean by entity type

| axis | medium | long |
|---|---|---|
| Document drafts fail on | WRONG_ENTITY (fabricated title) | WRONG_ENTITY (fabricated title) |
| Module drafts fail on | n/a (0 failures) | WRONG_ARG (description overreach) |

These are two **independent** failure modes with no overlap. Iter 5 needs
two examples — one per failure mode — and neither is collaterally covered
by the other.

## 4. What is NOT a problem

### 4.1 Zero hallucination

All 86 drafts are grounded in real source text. Reviewer did not mark any
draft `no` and did not use the `HALLUCINATED` reason code. The LLM is citing
real content; it is just binding that content to the wrong entity / predicate
shape. This is an important boundary: the structural fixes from iter 2–4
plus the current prompt template are strong enough to prevent the LLM from
fabricating out of thin air.

### 4.2 Structural validity unchanged from iter 4

Pattern A (subject leakage, `got 2, expected 1`) remains the only structural
rejection shape across all three runs in §1.3. The review packets only
contain drafts that passed structural validation — structural validity is
independent of semantic correctness. Iter 5 does not need to re-derive the
structural layer.

### 4.3 Zero entity-type or predicate-ID unknown errors

Neither sample produced any `schema_entity_type_unknown` or
`schema_pred_id_unknown` rejections. The LLM correctly uses only the two
entity types and two predicates defined in `test_schema_ir.json`. The
misroutings are between *those same two types*, not into invented ones.

### 4.4 Pattern A residual is unchanged

OBS-01 §What IS stable confirms that the rejection shape distribution is
identical across all three runs. This review pass does not exacerbate
Pattern A; it does not interact with it. The two concerns are orthogonal.

### 4.5 No variance-related review ambiguity

None of the per-draft REVIEW decisions depend on count reproducibility.
Every decision is a per-draft semantic judgment on whether the LLM's
output is correct for the raw_text it cites. The variance caveat from
OBS-01 does not affect the validity of the review findings.

## 5. Implication for iter 5

Iter 5 is a scoped prompt iteration targeting semantic grounding. See the
companion blueprint:

- [2026-04-11_agent-extraction-prompt-semantic-grounding.md](../../../blueprints/active/2026-04-11_agent-extraction-prompt-semantic-grounding.md)

The blueprint is framed as **positive grounding** + **emit nothing when
grounding is weak**, not as purely prohibitive rules. It adds two
wrong/right pairs to `SYSTEM_PROMPT_TEMPLATE`:

- Document title grounding example: title must be a stable identifier that
  appears **verbatim** in source text
- `module:description` narrowing example: description must be a
  **declarative description**, not a plan / checklist / test expectation /
  coverage label

### Target metrics for iter 5

| metric | current | iter 5 target | notes |
|---|---:|---:|---|
| combined strict approval rate | **11.6%** | **≥40%** | this is the optimization target |
| combined salvageable rate | 100% | ≥95% | guardrail — must not regress (no new hallucination) |
| Module strict rate | 18.6% | ≥50% | WRONG_ARG narrowing |
| Document strict rate | 4.6% | ≥25% | title grounding |
| Pattern A rejection shape | dominant residual | unchanged | iter 5 does not touch structural layer |
| absolute proposal volume | 86 (regen run 2) | **may decrease** | LLM learning to emit nothing in weak cases is expected; not a regression |

**Decrease in absolute proposal volume is expected and not a regression.**
If iter 5 drops Document proposals from 43 to, say, 20 and the strict
approval rate on Document jumps from 4.6% to 50%, that is a pure win even
though the total count is lower.

### Why 40% and not 90%

Iter 4 used a 90% structural target and missed it (real value ~72% per
OBS-01). Iter 5's 40% target is calibrated against two constraints:

1. **Semantic correctness is fundamentally harder than structural correctness.**
   A structural fix can be deterministic (rules 7–10 and the iter 4 examples
   give exact patterns). A semantic fix relies on the LLM's text-level
   judgment about what "verbatim stable identifier" means in a specific
   source segment.
2. **11.6% → 40% is already a ~3.5× improvement** and is a meaningful upper
   bound for a scoped prompt-only iteration. Pushing past 40% may require
   schema changes (new entity types for Repo, File, EnvVar, etc.) that are
   explicitly out of iter 5 scope.

## 6. Known limitations

1. **Sample size**: n=86 drafts across only 2 documents. Not enough to
   report per-reason-code confidence intervals. Directional findings
   (Module ≠ Document in approval rate, two dominant failure codes) are
   robust; exact percentages should be interpreted as ±5pp.
2. **Single review pass**: one reviewer, single pass. Inter-rater
   reliability on semantic judgments is unmeasured. For now, the reviewer's
   reason-code discipline is the source of truth.
3. **Reason code taxonomy forces single category**: dual-axis failures
   (e.g., draft #008's simultaneous `WRONG_ENTITY` + `WRONG_PREDICATE`)
   collapse into whichever code the reviewer picked. See F-03 above.
4. **Regen run 2 is a variance sample**: as noted in §1.3 and the variance
   caveats, this review reflects one point in the iter 4 distribution, not
   the archived iter 4 bundle.
5. **Provisional schema**: `test_schema_ir.json` is explicitly non-canonical
   and under-specified. Iter 5's prompt iteration compensates for some
   under-specification but cannot fix all of it. Schema expansion is a
   separate, deferred concern.
6. **`module:description` as a predicate name may itself be too loose.**
   The review surfaced that `module:description` catches checklist items
   because the name is inviting. A canonical schema might decompose this
   into `module:purpose`, `module:responsibility`, and
   `module:operational_expectation` as separate predicates. This is out of
   iter 5 scope but worth filing as a future observation.
