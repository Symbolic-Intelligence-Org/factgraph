# 商业领域 Agentic 文档事实提取调研报告

> 调研日期：2026年4月  
> 聚焦领域：知识图谱 / 图数据库驱动的文档事实提取  
> 评估维度：成本、速度、上下文连续性、提取可靠性

---

## 一、行业概览与定义边界

### 1.1 什么是 Agentic 文档提取 (ADE)

Agentic Document Extraction 是对传统 OCR 和 IDP（智能文档处理）的根本性升级。其核心特征在于：

- **自主决策**：系统能根据文档类型、结构复杂度自动选择处理策略，而非依赖预设模板
- **多步推理**：跨段落、跨文档的实体消歧和关系推断，而非孤立的字段提取
- **状态维持**：Agent 在处理流程中维护上下文状态，支持复杂的业务工作流（如合同审查→合规核对→风险建议）
- **结构化输出**：产出知识图谱三元组 (Entity-Relation-Entity)、JSON Schema 实例、或图数据库记录

与传统 RAG 的关键区别在于：RAG 专注于"检索+生成回答"，而 ADE 专注于"理解+结构化表征+驱动行动"。LlamaIndex 在 2025 年初正式提出 Agentic Document Workflows (ADW) 架构，将文档处理、检索、结构化输出和 Agent 编排统一为端到端系统。

### 1.2 文档类型覆盖与应用分布

根据调研，当前 ADE 技术在以下领域的商业应用最为集中（按采纳广度排序）：

| 排名 | 行业 | 典型文档类型 | 核心诉求 |
|------|------|------------|---------|
| 1 | **金融/保险** | 合同、保单、财报、KYC 文件 | 合规提取、风险评估、欺诈检测 |
| 2 | **法律** | 合同、案例法、监管文件 | 条款交叉引用、义务追踪、合规间隙识别 |
| 3 | **医疗健康** | 临床笔记、诊断报告、临床试验 | EHR 自动更新、药物交互分析、精准医疗 |
| 4 | **企业知识管理** | 内部文档、邮件、会议记录 | 知识发现、专家定位、组织记忆 |
| 5 | **制造/供应链** | 规格书、质检报告、供应商文件 | 供应链可见性、合规追踪 |

金融和法律领域是最大的采纳者，因为这些领域的文档天然具有高度的实体互联性、合规要求严格且错误成本极高。

## 二、技术架构全景

### 2.1 端到端管线架构

一个完整的 Agentic 文档事实提取管线通常包含以下层次：

```
文档输入 → [文档解析层] → [实体/关系提取层] → [图构建层] → [图存储/查询层] → [Agent 编排层]
   │              │                │                │                │                │
   │         LlamaParse       GraphRAG          Leiden算法        Neo4j/FalkorDB    LangChain
   │         Unstructured     LLM Extraction    社区检测          向量数据库         LlamaIndex
   │         Docling          NER+RE Pipeline   实体消歧          混合索引          自定义Agent
   │         Reducto          Schema约束提取     共指消解
   │         Mistral OCR
```

### 2.2 三大技术范式

#### 范式 A：LLM-Native 全托管提取（如 Microsoft GraphRAG）

LLM 直接完成实体识别、关系抽取、描述生成的全部工作。利用 Leiden 算法做社区检测，生成层级摘要。

- **优点**：无需训练数据，开箱即用，支持任意领域
- **缺点**：索引成本极高（大规模数据集曾达 $33K），对 LLM 输出的一致性高度依赖
- **代表**：Microsoft GraphRAG, LightRAG, Fast-GraphRAG

#### 范式 B：框架驱动的模块化管线（如 LlamaIndex Property Graph）

通过可组合的提取器（SimpleLLMPathExtractor, SchemaLLMPathExtractor, DynamicLLMPathExtractor）从文档中逐块提取三元组，存入图数据库。

- **优点**：模块可替换（换 LLM、换图数据库、换提取策略），支持 Schema 约束
- **缺点**：需要工程投入来组装管线，各模块间的错误会级联放大
- **代表**：LlamaIndex + Neo4j, LangChain + 图数据库, Cognee

#### 范式 C：预构建知识图谱 + 实时增量（如 Diffbot）

通过持续爬取公开网络，维护一个超大规模的预构建知识图谱（Diffbot 声称 200 亿+实体，1 万亿+事实），用户查询时进行图检索增强生成。

- **优点**：无需用户自行构建 KG，数据每 3-5 天刷新，适合公开信息领域
- **缺点**：不适用于私有/内部文档，定制化受限，信用制定价在大规模使用时成本陡增
- **代表**：Diffbot Knowledge Graph, Google Knowledge Graph

## 三、商业参数深度对比

### 3.1 成本分析

#### 3.1.1 图索引构建成本

| 方案 | 500页语料库成本 | 大规模数据集成本 | 成本构成 |
|------|----------------|-----------------|---------|
| **Microsoft GraphRAG（原版）** | $50-200 | 曾达$33,000 | 58% 花在实体提取的 LLM 调用 |
| **LazyGraphRAG** | 与向量 RAG 相当（~$2-5） | 原版的 0.1% | 延迟 LLM 使用，按需计算 |
| **LightRAG** | ~$0.50 | 显著低于 GraphRAG | 去除社区摘要层，轻量管线 |
| **标准向量 RAG** | $2-5 | $2-5 | 仅 embedding 成本 |
| **LlamaIndex + Neo4j** | $20-100（取决于 LLM） | 随文档线性增长 | LLM 提取 + 图数据库托管 |

**关键洞察**：GraphRAG 原版的成本瓶颈在于"每个文档分块都必须经过 LLM 做实体提取"。2025 年 6 月微软发布的 LazyGraphRAG 将索引成本降至原版的 0.1%，同时在多数基准测试中维持了相当的质量。2025 年 1 月的动态社区选择更新也将 token 使用减少了 79%。

### 3.3 上下文连续性

这是 Agentic 文档提取中最被低估但最关键的维度之一。

#### 3.3.1 跨文档实体消歧

| 方法 | 实现机制 | 效果 |
|------|---------|------|
| **Schema 约束提取** | LlamaIndex SchemaLLMPathExtractor 预定义实体/关系类型 | 可控性高，但需要领域专家预定义 schema |
| **Gleaning（多遍提取）** | LightRAG 的重试机制，使用更激进的 prompt 强制补全遗漏 | 实测可捕获首次提取遗漏的实体 |
| **社区检测 + 层级摘要** | GraphRAG Leiden 算法分层聚类 | 支持从高层主题到低层细节的多粒度理解 |
| **Ontology 驱动校验** | 企业 KG 中的本体规则（如"每个 Employee 必须关联 Department"） | 自动捕获不一致性，但构建成本高 |
| **时序知识图谱** | Zep Graphiti 框架：每个事实带时间戳，矛盾事实建立 supersedes 关系 | 适合 Agent 记忆场景，支持时间感知检索 |

#### 3.3.2 上下文窗口 vs 图结构

| 特性 | 长上下文窗口（如 1M token） | 图结构 |
|------|---------------------------|--------|
| 局部事实查找 | 表现与 GraphRAG 竞争力相当 | 无明显优势 |
| 多跳推理 | 随跳数增加快速退化 | 核心优势，准确率提升 35-90% |
| 全局摘要 | 受限于注意力机制的局限性 | GraphRAG 在综合性和多样性上 70-80% 胜率 |
| 成本效率 | 每次查询消耗大量 token | 索引一次，查询廉价 |

微软的实验表明，即使对比 1M token 上下文窗口的向量 RAG（使用 GPT-4.1），LazyGraphRAG 在所有对比中仍然获得更高的胜率。

### 3.4 提取可靠性

#### 3.4.1 准确率基准

| 方案 | 基准 | 准确率/胜率 | 对照组 |
|------|------|-----------|--------|
| **GraphRAG** | Microsoft 内部评估 | 72-83% 综合性 | vs 传统 RAG |
| **GraphRAG** | Lettria/AWS 评估（2024.12） | 80% vs 50% | vs 传统 RAG（复杂文档） |
| **Diffbot GraphRAG LLM** | FreshQA | 81% 准确率 | 超过 ChatGPT 和 Gemini |
| **GraphRAG** | Diffbot KG-LM Benchmark | 3.4x 准确率提升 | 企业场景 |
| **图检索** | HotpotQA 多跳问题 | 推理深度提升 4.5% | 但延迟增加 2.3x |

#### 3.4.2 幻觉与可靠性挑战

LLM 驱动的 KG 提取面临的核心可靠性问题：

1. **提取幻觉**：LLM 可能"发明"原文中不存在的实体或关系。研究表明约 90% 的医学实体消歧可以成功，但约 2% 的作者名存在歧义性问题
2. **Schema 漂移**：长文档或批量处理时，LLM 对实体类型和关系类型的命名可能不一致
3. **遗漏问题**：密集文本中，首次提取可能遗漏关键实体。LightRAG 的 gleaning 机制通过多遍提取来缓解
4. **跨文档不一致**：同一实体在不同文档中可能以不同名称出现（如 "IBM" vs "国际商业机器公司"）

#### 3.4.3 缓解策略

| 策略 | 机制 | 效果 |
|------|------|------|
| **KG 增强 RAG** | 用已有 KG 约束 LLM 输出 | 幻觉率降低约 60% |
| **Schema 约束提取** | Pydantic 模型 + 结构化输出验证 | 显著提升一致性 |
| **多遍提取 (Gleaning)** | 多次 LLM 调用 + 差异补全 | 提高召回率但增加成本 |
| **本体驱动校验** | 规则引擎检查提取结果的合规性 | 企业级质量保证 |
| **人工审核回路 (HITL)** | 低置信度结果交人工处理 | 最终防线，适用于高风险场景 |
| **GraphEval 框架** | 将 LLM 输出表示为 KG 结构做三元组级验证 | 在幻觉基准上改善了平衡准确率 |

### 6.5 核心结论：ADE 已经是标配了吗？

**分层回答**：

**在图数据库/KG 平台层面——是的，已经或正在成为标配。** 所有主要图数据库公司（Neo4j、Stardog、Ontotext、FalkorDB）都已在 2024-2025 年将 LLM 驱动的文档提取集成到产品中。Neo4j 的 LLM Knowledge Graph Builder 已成为其用户增长的重要入口。Stardog 的 BITES+Voicebox 将其从"语义数据库"重新定位为"AI 知识Agent 平台"。这不是可选附加功能——它正在成为图平台竞争的**准入门槛**。

**在企业应用层面——正处于从"早期采纳"到"早期多数"的过渡期。** Mordor Intelligence 的市场报告将 Neo4j、TigerGraph、Stardog 列为 Agentic AI + KG 市场的关键玩家，并指出全球银行在 GraphRAG 替代传统文档检索后合规审查时间缩短 40%。但大规模的、具名的生产案例仍然有限——多数证据来自供应商自报或匿名案例。Gartner 预测图技术将在 2025 年用于 80% 的数据和分析创新中（从 2021 年的 10% 上升），这个预测可能过于激进，但趋势方向是明确的。

**在"完全自主、零人工干预"层面——还没有。** 即使是最先进的系统（如 Docugami、Stardog Voicebox），仍然强调人工审核回路（HITL）。Ontotext 的产品哲学尤其强调"不是消灭 LLM，而是明智地在少数查询中使用 LLM"。高风险场景（医疗、法律、金融合规）中，完全无人值守的 ADE 尚不被接受。

**总结一句话**：**ADE 作为产品能力已是标配；作为企业部署正在快速攀升；但作为"零干预自治系统"仍处于早期。**

## 七、实施建议与决策框架

### 7.1 分阶段实施路径

**阶段 1：图增强向量 RAG（最简方案）**

保留现有向量 RAG 管线，增加图元数据作为过滤器或重排器。无需 LLM 做实体提取，从已有结构化数据（CRM、产品库、组织结构）构建简单图。成本仅为图数据库本身（Neo4j CE 免费，托管服务~$65/月起）。

**阶段 2：图引导检索（触发条件：用户频繁需要跨文档连接信息）**

引入 LLM 驱动的实体提取，构建知识图谱。推荐 LightRAG 或 LlamaIndex Property Graph 作为起点。成本主要在 LLM API 调用。

**阶段 3：全 GraphRAG + Agentic 工作流（触发条件：需要全局摘要和复杂推理）**

部署完整的 GraphRAG 管线或迁移到 LazyGraphRAG。引入 Agent 编排层，支持多步业务流程自动化。

### 7.2 何时不应使用 GraphRAG

- 简单事实查找和 FAQ 类问答 → 向量 RAG 足够
- 文档间低互联性（如独立产品手册集合） → 图结构收益有限
- 对延迟极敏感的实时场景 → 图检索引入约 2.3x 额外延迟
- 预算极其有限 → 从 LazyGraphRAG 或 LightRAG 开始

### 7.3 成本优化策略

1. **混合模型策略**：用强力模型（GPT-4/Gemini Pro）做实体提取，用轻量模型（Llama 3 8B/本地 Ollama）做查询应答，可节省 60-80% 推理成本
2. **LazyGraphRAG**：将索引成本降至全 GraphRAG 的 0.1%，同时通过相关性测试预算控制质量-成本平衡
3. **增量更新**：避免全量重建 KG，仅处理新增/变更文档
4. **Schema 预定义**：减少 LLM 在实体类型推断上的 token 消耗
5. **缓存**：LlamaParse 已解析文件仅需支付 split 成本

## 八·五、CTO 视角：产品设计建议与未被充分讨论的维度

> 以下内容跳出技术方案对比，聚焦于一个在此领域构建产品的 CTO 应当关注但行业报告常忽略的维度。

### 8.5.1 Build vs Buy：被低估的工程成本真相

行业中最常见的误判是"用开源框架搭一个管线很快"。实际数据揭示了不同的画面：

**自建管线的隐性成本清单**

| 成本项 | 典型耗时/费用 | 备注 |
|--------|-------------|------|
| 管线原型搭建 | 1-2 周 | LangChain/LlamaIndex 上手确实快 |
| Schema 设计与迭代 | 2-4 周 | 需要领域专家深度参与 |
| 提取质量调优 | 4-8 周 | 最耗时环节——prompt 工程、gleaning 策略、实体消歧规则 |
| 合规基础设施 | 4-12 周 | SOC 2/HIPAA/GDPR 认证不是"配置一下"的事 |
| 用户画像/权限系统 | 2-4 周 | 多租户场景下的数据隔离 |
| 生产监控与告警 | 2-3 周 | token 用量、提取质量漂移、图谱健康度 |
| **总计（到生产可用）** | **3-8 个月** | 不含持续维护 |

**关键发现**：SAP 的研究团队提出了一个值得关注的替代路径——基于依赖解析（SpaCy）的图构建管线，完全不依赖 LLM，却达到了 LLM 方案 94% 的性能（61.87% vs 65.83%）。对于成本敏感或数据隐私要求极高的场景，这种"无 LLM"路径可能是更务实的起点。

**CTO 决策框架**：

- **< 100 文档**：直接用 LLM API + Neo4j LLM KG Builder 手动验证，无需框架
- **100-1500 文档**：LlamaIndex/LangChain + 定制 prompt + 人工抽检
- **> 1500 文档/月持续处理**：需要认真评估 Buy（商业方案如 Unstructured、LlamaParse、Docugami）vs Build（自建管线 + 微调小模型）。此规模下 LightRAG 的 token 节省（65-80%）开始产生显著经济意义

### 8.5.2 提取质量的持续监控——图谱会"腐烂"

这是最容易被忽视的产品设计维度。**知识图谱不是构建一次就完成的静态资产——它会腐烂。**

**图谱质量退化的三种模式**：

1. **Schema 漂移**：随着新文档类型进入管线，LLM 开始生成 schema 中未预期的实体类型或关系类型，导致图谱逐渐失去一致性
2. **实体膨胀**：同一实体因表述不同被多次创建（"IBM" / "国际商业机器" / "IBM Corp."），图谱噪声随时间增长
3. **事实过期**：提取的事实随源文档更新而失效，但图谱中没有时间标记或版本机制来反映这一点

**产品设计建议——监控仪表板应包含的指标**：

| 指标 | 定义 | 告警阈值（参考） |
|------|------|----------------|
| 每文档实体提取数量 | 平均值和方差 | 偏离基线 >30% |
| Schema 一致性率 | 提取的实体/关系类型落入预定义 schema 的比例 | < 90% |
| 实体去重命中率 | 实体消解识别出的重复比例 | 突然升高可能暗示提取质量下降 |
| 每千 token 成本 | 含所有 LLM 调用 | 超出预算 20% |
| 平均置信度评分 | LLM 自报的提取置信度（如有） | 趋势性下降 |
| 处理延迟 p95 | 端到端文档处理时间 | 超过 SLA |

### 8.5.3 溯源与可审计性：被忽视的杀手级特性

在金融、法律、医疗等受监管行业，**"这个事实从哪里来？"不是一个锦上添花的功能，而是准入门槛**。

**溯源的三个层次**：

1. **文档级溯源**：每个提取的三元组链接回源文档（基本要求，大多数系统已支持）
2. **段落/页面级溯源**：精确到源文档的第几页第几段（LlamaParse 的 bounding box、Reducto 的 citation helper 支持此功能）
3. **推理链溯源**：从最终答案 → 使用的 claim → 支撑证据 → 源文档的完整路径（W3C PROV 标准，`wasDerivedFrom`/`used`/`wasAssociatedWith` 关系）

**产品设计建议**：

- 将每个提取的三元组存储在**命名图（Named Graph）**中，命名图 IRI 对应源文档——Stardog BITES 和多数 RDF 存储原生支持此模式
- 对提取结果附加**置信度分数**和**提取方法元数据**（哪个模型、什么版本、什么 prompt）
- 在用户界面中实现"点击事实 → 高亮源文档原文"的交互——这是将 AI 提取从"黑箱"变为"可信赖工具"的关键 UX
- 对于多源聚合的事实，记录"证据集合"而非单一来源——学术界的纳米出版物（Nanopublication）模型提供了参考框架

### 8.5.4 人机协作回路（HITL）的 UX 设计

当前行业共识是高风险场景需要人工审核，但**审核界面的设计质量直接决定了系统的实际吞吐量和采纳率**。

**常见的 HITL 反模式**：

- **反模式 1：全量审核** — 让人类审核 LLM 提取的每一个三元组。结果：审核者疲劳，效率低于手动提取
- **反模式 2：二元判断** — 只提供"对/错"选项，不提供修正路径。结果：标注数据无法用于改进管线
- **反模式 3：脱离上下文** — 展示提取的三元组但不显示源文本。结果：审核者需要回到原文档，流程断裂

**推荐设计模式**：

- **基于置信度的分流**：高置信度三元组自动入库；中置信度进入审核队列；低置信度标记为"需验证"或丢弃
- **对比视图**：左侧源文档（高亮提取位置），右侧提取结果（支持编辑），中间显示置信度
- **审核即训练数据**：将人工修正自动反馈为 few-shot 示例，持续改进提取 prompt
- **批量审核模式**：按实体类型或关系类型聚合，支持"同意这一类的所有提取"操作

Ontotext Metadata Studio 3.9 的"关联标注高亮"功能和 Stardog Voicebox 的 LLM 驱动实体消解提供了部分参考实现。

### 8.5.5 Schema 演化与本体版本管理

业务在变，文档类型在变，提取 schema 也必须跟着变。但图谱不能每次 schema 变更就全量重建。

**Schema 演化的三种策略**：

| 策略 | 适用场景 | 风险 |
|------|---------|------|
| **向前兼容**（只增不删） | 新增实体/关系类型，不影响已有数据 | 图谱会逐渐"臃肿"，包含历史遗留类型 |
| **版本化 schema**（多版本共存） | 法规变更导致 schema 大改 | 跨版本查询复杂度增加 |
| **增量迁移**（自动化批量更新） | 实体类型重命名、合并 | 需要精确的实体映射规则，一旦出错影响面大 |

**产品设计建议**：

- 将 schema 本身存储为图谱的一部分（元本体），支持版本控制
- 使用 SHACL 或等效约束机制做数据形状校验，在写入时拒绝违规三元组
- 提供"schema diff"工具——可视化两个版本之间的变更，预估影响范围
- Stardog 的 Voicebox 已支持用自然语言指令来修改 KG 模型，这代表了一种低门槛的 schema 演化路径

### 8.5.6 小模型/本地部署：隐私-成本-延迟三角

对于金融、医疗、政府等数据不出域的场景，"把文档发给 GPT-4 API"根本不是选项。

**本地/小模型方案的现实**：

| 方案 | 提取质量 | 硬件需求 | 延迟 | 成本模型 |
|------|---------|---------|------|---------|
| GPT-4/Claude (云API) | 最优基线 | 无 | 中（网络延迟）| 按 token |
| Llama 3 70B (本地) | 接近 GPT-4 | 2x H100 | 低 | 固定硬件成本 |
| Llama 3 8B (本地) | 中等，需要定制 | 1x A100 | 极低 | 低固定成本 |
| SpaCy 依赖解析（无 LLM）| LLM 的 94% | CPU 即可 | 极低 | 几乎为零 |
| 混合模式（本地小模型提取 + 云端大模型校验）| 接近最优 | 1x A100 | 中 | 大幅节省 |

Diffbot 的开源 GraphRAG LLM（基于 Llama 3.3）在 8B 参数版本上仅需单张 A100，70B 版本需 2x H100，提供了一个可本地部署的参考实现。

**产品设计建议**：支持**"模型热插拔"架构**——提取层和推理层使用不同模型（如 FalkorDB GraphRAG-SDK 和 Cognee 已支持多后端），允许客户根据数据敏感性选择本地或云端处理路径。

---



### 8.2 未解决的挑战

- **实体消歧的可扩展性**：当 KG 节点达到百万级，实体匹配和去重仍是工程瓶颈
- **图的持续维护**：KG 不是"构建一次就完成"的——它需要随源数据演变持续更新
- **评估标准化**：目前缺乏统一的行业基准来公平比较不同 GraphRAG 方案在真实企业数据上的表现
- **可解释性**：虽然图路径天然提供推理链，但 LLM 生成环节的透明度仍需提升

---

## 九、结论

Agentic 文档事实提取正处于从实验走向生产的关键转折点。知识图谱作为结构化表征层，在多跳推理、全局理解和上下文连续性上提供了向量 RAG 无法替代的能力。

**核心判断**：

1. **成本不再是阻碍因素**——LazyGraphRAG 和 LightRAG 已将图索引成本降至与向量 RAG 可比的水平
2. **"一刀切"不存在**——最佳方案高度取决于文档互联性、查询复杂度和合规要求
3. **混合架构是主流方向**——纯图或纯向量都不是最优解，图+向量+属性的混合检索是生产系统的共识
4. **文档解析层是隐藏瓶颈**——即使后端 GraphRAG 再强，如果前端解析丢失了表格或结构信息，整个管线的质量上限就被锁死
5. **ROI 已经可量化**——行业报告显示知识图谱驱动的系统实现了 300-320% 的投资回报率，尤其在金融、医疗和制造领域

对于计划落地的团队，建议从"图增强向量 RAG"起步，在验证了关系推理的价值后，再渐进式地升级到完整的 GraphRAG + Agentic 工作流架构。

## 附录 B：ADE 系统全栈技术选型手册

> 本附录为计划构建 ADE 系统的 CTO 提供逐层的工具/框架/设计理念选型指南。

### B.1 第一层：文档摄入与分块（Ingestion & Chunking）

#### B.1.1 文档解析工具（已在正文第五章覆盖，此处补充选型矩阵）

| 场景 | 推荐工具 | 理由 |
|------|---------|------|
| 快速原型 | LlamaParse（云） | 6秒/文档，无需 GPU |
| 开源优先+复杂表格 | Docling（IBM 开源） | 复杂表格 97.9% 准确率，MIT 协议 |
| 企业合规（HIPAA/SOC 2） | Unstructured / Reducto | 原生合规认证，VPC 部署 |
| 多模态（手写+图表） | Gemini 2.5 Pro / Reducto | VLM 原生理解布局 |
| 自托管+最大控制 | Docling + Tesseract + 自定义后处理 | 需要工程投入但完全可控 |

#### B.1.2 分块策略选型

分块是整个管线中**投入产出比最高的优化点**。

| 策略 | 检索准确率提升 | 计算成本 | 最佳适用 |
|------|-------------|---------|---------|
| **递归分块**（400-512 tokens, 10-20% overlap） | 基线（88-89.5% recall） | 极低 | **默认首选**——手册、文档、网页 |
| **语义分块** | 比递归高约 9%（可达 91.9%） | 高（每句需 embedding） | 知识库、技术文档 |
| **结构感知分块** | 显著 | 低 | Markdown/HTML/有明确标题的文档 |
| **Agentic 分块** | 最高（87% vs 13% baseline*） | 极高 | 高价值复杂文档（法律合同、临床指南） |
| **Late Chunking** | 改善代词/交叉引用问题 | 中 | 上下文频繁跨段落引用的文档 |
| **Proposition 分块** | 精确事实检索 | 高 | 需要原子级事实提取的场景 |

*MDPI Bioengineering 2025 同行评审研究数据

**设计理念建议**：不要只选一种——生产系统应采用**层级分块**：先用结构感知分块保留文档层级，再在每个结构块内部用递归/语义分块切分。工具推荐：LangChain `RecursiveCharacterTextSplitter`（默认）、LlamaIndex `NodeParser`、独立库 `chonkie`。

**2026 新趋势**：
- **Contextual Retrieval**：在 embedding 前为每个 chunk 添加上下文摘要（标题路径 + 简要描述），使 chunk 自解释
- **Late Chunking**：先 embedding 整个文档，再切分——解决代词和交叉引用丢失语境的问题
- **Context Cliff 效应**：Chroma 2025.7 研究发现检索性能在~2,500 tokens 后开始退化，即使是 GPT-4.1/Claude 4/Gemini 2.5 也不例外

### B.2 第二层：结构化输出与提取引擎（Structured Output & Extraction）

这是管线的"大脑"——决定了提取质量的上限。

#### B.2.1 结构化输出框架

| 框架 | 方法论 | 语言支持 | 核心优势 | 最佳场景 |
|------|--------|---------|---------|---------|
| **Instructor** | 后验证+重试（Pydantic 校验 → 失败则带错误信息重新请求 LLM） | Python, TS, Go, Ruby | 零样板代码，300万+月下载，与任何 LLM 提供商兼容 | **默认首选**——快速提取、原型到生产 |
| **BAML** (BoundaryML) | 专用 DSL 定义 schema+prompt，编译时类型检查，Schema Aligned Parsing 恢复畸形输出 | Python, TS, Go, Ruby 等（代码生成） | Schema 与 prompt 共存防止漂移；可恢复 markdown 包裹的 JSON 和思维链输出 | 分布式系统、多语言团队、严格类型安全 |
| **PydanticAI** | Pydantic 团队官方 Agent 运行时，含类型化工具、可重放数据集、生产仪表板 | Python | Agent + 结构化输出一体化；内置可观测性 | Python Agent 架构，需要超越纯提取的工作流 |
| **Outlines** | 约束解码（FSM token masking），在生成过程中阻止无效 token | Python（需控制 token 生成） | **物理上不可能**产生不合法输出；零重试开销 | 自托管模型（vLLM, llama.cpp）、高吞吐生产 |
| **XGrammar** | 运行时约束（类似 Outlines 但更底层） | 多语言 | 极致效率 | 推理引擎深度集成 |

**关键设计决策**：Cognee（认知记忆框架）已原生支持 Instructor（默认）和 BAML 两种后端可切换——这验证了"结构化输出框架应被视为可替换组件"的设计理念。

**CTO 建议**：原型阶段用 Instructor（最低门槛），生产阶段评估 BAML（schema-prompt 共存防漂移是其独特价值），自托管模型场景用 Outlines（零重试 = 零浪费 token）。

#### B.2.2 提取引擎架构模式

| 模式 | 技术 | 成本 | 质量 | 适用规模 |
|------|------|------|------|---------|
| **纯 LLM 提取** | GPT-4/Claude + Instructor/BAML | 高（按 token 计费） | 最优 | < 1,500 文档 |
| **纯 NLP 提取** | SpaCy NER + REBEL 关系提取 + 依赖解析 | 极低（CPU 即可） | LLM 的 94%（SAP 验证） | 无限（计算是瓶颈，非成本） |
| **混合级联提取** | SpaCy 初筛 + LLM 精炼边界情况 | 中低 | 接近纯 LLM | > 1,500 文档/月的持续管线 |
| **微调小模型提取** | 微调 Llama 3 8B + 领域数据 | 一次性训练成本 + 低推理成本 | 依领域数据质量而定 | 固定领域+大规模 |

### B.3 第三层：实体消解（Entity Resolution）

这是 KG 质量的**最大单点瓶颈**。LLM 越擅长提取，产生的重复实体就越多。

#### B.3.1 级联消解架构（推荐）

```
Tier 1: 确定性规则匹配（覆盖 ~40% 决策）
  → 税号/ID 精确匹配、明确非匹配排除
  → 成本：近零 | 延迟：亚毫秒

Tier 2: ML 概率匹配（覆盖 ~55% 决策）
  → 预训练模型（DITTO, Magellan）或嵌入相似度
  → 高置信度匹配/非匹配自动处理
  → 成本：低 | 延迟：毫秒级

Tier 3: LLM 语义匹配（覆盖 ~5% 边缘情况）
  → 仅对 Tier 2 不确定的案例调用 LLM
  → 成本：仅对最难的 5% 使用昂贵 LLM
  → 延迟：秒级（可接受，因为只处理小部分）
```

#### B.3.2 工具选型

| 工具 | 类型 | 适用规模 | 核心特性 |
|------|------|---------|---------|
| **Dedupe.io** | 开源 (MIT) | < 100 万记录 | 主动学习，Python 原生，快速原型 |
| **splink** | 开源 (MIT) | 千万级+ | Spark/DuckDB，Fellegi-Sunter 概率匹配 |
| **Zingg** | 开源 (AGPL) | 亿级+ | Spark 原生，ML 阻塞 |
| **Senzing** | 商业（免费 10 万记录） | 无限 | 实时 ER，关系感知，MCP Server 集成，解释性最强 |
| **LLM 语义 ER** | 自建 | 依赖 LLM 成本 | 用 BAML/Instructor 定义匹配 schema，嵌入聚类做阻塞 |

**关键洞察**：Senzing 的 CEO 自称"我们卖变速器，不卖整车"——这反映了 ER 正成为一个独立的专业化组件而非 KG 平台的附属功能。对于严肃的 KG 项目，专业 ER 工具的投入会显著提升下游质量。

#### B.3.3 图聚类防止过度合并

纯粹的传递闭包（A=B, B=C → A=C）在 ER 中是危险的。推荐使用 **Louvain/Leiden 社区检测**自动切断弱边，形成健康的实体聚类而非错误的超级节点。

### B.5 第五层：Agent 编排与工作流引擎

| 框架 | 定位 | 状态管理 | 适用场景 |
|------|------|---------|---------|
| **LangGraph** | LangChain 的有状态图执行引擎 | 内置检查点、时间旅行 | 复杂多步骤 Agent 工作流 |
| **CrewAI** | 多 Agent 协作框架 | Agent 间消息传递 | 角色分工明确的 Agent 团队 |
| **PydanticAI** | Pydantic 团队的 Agent 运行时 | 类型化工具 + 可重放数据集 | Python 中心化 Agent |
| **Temporal** | 持久化工作流引擎 | ACID 级持久化、自动重试 | 关键任务级管线（金融合规） |
| **Prefect / Airflow** | 数据管线编排 | DAG 调度 + 重试 | 批处理 ETL/ELT 管线 |

**设计理念辩论：Agent 框架 vs 工作流引擎**

对于 ADE 管线，需要区分两类编排需求：
- **确定性流程**（文档解析 → 分块 → 提取 → 存储）→ 用 **Temporal/Prefect**，因为需要可靠重试、幂等性、任务可见性
- **非确定性推理**（"这个实体是人还是组织？需要更多上下文"）→ 用 **LangGraph/PydanticAI**，因为需要条件分支和 LLM 推理

**生产建议**：两者组合——Temporal 编排整体管线，在"提取"步骤内部使用 LangGraph 处理需要推理的子任务。
