# 声明元数据统一化蓝图

## 1. 背景

当前 `Entity`、`Rule`、`Derivation` 在“管理信息”上的表达并不统一：

- `Entity` 已经有 docstring 与 `Meta` 的概念
- `Rule` / `Derivation` 以 dataclass 形式声明，当前仅显式暴露 `id/version/status` 的一部分
- authoring compile 阶段主要保留执行语义字段，尚未形成统一的“声明元数据 contract”

这会带来两个问题：

1. 上层产品能力很难稳定依赖这些声明信息做检索、展示、管理和 LLM 上下文构造
2. `schema / rule / derivation` 三类资产虽然都具备“版本化声明”的性质，但表达方式割裂

本蓝图的目标是：在不引入泛化 `meta` 杂物袋的前提下，为三类声明建立一套最小统一元数据模型。

## 2. 目标与非目标

### 2.1 目标

- 统一 `Entity`、`Rule`、`Derivation` 的声明级管理字段
- 保持字段集合最小，仅引入：
  - `version`
  - `description`
  - `tags`
- 明确 `description` 的 fallback 规则
- 统一 authoring payload 的顶层形态，避免新增泛化 `meta`

### 2.2 非目标

- 不改变 core 执行语义
- 不引入新的运行时 policy / storage 语义
- 不在本阶段开放任意键的 `meta`
- 不要求三类声明在 Python 语法层面完全一致

## 3. 统一声明模型

三类声明统一到同一组“管理字段”：

- `decl_id`
- `version`
- `description`
- `tags`

其中 `decl_id` 只作为管理视角下的统一概念，不要求用户显式书写同名字段。

映射规则：

- `Entity.decl_id = entity_type`
- `Rule.decl_id = rule_id`
- `Derivation.decl_id = derivation_id`

## 4. 字段定义

### 4.1 `version`

- 类型：`str`
- 语义：声明版本，不等同于 assertion 级 `meta.version`
- 要求：非空字符串

### 4.2 `description`

- 类型：`str | None`
- 语义：人类可读说明，同时可承担面向 LLM 的提示职责
- 要求：若提供则必须为非空字符串

### 4.3 `tags`

- 类型：`list[str]`
- 语义：分类、检索、管理
- 要求：
  - 默认为空列表
  - 元素必须为非空字符串
  - 不参与编译或运行时语义决策

## 5. Entity 统一形态

### 5.1 SDK 声明形态

```python
class EmploymentEvent(Entity):
    """Fallback description when explicit description is absent."""

    class Meta:
        version = "v1"
        description = "Employment event in business domain"
        tags = ["employment", "event"]

    employee_id: str = Identity(primary_key=True)
    company: str = Field(cardinality="single")
    title: str = Field(cardinality="single")
```

### 5.2 规则

- `entity_type` 仍由类名推导，不新增独立 `schema_id`
- `description` 解析优先级：
  1. `Meta.description`
  2. class docstring
  3. `None`
- `tags` 来源于 `Meta.tags`
- `version` 来源于 `Meta.version`

### 5.3 authoring payload 目标形态

```python
{
  "entity_type": "EmploymentEvent",
  "version": "v1",
  "description": "Employment event in business domain",
  "tags": ["employment", "event"],
  "identity_fields": [...],
  "fields": [...],
}
```

## 6. Rule 统一形态

### 6.1 SDK 声明形态

```python
Rule(
    id="employment_match",
    version="v1",
    description="Find employment-related matches",
    tags=["employment", "match"],
    select=[...],
    where=[...],
    expose=False,
)
```

### 6.2 规则

- `decl_id` 对应 `rule_id`
- `description` 为显式字段，不做 docstring fallback
- `tags` 为显式字段，不参与编译语义

### 6.3 authoring payload 目标形态

```python
{
  "rule_id": "employment_match",
  "version": "v1",
  "description": "Find employment-related matches",
  "tags": ["employment", "match"],
  "select": [...],
  "where": [...],
  "expose": false,
}
```

## 7. Derivation 统一形态

### 7.1 SDK 声明形态

```python
Derivation(
    id="employment_event_from_cv",
    version="v1",
    description="Derive EmploymentEvent from resume evidence",
    tags=["employment", "extraction"],
    where=[...],
    head=...,
)
```

### 7.2 规则

- `decl_id` 对应 `derivation_id`
- `description` 为显式字段，不做 docstring fallback
- `tags` 为显式字段，不参与编译语义
- 在高层 authoring 语法中，`head` 应视为真相源
- `target` 继续保留为兼容字段，但不作为推荐统一形态的一部分

### 7.3 authoring payload 目标形态

```python
{
  "derivation_id": "employment_event_from_cv",
  "version": "v1",
  "description": "Derive EmploymentEvent from resume evidence",
  "tags": ["employment", "extraction"],
  "where": [...],
  "head": {...},
}
```

## 8. 为什么不引入泛化 `meta`

本阶段不引入 `meta: dict[str, Any]`，原因如下：

- `meta` 容易退化成无边界杂物袋
- `Rule` / `Derivation` 已经有较多执行语义字段，再叠加 `meta` 会放大认知歧义
- 仓库中已有多处使用 `meta` 表示 assertion / provenance / runtime 元数据，继续复用会增加歧义

因此本阶段坚持 typed metadata：

- `version`
- `description`
- `tags`

若未来出现新的稳定管理字段，应显式加入 contract，而不是回退到开放式 `meta`

## 9. 兼容性策略

### 9.1 Entity

- 兼容现有 docstring 描述机制
- 行为调整为：
  - 只有当未显式提供 `description` 时，才回退解析 docstring

### 9.2 Rule / Derivation

- 现有调用方若未提供 `description/tags`，行为保持不变
- compile 阶段新增对这些字段的透传与校验，但不影响现有执行字段

### 9.3 Derivation.target

- 短期：保留
- 中期：降级为冗余校验字段
- 长期：在高层 authoring API 中可选甚至隐藏，仅保留 compiled IR 的 `target_pred_id`

## 10. 迁移步骤

建议按以下顺序落地：

1. `Entity`
   - 支持 `Meta.version`
   - 支持 `Meta.description`
   - 支持 `Meta.tags`
   - 将 docstring 改为 `description` fallback
2. `Rule` / `Derivation`
   - SDK 对象增加 `description`、`tags`
   - `to_authoring_payload()` 透传这两个字段
3. authoring compiler
   - 校验并透传 `version/description/tags`
4. 文档与示例
   - SDK 文档、blueprint、tutorial 全部统一

## 11. 决策摘要

- 统一的是声明元数据 contract，不是 Python 语法表面形式
- 不引入开放式 `meta`
- 三类声明统一支持 `version/description/tags`
- `Entity` 的 `description` 采用“显式优先，docstring fallback”
- `Derivation.head` 是高层 authoring 的真相源，`target` 仅保留兼容价值
