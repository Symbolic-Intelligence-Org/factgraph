### 2026-06-02 — Step 4.2 review precision tightening (P2-1 / P2-2 / P3-1)

- **P2-1 — F6 reject mechanism distinction must survive into docs**: initial blueprint G4 / §5.3 / §7 phrasing "all 7 reject items" would have collapsed two distinct code mechanisms into one. Code at `sdk/store.py:2374-2395` splits cleanly: 5 keys (`view=, policy=, semantics_profile=, mode=, temporal_view=`) use `if "X" in kwargs:` checks (hard presence — even `key=None` raises) while 2 keys (`registry=, engine_options=`) use `kwargs.pop("X", None)` + non-None guard (only non-None raises). Docs must keep the two columns distinct or users debugging `evaluate(view=None)` raises will be surprised. Amended phrasing locks in this precision.

- **P2-2 — F4 target shapes need explicit enumeration, not "field cell" hand-wave**: `conflicts(target)` accepts 4 distinct target shapes routed through two helpers — `_resolve_record_asrt_id` (1326-1332) covers shapes 1 (asrt_id string) + 2 (object with `.asrt_id`), and `_conflict_cell_for_target` (1341-1369) adds shapes 3 (`(entity, Field)`) + 4 (`(entity, field_name: str)`) via a tuple-arity-2 branch before falling through to `_claim_for_audit_target` (1370). Critical asymmetry: `fg.audit.explain(target)` at 1373 only calls `_claim_for_audit_target` (no tuple branch), so shapes 3+4 work for `conflicts` but NOT for `explain`. Step 4.7 docs must call this asymmetry out — a footnote on §2.12 explain row is sufficient. §5.3 amended to enumerate shapes 1-4 explicitly + footnote requirement; §7 Acceptance F4 checkbox upgraded from signature-only to signature + enumeration + footnote.

- **P3-1 — Related Code anchor split**: `conflicts` signature lives at 1382-1385; its target-normalization logic lives in two separate helpers at 1326-1339 (`_resolve_record_asrt_id` + `_claim_for_audit_target`) and 1341-1371 (`_conflict_cell_for_target`). Initial blueprint cited only the signature line range, leaving Step 4.7 author one indirection away from the actual normalization logic. Two anchor rows added to §0 Related Code so Step 4.7 can land each docs sentence with a direct line citation.

- **Why amend on blueprint branch, not preflight branch**: per Slice 7B precedent and CLAUDE.md cadence governance, Step 4.2 fast-pass amendments stay on the blueprint branch — preflight branch is reserved for Step 4.3 artifact + Step 4.4 finding-derived amendments. This keeps the audit trail clean: blueprint branch sees Step 4.1 draft + Step 4.2 amend; preflight branch (created at Step 4.3) sees only Step 4.3 onwards.
