## 1. Problem

Parent essay C98 (§10.6.2) describes ArithExpr as a value-producing expression language for comparison LHS/RHS, with authoring examples like score arithmetic and division handling. The shipped implementation is narrower but already has a useful substrate:

- SDK object DSL has `BinaryExpr` for `+`, `-`, `*`, and unary `-` over `LogicVar`/existing `BinaryExpr` shapes (`src/factgraph/sdk/dsl/expr.py:134-176`).
- SDK lowering already emits core arithmetic builtin IR for those forms (`src/factgraph/sdk/dsl/expr.py:438-464`).
- Core AST, validation, Python evaluation, and Souffle compilation already accept five arithmetic builtin tags: `add`, `sub`, `neg`, `addc`, and `mulc` (`src/factgraph/core/rules/where_ast.py:95-96`, `src/factgraph/adapters/souffle/where_compile.py:20`).
- ProbLog export still has no arithmetic branch (`src/factgraph/adapters/problog/problog_export.py:208-276`), so the existing arithmetic builtin substrate is not portable across adapters.

This slice closes the ProbLog parity gap for the already-shipped five arithmetic builtin forms and adds explicit tests for the SDK-to-application bridge that already produces those forms. It does **not** complete the full C98 vision for `/`, AttrRef arithmetic syntax, float literals, or division-by-zero evidence semantics.

## 2. Goals

### 2.1 C98 / §8.7 — Export shipped arithmetic builtins to ProbLog

Add ProbLog export support for existing core arithmetic builtin atoms:

- `BuiltinAtom("add", (out, lhs, rhs))`
- `BuiltinAtom("sub", (out, lhs, rhs))`
- `BuiltinAtom("neg", (out, value))`
- `BuiltinAtom("addc", (out, var, integer_const))`
- `BuiltinAtom("mulc", (out, var, integer_const))`

The export target is ProbLog/Prolog `is/2`, for example `V_TMP is V_SCORE + 1`. This maps the shipped arithmetic substrate from parent essay §8.7 to ProbLog without adding new expression kinds.

### 2.2 C98 / §10.6.2 — Make existing SDK BinaryExpr bridge coverage explicit

Add tests proving the current SDK bridge can already lower supported arithmetic shapes into application `Rule.where` core AST:

- `(u + 1) == 3` lowers through `BinaryExpr` to `BuiltinAtom("addc", ...)` plus `CmpAtom("eq", ...)`.
- `-(u) == -1` lowers to `BuiltinAtom("neg", ...)` plus comparison.
- `u * 2` lowers to `BuiltinAtom("mulc", ...)` where used in a comparison.

These are not new public syntax promises; they document and protect the shipped substrate before adding ProbLog parity.

### 2.3 C98 / §8.7 — Preserve Souffle and Python behavior

Do not alter core or Souffle arithmetic lowering unless tests expose a compatibility bug. Souffle already has arithmetic lowering for the five shipped builtin tags at `src/factgraph/adapters/souffle/where_compile.py:1060-1103`, and Python evaluation already has runtime evaluation at `src/factgraph/core/rules/where_eval.py:773-826`.

### 2.4 G5 — Document incomplete C98 surface explicitly

Record that this S-class slice is a substrate/parity step, not full C98 completion. Full C98 user-facing examples that require `AttrRef` arithmetic, `/`, float literals, or division-by-zero semantics remain deferred.

## 3. Non-goals

- No `div` builtin, `/` operator, or div-by-zero violation/evidence behavior. Parent essay §8.7 and §10.6.2 discuss division, but shipped core builtin tags do not include `div` (`src/factgraph/core/rules/where_ast.py:95-96`; `src/factgraph/core/rules/where_ast_validate.py:33-35`).
- No `User(u).score + 1` / `AttrRef` arithmetic. `AttrRef` currently defines comparison methods but no arithmetic operators (`src/factgraph/sdk/dsl/expr.py:100-130`), and T1.2 deferred non-equality AttrRef compare.
- No `User(u).score < User(u).age * 0.7 + 5` full essay syntax. That requires AttrRef arithmetic, float literal support, and non-equality AttrRef comparison.
- No float numeric literal support. Shipped `_is_numeric_literal(...)` accepts `int` but excludes `bool` (`src/factgraph/sdk/dsl/expr.py:467-468`).
- No non-linear multiplication. Shipped `_lower_binary_expr(...)` rejects `BinaryExpr("mul", non_constant, non_constant)` (`src/factgraph/sdk/dsl/expr.py:454-464`).
- No AggregateExpr / NoValue work; those remain T2.3.
- No PyReason adapter parity.
- No fix for the known ProbLog fixture baseline `meta[confidence] was removed`; closure must document it if a full ProbLog test gate reaches that baseline.

## 4. Current Context

### 4.1 G2/G3 — SDK BinaryExpr already exists but is narrower than C98 examples

`src/factgraph/sdk/dsl/expr.py:134-176` defines `BinaryExpr` and its arithmetic operators. It supports `+`, `-`, `*`, and unary `-`, but no `/`.

`src/factgraph/sdk/dsl/expr.py:100-130` defines `AttrRef` comparison operators and has no arithmetic operator methods, so `User(u).score + 1` is currently a `TypeError`.

`src/factgraph/sdk/dsl/expr.py:438-464` lowers existing `BinaryExpr` values to raw builtin IR:

- `neg` -> `("neg", tmp, value)`
- `add` -> `("add", tmp, lhs, rhs)` or `("addc", tmp, var, const)`
- `sub` -> `("sub", tmp, lhs, rhs)` or `("addc", tmp, var, -const)`
- `mul` -> `("mulc", tmp, var, const)` only when one side is an integer literal

`src/factgraph/sdk/dsl/expr.py:480-489` rejects a standalone `BinaryExpr` as a head/term value, so arithmetic must appear through comparison lowering, not as a predicate term.

### 4.2 G2/G3 — Application bridge already carries arithmetic into Rule.where

`src/factgraph/sdk/dsl/application_rule.py:40-69` builds an application `Rule` by calling `lower_where(...)`, parsing the lowered IR with `parse_where_ir_to_ast(...)`, and canonicalizing atoms before constructing `ApplicationRule`.

`src/factgraph/sdk/dsl/application_rule.py:172-175` already includes `BuiltinAtom` in variable collection, and `src/factgraph/sdk/dsl/application_rule.py:236-240` canonicalizes `BuiltinAtom` args.

`src/factgraph/application/protocol/rule.py:44-47` stores `where` as `tuple[Atom, ...]`, and T1.1 permits core `BuiltinAtom` values in that tuple.

### 4.3 G2/G3 — Core AST, validation, and Python eval already ship five arithmetic tags

`src/factgraph/core/rules/where_ast.py:64-68` defines `BuiltinAtom`.

`src/factgraph/core/rules/where_ast.py:95-96` defines:

```python
_BUILTIN_TAGS = {"add", "sub", "neg", "addc", "mulc"}
```

`src/factgraph/core/rules/where_ast.py:209-214` parses those tags into `BuiltinAtom`.

`src/factgraph/core/rules/where_ast_validate.py:210-218` validates builtin op membership, and `src/factgraph/core/rules/where_ast_validate.py:254-278` validates the supported shapes.

`src/factgraph/core/rules/where_eval.py:38` defines `_ARITH_KINDS = {"add", "sub", "neg", "addc", "mulc"}`, and `src/factgraph/core/rules/where_eval.py:773-826` evaluates those forms.

### 4.4 G2/G3 — Souffle already lowers five arithmetic tags

`src/factgraph/adapters/souffle/where_compile.py:20` defines `_ARITH_KINDS = {"add", "sub", "neg", "addc", "mulc"}`.

`src/factgraph/adapters/souffle/where_compile.py:721-765` validates arithmetic shapes.

`src/factgraph/adapters/souffle/where_compile.py:562` dispatches arithmetic builtins from the main body, and `src/factgraph/adapters/souffle/where_compile.py:1050` dispatches arithmetic builtins from `not` body compilation.

`src/factgraph/adapters/souffle/where_compile.py:1060-1103` compiles `add`, `sub`, `neg`, `addc`, and `mulc` using `to_number(...)` and `to_string(...)`.

### 4.5 G2/G3 — ProbLog has no arithmetic branch

`src/factgraph/adapters/problog/problog_export.py:202-205` compiles a body by joining `_compile_atom(...)` output.

`src/factgraph/adapters/problog/problog_export.py:208-276` handles `pred`, `eq`, `ne`, ordering comparisons, `in`, and `not`. There is no branch for `add`, `sub`, `neg`, `addc`, or `mulc`.

### 4.6 Known test baseline

ProbLog hygiene fixed the import cycle, but the full ProbLog test gate can now surface an unrelated fixture baseline: `WriteProtocolError: meta[confidence] was removed`. This is not in T2.2 scope unless implementation directly touches affected fixtures; closure must document any such baseline per §7.

## 5. Proposed Shape

### 5.1 ProbLog builtin export

Add arithmetic builtin support inside `src/factgraph/adapters/problog/problog_export.py:_compile_atom(...)`.

Expected mapping:

| Core builtin | ProbLog expression |
| --- | --- |
| `("add", out, lhs, rhs)` | `OUT is LHS + RHS` |
| `("sub", out, lhs, rhs)` | `OUT is LHS - RHS` |
| `("neg", out, value)` | `OUT is -VALUE` |
| `("addc", out, var, const)` | `OUT is VAR + CONST` |
| `("mulc", out, var, const)` | `OUT is VAR * CONST` |

The implementation should keep shape checks local to export so malformed raw tuples fail with clear errors even when the caller bypasses core validation.

### 5.2 No new core builtin tags

Do not add `div` to `_BUILTIN_TAGS`, `_DEFAULT_BUILTINS`, `_ARITH_KINDS`, Souffle `_ARITH_KINDS`, or SDK lowering. That would expand beyond the already-shipped substrate and requires div-by-zero semantics from parent essay §10.6.2.

### 5.3 SDK bridge tests for shipped substrate

Add tests around the existing DSL-to-application bridge, not new syntax:

- `(u + 1) == 3` results in `BuiltinAtom("addc", ...)` plus `CmpAtom("eq", ...)`.
- `u * 2` results in `BuiltinAtom("mulc", ...)` plus `CmpAtom("eq", ...)` when wrapped in a comparison.
- `User(u).score + 1` remains unsupported in this slice and may be captured as an explicit non-goal or negative smoke if useful.

### 5.4 G7 pre-impl precondition

Before implementation, verify these assumptions on the impl branch:

1. `div` is not present in core/Souffle/Python arithmetic tag sets.
2. `AttrRef` still has no arithmetic operator methods.
3. `src/factgraph/adapters/problog/problog_export.py:_compile_atom(...)` still lacks arithmetic builtin branches.
4. Existing SDK arithmetic lowering smoke still produces `BuiltinAtom("addc", ...)` for `(u + 1) == 3`.

If any assumption fails, amend this blueprint before code implementation.

## 6. Boundaries And Invariants

- **Existing-substrate invariant**: T2.2 implements ProbLog export for already-shipped arithmetic builtin tags only.
- **No-div invariant**: `/`, `div`, and div-by-zero semantics are deferred.
- **AttrRef boundary invariant**: no `AttrRef` arithmetic operators and no non-equality AttrRef compare are added.
- **Integer-literal invariant**: constant arithmetic stays aligned with shipped `int` literal support; floats remain deferred.
- **Adapter parity invariant**: Souffle behavior should not change except for tests proving current support.
- **ProbLog `is/2` invariant**: arithmetic builtins export as deterministic arithmetic computations, not probabilistic facts or evidence writes.
- **Baseline separation invariant**: `meta[confidence]` fixture drift is not fixed here unless implementation necessarily edits those fixtures; otherwise it is recorded in closure.
