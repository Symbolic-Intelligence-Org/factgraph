## 1. Problem

F1-lite and F2A now provide exact semantic Rule-port contracts and stable
occurrence-qualified addresses. The next necessary link is a Policy value that
states how managed Rule occurrences compose, while reusing the shipped RuleExpr
and native lowering path.

The shipped lowerer currently drops an explicit join from a DNF branch that
lacks one endpoint. That behavior is observable but neither specified nor
covered by an asymmetric lowering golden. It also rewrites repeated aliases
without retaining their authored alias. A managed Policy compiler therefore
cannot merely pass arbitrary Policy-shaped input through the existing lowerer.

## 2. Scope

This decision locks a deliberately small Policy v0:

- `Policy(id, version, when)`;
- `PolicyOccurrence(alias)` as a reference into an exact
  `SemanticAddressSpace`;
- `PolicyAll`, `PolicyAny` and equality-only `PolicyUnify`;
- deterministic compilation into the existing RuleExpr body substrate;
- head-independent, machine-checkable authored-node → DNF branch → lowered
  occurrence/body-atom/join lineage.

## 3. Non-scope

- `Compare`, literals, field navigation or derived-path materialization.
- Query, bind, select, expect, synthetic head, Evaluate or Explain.
- Policy persistence, codec, registry, Package, Plan, Meander or Agent APIs.
- Policy-language Not/Unless, priority, aggregate, temporal or rule overlay.
- Soufflé/ProbLog/PyReason parity or any new engine execution path.

`Compare` is intentionally split out. RuleExpr has no authored comparison
constraint surface: adding it here would either create a second constraint
lowering or disguise comparison as a synthetic Rule. The split is a scope
control, not a decision that Policy will never support comparison.

## 4. Decision

### 4.1 Policy references the F2A namespace

The Policy AST stores authored occurrence aliases, not Rule objects and not
lowered aliases. `compile_policy(policy, address_space=...)` requires the set of
occurrence aliases used by the AST to exactly equal the supplied address-space
aliases. There are no ambient or unused occurrences.

Each occurrence alias appears exactly once in the Policy AST. The same Rule may
still appear under multiple explicit aliases. All managed occurrences must pin
the same schema digest, and every Rule/contract pair is rechecked at compile
time.

### 4.2 Managed Rule admission is a conservative v0 allowlist

Policy v0 admits only Rules whose top-level body atoms are:

- `PredAtom`; or
- `CmpAtom` with a shipped comparison op (`eq/ne/gt/ge/lt/le`) and no aggregate
  term.

`NotAtom`, `InAtom`, `BuiltinAtom`, aggregates and any unrecognized body shape
fail with `UNSUPPORTED_MANAGED_RULE_CAPABILITY` during `policy_admission`.
Legacy Rule and RuleExpr paths remain unchanged.

Actual compiler-reserved Rule-id namespaces are rejected during admission. F2B
does not generate a synthetic head or a `__query__` identifier, so AC-21 is only
closed for the namespace boundary this slice actually owns; Query-head
collision behavior remains an F3 obligation.

### 4.3 SC-01 uses reject-on-partial for managed Policy only

`PolicyUnify` is an equality constraint between two direct
`SemanticPortAddress` values. It must be a direct child of a `PolicyAll` node,
and both endpoint occurrences must be present in every branch generated by that
`PolicyAll` subtree. Otherwise compilation fails before RuleExpr lowering with
`PARTIAL_BRANCH_CONSTRAINT`.

This is a conservative v0 product choice, not a claim that the vertical probe
proved one uniquely correct semantic. The legacy RuleExpr behavior is not
changed. A branch-local constraint must be authored inside an `All` subtree
whose own branches all contain both endpoints.

The endpoints must belong to different occurrences and resolve to the exact
same semantic endpoint. Identity-to-field, different entity identities and
different field paths are rejected. Broader schema-backed coercion is deferred.

### 4.4 DNF limit is a static compiler capability

Policy v0 uses the shipped limit of 32 DNF branches. The compiler performs a
bounded projected-count check before calling structural RuleExpr lowering:

- 32 branches are accepted;
- more than 32 fails with `POLICY_DNF_BRANCH_LIMIT_EXCEEDED` at
  `policy_compile` and reports both limit and projected count;
- this is not a logical false result and does not invoke an engine.

Runtime row/time/memory budgets are separate Query/execution concerns.

### 4.5 Lineage is generated during lowering, never reconstructed from repr

Policy nodes receive deterministic content-derived node IDs. `All` and `Any`
are canonical and order-insensitive; duplicate canonical children reject.

The shipped RuleExpr body lowering is factored into a head-independent internal
plan. Alias rewriting retains an explicit optional authored alias beside each
lowered occurrence binding. Policy compilation consumes that exact plan and
emits immutable structural lineage for:

- DNF branches;
- lowered occurrences, including one authored occurrence copied into multiple
  branches;
- each occurrence-owned body atom and its branch-local condition index;
- each lowered equality constraint.

Every authored Policy node must map to at least one lowered reference, and every
lowered reference emitted in the Policy artifact must map back to one or more
authored node IDs. Branch IDs, generated aliases and condition indexes are
artifact-local coordinates; only authored occurrence aliases remain public
semantic addresses.

### 4.6 The compiled artifact is structural, not executable

The application-layer result pins Policy identity, address-space identity,
Rule/contract identities, exact RuleExpr body structure, branch inventory and
lineage. It has no head, selection, runtime config, snapshot or result rows and
cannot be passed off as a completed evaluation.

## 5. Rejected Alternatives

### Option A: Preserve current partial-join filtering as Policy semantics

Rejected because it can silently remove an authored condition from one branch
and has no specification or asymmetric golden establishing author intent.

### Option B: Rewrite the RuleExpr/DNF evaluator for Policy

Rejected because RuleExpr already supplies the needed Boolean and equality
substrate. F2B adds a checked adapter and provenance, not a second engine.

### Option C: Include Compare by generating synthetic Rules

Rejected for this slice because generated relations would add namespace,
capability and lineage semantics before a direct-comparison contract has been
decided.

## 6. Consequences

- F3 can build Query projection and execution on a head-independent compiled
  Policy without asking an Agent to provide a head.
- The UI/Explain layers can later consume explicit lineage rather than guessing
  from generated aliases or variable names.
- Policy v0 is intentionally less expressive than raw RuleExpr; unsupported
  managed shapes fail explicitly while the legacy path remains available.
- A later Compare slice must decide direct comparison lowering and semantic
  type compatibility before adding syntax.

## 7. Acceptance Criteria

- [x] `All/Any/Occurrence/Unify` compile deterministically against one exact address space.
- [x] Partial-branch Unify rejects before structural lowering; explicit local forms compile.
- [x] 32 DNF branches compile and 33 reject with a typed static-capability error.
- [x] Managed Rule allowlist, stale contracts and reserved namespaces fail distinctly.
- [x] Authored-to-lowered and lowered-to-authored lineage are total for every compiled artifact.
- [x] Reordered commutative input has the same Policy digest, branch inventory and lineage.
- [x] Existing RuleExpr/lowering/evaluate/Explain behavior remains unchanged.
- [x] No Compare, Query, synthetic head, engine execution or Meander surface is added.
